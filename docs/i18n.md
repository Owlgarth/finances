# Internationalization (i18n)

Owlgarth Finances ships its UI in English, Ukrainian, and Polish, and translates backend
API error messages to the requester's language. Scope: UI strings, backend API error
messages, and per-user number and date display formatting. Emails and legal document
text stay English by design.

The current Ukrainian and Polish translations (frontend catalogs and backend `.po`
messages) were generated with AI tools. Mechanical integrity is enforced by the guards
(key parity, placeholder parity, plural-family coverage, `msgfmt`); phrasing naturalness
has not had a full human review pass, so improvements land as ordinary follow-up edits
via the [Language lifecycle](#language-lifecycle) procedure.

Out of scope, deliberately:

- `document.title` (browser-tab text) stays English.
- Amount input is normalized client-side, not by the API: inputs accept both decimal
  separators, and `normalizeAmountInput` (`src/utils/amountInput.ts`) rewrites what the
  user typed per the active number style at each submit boundary, before validation and
  send - the wire shape stays dot-decimal. Display formatting remains style-driven via
  `configureFormatting` (see [Architecture](#architecture)).
- Persisted data never depends on language. Period names, seeded workspace/account
  names, and API-written transaction descriptions (for example the balance-adjustment
  description) stay byte-identical in every language.
- Django Ninja 422 array `detail` payloads are pretty-printed client-side:
  `getApiErrorMessage` (`src/utils/errors.ts`) dedupes the elements' `msg` strings
  (translated server-side) and joins them with `'; '` into one line. There is no
  backend error-code system by design.

## Architecture

- **One registry decides what exists**: `backend/common/languages.json` (full contents
  in [Preferences](#preferences) below). The backend reads it through
  `backend/common/languages.py` constants to validate preference values and defaults;
  the frontend imports the JSON directly across the tree (vite `server.fs.allow` permits
  the repo root, tsconfig sets `resolveJsonModule`), so the UI and the API can never
  disagree about the language list. Never add a second hardcoded language list anywhere.
- **Frontend catalogs**: `frontend/src/i18n/locales/<lang>/<ns>.json` - 12 namespaces:
  auth, nav, accounts, transfers, budgets, transactions, planned, dashboard, members,
  settings, common, numbers. Each namespace is owned by the pages and components that
  render it; new keys for a surface go into its owning namespace:

  | Namespace | Owned by |
  | --- | --- |
  | `auth` | Login, Register, VerifyEmail, ConfirmEmailChange, ReConsent pages; AuthContext toasts |
  | `nav` | Sidebar, BottomNav, UserMenu, ThemeToggleRow, LanguageModal; command-palette destinations |
  | `accounts` | Accounts page; account and set-balance modals |
  | `transfers` | Transfers page; transfer modal |
  | `budgets` | Budgets list, detail, and periods pages; PeriodPicker, PeriodCard; period and categories modals |
  | `transactions` | Transactions page; transaction form modal; list filter fields; attachments and items editor/list; extraction review |
  | `planned` | Planned page; planned form modal |
  | `dashboard` | Dashboard page; legal pages (Privacy, Terms, LegalDocPage) |
  | `members` | Members page; RoleBadge |
  | `settings` | Profile page and profile forms (incl. PreferencesForm); currencies settings and currency set field; workspace selector, settings panel, create form |
  | `common` | Shared primitives (Modal, Select, MultiSelect, ConfirmDialog, Pagination, SearchInput, ActionSheet, listbox parts, FilterBar); MainLayout; NotFound page; command-palette chrome |
  | `numbers` | Number/date-adjacent widgets: DatePicker; dashboard BudgetInsights chart labels |

  The general frontend file map is in [docs/frontend.md](frontend.md).
- **Bootstrap is synchronous**: `src/i18n/index.ts` eagerly loads every catalog via
  `import.meta.glob`, and `main.tsx` imports it before rendering, so `i18next.init`
  completes before any component renders - no language flash. The inline script in
  `index.html` sets `<html lang>` pre-paint from localStorage (`owlgarth_language`)
  using a hardcoded mini-list that must be kept in sync with the registry by hand.
  Detection order: localStorage, then navigator, then `'en'`. `<html lang>` has three
  writers: the inline script covers the stored choice pre-paint, the i18n bootstrap
  syncs it to the resolved language after init for every detection path (navigator
  included), and `setLanguage` syncs it on an explicit switch.
- **Backend errors arrive translated**: the API client sets `Accept-Language` on every
  request (`setApiLanguage` in `src/api/client.ts`, seeded from localStorage at startup
  and updated by `LanguageContext` on every language change).
- **Number and date formatting is a module singleton** in `src/utils/format.ts`:
  `configureFormatting({ numberStyle, dateLocale })`. `LanguageContext` is the sole
  writer - it applies the config on first render, on every language or number-format
  change, and when authenticated preferences arrive. Two number styles: `en`
  (1,234.56) and `eu` (1 234,56, where the grouping separator is a non-breaking space
  U+00A0 and the decimal separator is a comma). Date shapes follow the number style
  while month names follow the UI language's date-fns locale: en renders the
  "Apr 1 2026" family, eu renders "01.04.2026". `formatAmount` call sites never pass a
  style or locale. `formatPeriodName` is the deliberate exception: it ignores the
  singleton entirely because its output is persisted as period names and mirrors the
  backend's naming byte for byte - see the warning in `src/utils/format.ts`.

## Preferences

`UserPreferences.language` and `UserPreferences.number_format` (`PATCH
/api/users/me/preferences`) are validated against the registry and defaulted from the
`DEFAULT_LANGUAGE` / `DEFAULT_NUMBER_FORMAT` env vars (see `backend/example.env`). On
first load after login the server preference wins, applied silently with no PATCH;
anonymous visitors get localStorage plus browser detection. The number format has its
own localStorage key (`owlgarth_number_format`); precedence is the server value, then
localStorage, then the registry default.

The switcher is a single "Language" row (Globe icon) in the desktop UserMenu dropdown
and the mobile BottomNav More sheet; both close their own container and open
`LanguageModal` (mount-per-use), which renders one selectable card per registry
language. The Profile > Preferences form Selects derive their options from the
registry at module level (`registry.languages.map` in
`frontend/src/components/profile/PreferencesForm.tsx`), so adding a language needs no
UI change in either surface. An authenticated switch is optimistic: the UI language
changes immediately, then a fire-and-forget preferences PATCH runs and invalidates the
preferences query; a failed PATCH only toasts - it never reverts the switch.

Registry (`backend/common/languages.json`, verbatim):

```json
{
  "defaultLanguage": "en",
  "languages": [
    {"code": "en", "englishName": "English", "nativeName": "English", "dateFnsLocale": "enUS"},
    {"code": "uk", "englishName": "Ukrainian", "nativeName": "Українська", "dateFnsLocale": "uk"},
    {"code": "pl", "englishName": "Polish", "nativeName": "Polski", "dateFnsLocale": "pl"}
  ],
  "numberFormats": [
    {"code": "en", "label": "1,234.56"},
    {"code": "eu", "label": "1 234,56"}
  ],
  "defaultNumberFormat": "en"
}
```

## Key conventions

- Nested JSON, at most two levels (`section.control`), camelCase leaf keys.
- A key exists in ALL THREE languages or `npm run i18n:check` fails.
- Plurals use the i18next `count` option: `key_one`/`key_other` in English; the full
  `_one`/`_few`/`_many`/`_other` set in Ukrainian and Polish. Required categories are
  derived per language from `Intl.PluralRules`, never hardcoded.
- Interpolation is `{{name}}`, double-brace, matching i18next defaults.
- No markup in values; components compose, values are plain text.
- English values keep typographic characters (em dash, ellipsis, curly quotes) as
  `\uXXXX` JSON escapes so the catalogs stay ASCII-clean; translated values use plain
  hyphens and ASCII punctuation.
- New UI text goes through `t()` with keys in the owning namespace (table in
  [Architecture](#architecture)). `aria-label`, `placeholder`, `title`, and `alt`
  attributes count as UI text - the ESLint `no-literal-string` rule warns on new
  literals in those positions.
- Removing a key goes through `npm run key:rm` (it gates on `npm run key:find`), never
  a hand edit across three files.

## Language lifecycle

How a language is created, edited, and removed, plus the end-to-end flow every change
rides on. Background lives in [Architecture](#architecture) and
[Preferences](#preferences); backend message handling lives in the
[Backend gettext workflow](#backend-gettext-workflow). Commands run from `frontend/`
unless noted.

### Create

Walkthrough in order:

1. `npm run lang:add <code> <englishName> <nativeName> <dateFnsLocale>` - for example
   `npm run lang:add de German Deutsch de`. The code must match `^[a-z]{2,3}$` and
   must not already exist. The script adds the registry entry (inserted at the sorted
   position without reordering the existing entries) and creates
   `src/i18n/locales/<code>/*.json` for all 12 namespaces, seeded with the current
   ENGLISH values on purpose: `i18n:check` fails until they are translated, so a
   language cannot ship with English placeholders in place.
2. Add the date-fns import and map entry in `src/i18n/dateLocales.ts`
   (`IMPORTED_LOCALES` is keyed by the registry's `dateFnsLocale` name).
3. Extend the hardcoded mini-list in `frontend/index.html`'s FOUC script. The script
   prints reminders for this step and the previous one.
4. `frontend/.i18rc` needs no hand edit: `lang:add` has already added the code to its
   `locales` array (the script prints the resulting list). That array is what
   `npm run i18n:extract` reads.
5. Translate every namespace file. Values identical to English fail `i18n:check`
   unless allowlisted in `frontend/scripts/i18n-allowlist.json` (`<ns>.<key.path>`
   entries per language) - only genuinely identical entries (brand strings) belong
   there.
6. Backend messages (from `backend/`): `uv run python manage.py makemessages -l <code>
   --no-obsolete`, translate `backend/locale/<code>/LC_MESSAGES/django.po`, then
   `uv run python manage.py compilemessages` or restart the api/worker containers
   (both entrypoints compile on boot). See the plural-header warning in the backend
   workflow below.
7. Gates: `npm run i18n:check` green, `npm run build` green (typegen derives from the
   en catalogs only, so `i18n.d.ts` needs no change), backend `pytest -q` green.
8. The switcher modal and the preference Selects render from the registry - no UI
   change needed.

Languages whose plurals need categories the built-in probe counts do not cover
(Arabic zero/two, for example) also require extending `PLURAL_PROBE_COUNTS` in
`frontend/scripts/i18n-check.mjs`.

### Edit

There is deliberately no `lang:edit` script: edits are rare and heterogeneous (a name
here, one msgstr there), so each kind below is a hand edit, and the gates at the end
of this section catch drift.

- **Registry entry** (`nativeName`, `englishName`, `dateFnsLocale`): hand-edit
  `backend/common/languages.json`, preserving its one-line-per-entry style - the
  `lang:add`/`lang:rm` serializer rewrites the whole file in that shape, so any
  multiline deviation gets normalized away on the next script run. Renaming a `code`
  is a remove plus a create, not an edit: the code keys the locale directory,
  `.i18rc`, `backend/locale/`, and users' stored preferences.
- **Frontend catalog values**: hand-edit the language's
  `src/i18n/locales/<code>/<ns>.json`. `npm run i18n:check` gates key parity against
  en and rejects values left identical to English (allowlist excepted). Key-level
  changes go through `npm run key:rm` and re-adding per
  [Key conventions](#key-conventions), never a hand delete across three files.
- **Backend messages**: change the English source string first (that string is the
  msgid), then rerun `makemessages` - it regenerates the msgids for every language,
  and each translation gets re-authored against the new source. After every
  regeneration, mind the plural-header warning in the
  [Backend gettext workflow](#backend-gettext-workflow).
- The FOUC mini-list in `frontend/index.html` and the imports in
  `src/i18n/dateLocales.ts` change only when a `code` or `dateFnsLocale` changes -
  never for value edits.

Gates after any edit: `npm run i18n:check` green (parity, untranslated values),
`npm run build` green (typegen), `npm run lang:list` clean (registry vs on-disk
drift), and backend `pytest -q` green when `.po` files changed.

### Remove

`npm run lang:rm <code>` removes the locale directory (`src/i18n/locales/<code>/`),
the registry entry, and the code's `.i18rc` entry. It refuses the default language,
the last remaining language, and unknown codes. After it runs, finish by hand:

1. Remove the language's date-fns import and its `IMPORTED_LOCALES` entry in
   `src/i18n/dateLocales.ts`.
2. Shrink the hardcoded mini-list in `frontend/index.html`'s FOUC script.
3. Delete `backend/locale/<code>/` entirely - `django.po` and the compiled
   `django.mo`. `makemessages` never prunes locale directories, so a removed
   language's catalog lingers (and its `.mo` keeps being recompiled by the
   entrypoints) until deleted by hand.
4. No UI change: `LanguageModal` and the preference Selects render from the registry,
   so the removed language disappears from both on the next build.

Stale `owlgarth_language` values in localStorage on user devices are harmless:
i18next is configured with `supportedLngs` (the registry codes) and `fallbackLng`
(the registry default), so an unsupported stored code falls back to the default
language.

### End-to-end flow

Every step below is described in detail in its own section; this trace is the map. A
language exists because the registry says so; the frontend renders from catalogs
bundled at build time; the backend translates error messages at request time from
gettext catalogs compiled in the entrypoints.

1. `backend/common/languages.json` is the single source. The backend reads it through
   `backend/common/languages.py` constants; the frontend imports the JSON across the
   tree. There is never a second list.
2. The en catalogs drive typegen: `src/i18n/i18n.d.ts` derives its resource types
   from `src/i18n/locales/en/*.json`, so `t()` keys are compile-checked
   ([Guards](#guards)).
3. Every language's catalogs are bundled at build time (eager `import.meta.glob` in
   `src/i18n/index.ts`).
4. `i18next.init` is synchronous and `main.tsx` imports it before rendering - no
   language flash, no loading state.
5. The inline FOUC script in `index.html` sets `<html lang>` pre-paint from
   localStorage.
6. The user switches via `LanguageModal` (the "Language" row in the UserMenu dropdown
   or the BottomNav More sheet) or the Preferences form Selects. A switch is
   optimistic: `setLanguage` applies locally, an authenticated fire-and-forget PATCH
   persists it, `['user-preferences']` is invalidated, and the server preference
   wins on the next load.
7. Every API call carries `Accept-Language` (`setApiLanguage` in `src/api/client.ts`,
   seeded at startup, updated on every switch).
8. `LocaleMiddleware` resolves the header; runtime `gettext` serves the translated
   message.
9. The translations live in `backend/locale/<lang>/LC_MESSAGES/django.po`, edited by
   hand (see the [Backend gettext workflow](#backend-gettext-workflow)).
10. `compilemessages` - both Docker entrypoints run it on boot - compiles `.po` into
    the `.mo` catalogs Django reads at runtime.

## Tooling reference

All scripts are dependency-free Node ESM under `frontend/scripts/` (Node >= 20).

| Command | What it does |
| --- | --- |
| `npm run lang:list` | Prints the registry (languages, number formats) and every locale directory with its namespace file count. Locale directories are enumerated from the filesystem, so this is where registry drift shows up. |
| `npm run lang:add <code> <englishName> <nativeName> <dateFnsLocale>` | Adds the registry entry and scaffolds `src/i18n/locales/<code>/*.json` from the en catalogs with values copied verbatim, forcing translation. Also adds the code to the `locales` array in `frontend/.i18rc` automatically. Prints the manual follow-ups (dateLocales.ts, index.html mini-list). |
| `npm run lang:rm <code>` | Removes the locale directory, the registry entry, and its `.i18rc` entry. Refuses the default language, the last remaining language, and unknown codes. |
| `npm run key:find <ns>.<key>` | Lists code references to a key. Accepts `ns.key` and `ns:key` forms; matches `t('a.b')`, `t('ns:a.b')`, and bare labelKey strings in files that call `useTranslation('<ns>')`; comments count as references. Prints `no references` when clean. Static literals only: dynamic key variables and the `t('key', { ns })` option-object form are invisible. |
| `npm run key:rm <ns>.<key>` | Deletes a key (and its plural siblings) from every language's namespace file. Refuses with zero writes while `key:find` still sees references; `--force` overrides (discouraged - only sane when the remaining hits are dead comments). |
| `npm run i18n:extract` | Runs i18next-parser over `src/` per `frontend/.i18rc`, appending newly seen `t()` keys to the catalogs with empty values (flagged by `i18n:check` until filled). An append-only assist, not a gate: it reformats every catalog it touches (key sort, de-escaping), it never removes keys the parser cannot see, and its `locales` list is the `.i18rc` array that `lang:add`/`lang:rm` keep in sync. Catalogs are hand-authored; parity is enforced by `i18n:check`. Do not commit its output blindly. |
| `npm run i18n:check` | The catalog parity gate (runs in CI): missing/extra keys vs en per language and namespace, empty values, untranslated values (identical to en) with allowlist, plural-category parity via `Intl.PluralRules`, language-only namespace files, and `i18n.d.ts` namespace coverage. |

## Backend gettext workflow

- `LocaleMiddleware` (in `config/settings.py`, directly after `SessionMiddleware`)
  picks the translation from `Accept-Language`. A missing header, an unknown language,
  or a missing translation falls back to the English source string (there is no
  `LANGUAGES` setting; `LANGUAGE_CODE` is `en-us`).
- Exception classes declare `default_message = gettext_lazy('...')` (import-time);
  raise sites and Pydantic validators call `gettext` `_()` at runtime so the active
  request language applies. Interpolated messages are named-placeholder templates
  rendered with `%` at runtime, for example `_('Currency %(code)s not found') %
  {'code': code}` - never f-strings. An f-string bakes the English in before gettext
  ever sees the string, which makes the message untranslatable; this is a correctness
  rule, not a style preference.
- Collect msgids (from `backend/`): `uv run python manage.py makemessages -l uk -l pl
  --no-obsolete`. This needs the gettext binaries on the host; when they are absent,
  run the same command through `./dev.sh manage makemessages -l uk -l pl
  --no-obsolete` - it executes in the api image, which installs gettext. Translate
  `backend/locale/<lang>/LC_MESSAGES/django.po`. Keep msgid bytes identical to the
  source strings, including any typographic characters they contain. The existing
  uk/pl `msgstr` blocks were generated with AI tools and follow the same
  follow-up-edit expectation.
- Plural-header warning: gettext 0.26 and newer auto-guesses `nplurals=4` formulas
  for uk/pl and writes only `msgstr[0..1]`. After regenerating, restore the canonical
  3-form `Plural-Forms` header and the `msgstr[0..2]` slots, then verify the file with
  `msgfmt --check`.
- Compile: `uv run python manage.py compilemessages`, or restart the api/worker
  containers - `backend/docker-entrypoint.sh` and `backend/celery-entrypoint.sh` both
  run compilemessages on boot (the Dockerfile installs gettext for `msgfmt`).
- `.mo` files are build artifacts: gitignored (`backend/locale/**/*.mo`), never
  committed.

The backend's overall layering is in [docs/architecture.md](architecture.md).

## Guards

- CI runs `npm run i18n:check` on every frontend job, between install and lint.
- `npm run build` type-checks `t()` calls against `src/i18n/i18n.d.ts`, whose resource
  types derive from the en catalogs - a typo'd key or namespace is a build error.
- ESLint `i18next/no-literal-string` (warn) flags new JSX text literals and new
  `placeholder`/`title`/`alt`/`aria-label` literals in `frontend/`; the warning
  baseline is documented in `frontend/eslint.config.js` and only goes down.
