# Feature & Complexity Audit — July 2026 (Task 0.1)

Verdict per feature/app: **keep** / **simplify** / **make-optional** / **remove**, with rationale.
This document feeds the domain redesign design (`docs/design/domain-redesign.md`, Task 1.1).
"Absorbed by" names the plan task (`.ipm/IMPLEMENTATION_PLAN.md`) that implements the verdict.

The lens throughout: Denarly grew around one power-user workflow (heavy multi-currency, frequent
exchanges, manual period management). For open source it must serve the **simple user** —
single currency, one budget, no exchanges — as the default experience, with the power features
becoming opt-in.

---

## 1. The simple-user walkthrough (current state)

What a brand-new single-currency user must do today to record their first expense:

1. **Register** → a workspace is auto-created with **four currencies** (PLN-biased default) and a
   "General" budget account, plus demo records (`create_demo=True` on every registration).
2. **Understand "budget account"** — the General account exists, but its name, `default_currency`,
   color/icon/order settings all suggest a concept to manage.
3. **Create a budget period** — nothing can be recorded without one. The create-period modal asks
   for name, start date, end date, and an optional `weeks` count. (Demo data may have created one,
   mixed with sample records the user must eventually clean up.)
4. **Create a category** — categories are **scoped to the period**, so this repeats every month
   (or the user must learn the "copy period" feature).
5. **Create the transaction** — date, description, category, amount, **currency picker with four
   choices**, type.

**Concept count before first transaction: 6** (workspace, budget account, period, category,
currency, transaction) — of which the user must actively manage 4 (period, category, currency
choice, transaction).

**Target after redesign: 2** (workspace exists silently; user picks a category and types an
amount). Register → record first expense in under a minute.

Recurring friction (not just first-run): every new month requires creating/copying a period and
its categories; balances have a user-facing "recalculate" button (cache invalidation exposed as a
feature); the sidebar has ~11 top-level destinations.

## 2. Verdicts — backend apps

### `workspaces` — Workspace, WorkspaceMember, roles — **keep**
The multi-tenancy boundary, membership, and 4-role hierarchy (owner/admin/member/viewer) work and
are invisible to the simple user (they just have a workspace). No structural change; only naming
polish in UI. *Absorbed by: 1.1 (naming only).*

### `workspaces.Currency` (per-workspace currency rows) — **simplify**
Users define currencies by hand (name + symbol) and every new workspace gets four pre-created,
PLN-first — the developer's own workflow baked in as default. Replace with a global ISO 4217
table + per-workspace enablement; the workspace creation flow picks **one** currency (no PLN
bias). Keep an escape hatch for custom (non-ISO) entries — crypto, loyalty points — flagged as
custom. With one enabled currency, no currency picker appears anywhere. *Absorbed by: 1.5.*
**Confirms plan assumption 5** (revised: add the custom-currency escape hatch).

### `exchange_shortcuts` — **remove**
An entire Django app whose model stores a from/to currency pair — a saved-favorites feature for
someone exchanging PLN↔USD weekly. When exchanges become transfers between accounts (below), the
transfer form's account pickers make the shortcut meaningless: the account pair *is* the shortcut.
No migration needed beyond dropping the table (nothing references it). *Absorbed by: 1.3.*
**Confirms plan assumption 4.**

### `currency_exchanges` — **remove (replaced by transfers)**
Exchange records exist because money implicitly lives "in currencies" inside a period. Once money
lives in accounts, exchanging currency *is* a transfer from a PLN account to a USD account with
two amounts. Historical exchanges migrate to transfers losslessly (both amounts and the rate are
preserved). The `exchanges_in`/`exchanges_out` columns in period balances disappear with them.
Single-currency users never see any of it. *Absorbed by: 1.3.* **Confirms plan assumption 4.**

### `period_balances` — **remove (replaced by account balances)**
This app is the strongest overengineering signal:
- It is a **stored cache** of derivable numbers, with user-facing `POST /recalculate` and
  `/recalculate-all` endpoints — the user is asked to fix the app's stale caches.
- Opening balances carry forward from the previous period's closing but can be manually
  overridden, silently forking "calculated" from "actual" (the code must special-case
  "preserve manually set opening balances").
- One row per period × currency, entangled with exchange in/out flows.

Replace with: per-**account** balances (opening anchor + transactions + transfers, computed with
indexed queries), and per-budget-per-period summaries computed on demand. The legitimate need
behind manual opening-balance edits — "make the app match my real bank balance" — becomes an
explicit **balance adjustment** transaction on an account, which keeps an audit trail instead of
silently rewriting history. *Absorbed by: 1.2, 1.3.* If computed balances ever become slow, add
snapshotting back as an internal optimization — never as a user-facing feature.

### `budget_accounts` — **simplify + rename**
The concept survives but changes meaning: it stops pretending to hold money and becomes a
**Budget** (a spending plan over shared money). Field-level verdicts: `name`, `description`,
`color`, `icon` — keep (cheap, useful in nav); `display_order`, `is_active` — keep;
`default_currency` — becomes the budget's display currency (drop if single-currency workspace).
The name "budget account" itself is the worst offender in the naming overlap ("account" ×2) and
is retired. *Absorbed by: 1.4.*

### `budget_periods` — **make-optional (background objects)**
Manual period management is the biggest recurring friction. Periods become auto-created monthly
per budget; the create/copy/edit modals and the top-level "Budget Periods" page disappear from the
default path (custom period ranges remain an advanced budget setting). The `weeks` field —
manually entered, informational — is **removed**; anything week-based can be derived from the date
range. The period `copy` service disappears once categories persist (below); only planned amounts
copy forward. *Absorbed by: 1.4.* **Confirms plan assumption 3.**

### `categories` — **simplify (re-parent from period to budget)** ⚠ biggest hidden complexity
Categories are children of a **budget period**, so they are destroyed and recreated every month.
Consequences: category history is fragmented (the "Food" of January is a different row than the
"Food" of February — cross-period reporting by category is impossible without name-matching), the
copy-period feature exists mostly to work around this, and users must re-create categories if they
forget to copy. Categories become **persistent, budget-scoped**; per-period planned amounts live
in the allocation model (below). This single change eliminates most copy-forward machinery.
*Absorbed by: 1.4.* **Revises plan assumption 3** (copy-forward shrinks to amounts only).

### `budgets` (per-category allocation) — **keep + rename → CategoryBudget**
The period × category × currency allocation amount is the core of budgeting — keep. Renamed
because "Budget" is taken by the renamed BudgetAccount. In single-currency workspaces the currency
dimension collapses silently. *Absorbed by: 1.4.*

### `transactions` — **keep (core)**
The heart of the app; the model is clean. Redesign adds an `account` FK (where the money moved)
and derives period membership from `date` instead of a stored `budget_period` FK — which also
eliminates the SET_NULL-orphan class of deletion bugs documented in the GDPR rules. Gains a
sibling: **Transfer** (between accounts; first-class, not income/expense). *Absorbed by: 1.3.*

### `planned_transactions` — **keep**
Genuinely useful (scheduled bills), Celery execution works, status flow is reasonable. Gets the
same treatment as transactions (account FK, derived period). Not part of the simple user's first
hour, and it doesn't get in the way. *Absorbed by: 1.3 (model alignment only).*

### `reports` — **keep**
Only two endpoints (budget-summary, current-balances) — already minimal. Data sources are rebuilt
on the new model (current-balances becomes per-account). *Absorbed by: 1.4/1.6.*

### `users`, `core` (auth, 2FA, GDPR, legal, consent) — **keep**
Security and GDPR machinery is an open-source strength, not overengineering. One change: **demo
data on every registration** (`create_workspace(..., create_demo=True)`) becomes **opt-in** — a
"start with sample data" choice at registration/first-run. New users should not begin by deleting
records they didn't create. *Absorbed by: 1.7.*

## 3. Verdicts — frontend surface

Current sidebar/top-level routes: Dashboard, Budgets, Period detail, Transactions, Exchanges,
Balances, Planned, Categories, Budget Periods, Budget Accounts, Members, Profile — **11 nav
destinations**, several of which are pure entity-management screens for concepts that are being
demoted or removed.

| Page | Verdict | Rationale |
|---|---|---|
| Dashboard | keep | Landing view; rebuilt on account balances. |
| Transactions | keep | Core. Gains account column/filter (hidden when one account). |
| Planned | keep | Core-adjacent. |
| Budgets (`BudgetsPage`) | keep (rework) | Becomes the budget overview (plan vs actual per category, period switcher). |
| Budget Accounts page | remove | Merges into the new Budgets section (rename + redesign). |
| Budget Periods page | remove | Periods are background objects; custom ranges move to budget settings. |
| Categories page | simplify | Category management moves inside a budget's view; no top-level page. |
| Exchanges page | remove | Replaced by transfers (from Accounts and the global add action). |
| Balances page | remove (replaced) | Replaced by the new **Accounts** section (per-account balances). |
| Period detail (`/period/:id`) | simplify | Folds into the budget view with a period switcher — not a navigation level. |
| Members, Profile, legal/auth pages | keep | Fine as-is. |

Target sidebar: **Dashboard, Accounts, Budgets, Transactions, Planned, Members, Settings** —
7 destinations, none of which is a management page for a background concept. *Absorbed by: 1.6.*

Period-related modals (Create/Edit/Copy/Selector — 4 modals) shrink to at most one advanced
"custom period" form. The `weeks` input disappears from all of them.

## 5. Plan assumptions — confirmations

- Assumption 1 (budgets are plans, not envelopes): **confirmed** for v1 — see design doc §2.
- Assumption 2 (target model & renames): **confirmed**, with the addition of persistent
  budget-scoped categories.
- Assumption 3 (background periods): **confirmed**; copy-forward shrinks to planned amounts only.
- Assumption 4 (exchange → transfer, drop shortcuts): **confirmed**.
- Assumption 5 (global ISO currencies): **confirmed**, plus a custom-currency escape hatch, and
  new workspaces get **one** currency, not four.
- Assumption 6 (migration default accounts): **confirmed** — see design doc §6.
- New verdict not in the assumptions: registration demo data becomes opt-in.
