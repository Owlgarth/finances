# Frontend Conventions (TypeScript/React)

## Design System Tokens

The frontend uses an "Architectural Ledger" design system via CSS custom properties. All colors reference `var(--color-*)` variables — never hardcoded hex values in component code.

- **Color tokens:** `primary`, `primary-hover`, `background`, `surface`, `surface-hover`, `surface-muted`, `border`, `border-focus`, `text`, `text-muted`, `positive`, `positive-bg`, `negative`, `negative-bg`, `warning`, `warning-bg`, `planned`/`actual`/`remaining` (budget ledger columns - muted pastels), `scrim` (overlay backdrop - `bg-scrim` in `Modal`/`BottomSheet` overlays) - 20 tokens, all mirrored in the `@theme inline` block
- **Border radii:** `rounded-sm` (4px) — containers, buttons; `rounded-none` (0px) — inputs, table cells
- **Fonts:** `font-sans` — Geist (body/UI); `font-mono` — JetBrains Mono (code, numbers)
- **Muted metadata stamps:** page furniture in a metadata register (a version line, a period range under a card) uses the tokens.md Metadata row combo `font-mono text-[11px]` + `text-text-muted` - the row's `font-normal` is the default weight, omitted as in the `PeriodCard` exemplar. Not `text-sm` Geist + muted: that is the interactive caption/empty-state register, and reaching for it drifts metadata styling off the design system.
- **Icons:** `lucide-react` only. No Material Symbols or other icon fonts.
- **Focus ring:** `:focus-visible` uses `var(--color-border-focus)`. No shadow variables — avoid `box-shadow` utilities for elevation.
- **Full-bleed focus rings draw inside:** a positive `focus-visible:outline-offset-2` draws the outline OUTSIDE the element edge, so on a `w-full h-full` button inside an `overflow-hidden` wrapper (media tiles) it clips invisible on three of four sides - use `focus-visible:-outline-offset-2` (inset ring) there, and the standard positive offset on contained buttons. Exemplar: the attachment tiles in `transactions/TransactionAttachments.tsx`.
- **Programmatic-focus highlights append a STATIC outline ring, never a `focus-visible:` gate.** `:focus-visible` keys on input modality heuristics and a programmatic `.focus()` does not reliably trigger it, so a one-shot mount effect that focuses a field cannot light a `focus-visible:` ring. The effect that steals focus also renders the highlight as presentation state - a static `outline-2 outline-offset-2 outline-border-focus` class (zero setState; cleared on first interaction in the blur/click/keydown handlers) - never a pulse animation. Exemplar: the scan-seed focus highlight on the amount row in `pages/NewTransactionPage.tsx`.
- **Border widths:** Tailwind preflight resets `border-width: 0`, so a color utility alone (`border-primary`) renders **no** border. Always keep the bare `border` width utility and swap only the color half — `border border-primary` (open/selected) vs `border border-border` (default).
- **Shared control classes:** button/control variants live in `common/formStyles.ts` and follow the four-part shape: base colors + padding + `controlHeightClass` + `focus-visible:outline-*` + `disabled:opacity-50 disabled:cursor-not-allowed`. Solid semantic fills have no `-hover` token — hover is an opacity step (`hover:bg-negative/90`), which inverts acceptably in both themes.
- **Stacking (z-index) tokens:** use the semantic scale, registered as ten `@utility z-*` rules in `src/index.css` (v4 has no `--z-index-*` theme namespace) - `z-dropdown` (100) < `z-sticky` (200) < `z-popover` (250) < `z-sidebar`/`z-bottom-nav` (300) < `z-topbar` (400) < `z-modal-backdrop` (500) < `z-modal` (510) < `z-toast` (600) < `z-tooltip` (700) - never raw `z-10`/`z-50` utilities for overlays or persistent chrome. An overlay is two layers: backdrop at `z-modal-backdrop`, dismiss wrapper + panel at `z-modal` (`Modal.tsx`); plain `z-10` is only for local stacking *inside* a surface (a sticky drag handle, the lightbox close X above a tall sibling image, sticky table columns). `z-popover` (250) is the tier for a transient light-dismiss popover that must paint over sticky in-flow content - a toolbar popover opening directly over a sticky `thead` at `z-sticky` is pointer-dead in the band the thead covers (the TH wins the paint, the popover's outside-mousedown handler closes it, the action never runs), while a dropdown inside scrolling content stays at `z-dropdown` by original design.
- **Raising a shared panel class's z-tier is an APPEND at the composition site, never an edit to the shared constant.** Appending the higher-tier utility over a verbatim shared class string (`${listboxPanelClass} z-popover right-0 py-1`) wins because Tailwind v4 emits utilities alphabetically - `.z-popover` lands after `.z-dropdown` in the sheet, and at equal specificity the later rule wins; className order inside the string is irrelevant. This is the deliberately exploited inverse of the one-width-class trap below (same mechanism, opposite outcome: there the shared `w-full` out-cascades the appended caller `w-NN`, here the append is chosen precisely because it wins). Verify the win with a computed-style probe on an element carrying both classes - never the className string - and prove the utility is emitted at all via the compiled-sheet grep gate (`.z-popover{z-index:250}` present in `dist/assets/*.css`). For the pointer-dead bug class, `document.elementFromPoint()` at each member's center is the browser's own top-most-paint answer, stronger evidence than screenshots. A new tier lands in the existing scale block in scale order with a docblock stating WHY (the domain reason, no PR references). Exemplar: the Add-filter/Save-view menu panels in `components/filters/FilterChipsBar.tsx` appending `z-popover` over the verbatim `listboxPanelClass` (`common/listboxParts.tsx` untouched).
- **Beating a third-party widget's own INLINE styles takes the semantic tier's VALUE inline, or the v4 important suffix when a media query must win.** A library that sets its own inline `z-index` (react-hot-toast's Toaster at 9999) cannot be out-cascaded by a class - pass the tier's VALUE inline: `containerStyle={{ zIndex: 600 }}` (`z-toast`). The same fight over a position offset goes to the important suffix when the winner must be media-gated: `containerClassName="max-sm:bottom-[calc(4.5rem+env(safe-area-inset-bottom))]!"` - an important-suffixed `max-sm:` declaration beats the library's inline 16px (mirroring MainLayout's phone bottom clearance). Exemplar: the Toaster in `main.tsx`.
- **Animation utilities:** keyframes + utilities live at `index.css` root level (`fadeIn` / `.animate-fade-in`) and are covered by the GLOBAL `prefers-reduced-motion` kill switch at the end of that file - a new root-level animation utility needs no per-class reduced-motion handling, and a block-local reduced-motion list there is wrong (the global switch already fires).
- **Utilities that must compose with variants are `@utility` rules in `src/index.css`, never `@layer utilities` classes.** A plain layer class (`.touch-hit`) is variant-inert - a `max-sm:`/`pointer-coarse:` prefixed usage of it emits nothing in the compiled sheet (two live call sites shipped such dead classes unnoticed; v4 keeps exactly these semantics). Register variant-composing utilities with `@utility` (pseudo-element rules use the nested `&::-webkit-scrollbar` form); custom variants themselves are `@custom-variant` rules (`dark`, `pointer-coarse`) in the same scaffolding. `@layer utilities` stays for variant-free utilities only (`.touch-hit`, `.pt-safe`). Exemplar: `@utility scrollbar-none`.

## Tailwind CSS 4 (CSS-First Theme)

The v3 JS-config era is gone - no `tailwind.config.js`, no `postcss.config.js`, no autoprefixer. The theme contract is the CSS-first scaffolding block at the top of `src/index.css` (`@import "tailwindcss" source(none)` + `@source` scanning + `@custom-variant dark`/`pointer-coarse` + `@theme inline` color tokens + `@theme` fonts/radii/line-heights + `@utility` rules + the `@layer base` button-cursor restore, built through the `@tailwindcss/vite` plugin). `design/tokens.md` §3 mirrors that block byte-identically, and a scaffolding change and its fence re-extraction are ONE commit: the empty post-extraction diff is a native done criterion for every scaffolding edit, and any non-empty diff against the fence is the drift alarm firing (a reviewer blocking on the split is the alarm working as designed; never a hand-paste - mechanics in `docs-accuracy`).

- **`@theme inline` is load-bearing for the color tokens:** inline mode makes utilities emit `var(--color-primary)` etc. so they follow the runtime `:root`/`.dark` token blocks lower in the file; a plain `@theme` block would duplicate the definitions and fight dark mode. Key name == var name, all 20 tokens, none added or renamed unilaterally.
- **v4 emits utilities on demand from `@source` scanning and emits NOTHING for unknown class names.** A v3-spelled utility (`flex-shrink-0`, `outline-none`, prefix-form `!absolute`) or a misspelled one compiles away with no diagnostic, so build, lint, and tsc are all structurally blind to it. A rename or new registration is proven ONLY by paired grep gates: source-tree remnant count = 0 AND compiled-sheet presence in `dist/assets/*.css` > 0 (e.g. `.shrink-0{`, `.outline-hidden{`, `.absolute\!`). A green build proves nothing by itself.
- **Compiled-sheet grep mechanics:** the minified sheet is ONE physical line - count occurrences with `grep -o | wc -l`, never `grep -c` (which reports 1 for any number of matches, or 0 and a false pass). Prefixed variants compile to ESCAPED selectors (`.focus\:outline-hidden:focus`), so a leading-dot pattern matches 0 - grep the bare selector fragment or escape the colon yourself. Arbitrary-value brackets stay escaped in the compiled selector as well (a prefixed min-width utility emits `.pointer-coarse\:min-w-\[44px\]` with both backslashes), so the regex form `grep -o 'min-w-\[44px\]'` - whose `\[` matches a bare bracket - can never match the output; gate arbitrary-value utilities with the fixed-string form `grep -oF 'min-w-\[44px\]' | wc -l`, never a bare regex. A utility and its alpha-modifier siblings GROUP into one rule (`.x,.x\/90{...}`), so an exact-string grep anchored on the full selector or the declaration block false-negates.
- **Touch-action utilities compile to var indirection, and the wrong spelling emits nothing.** `touch-action-none` is not a v4 utility - it compiles to NOTHING; the spelling is `touch-none` (`.touch-none{touch-action:none}`). `touch-pan-y` IS real but emits `--tw-pan-y:pan-y; touch-action:var(--tw-pan-x,) var(--tw-pan-y,) var(--tw-pinch-zoom,)` - a compiled-sheet gate for it greps `touch-pan-y` / `--tw-pan-y:pan-y`, never the literal `touch-action:pan-y` declaration (the runtime computed value IS `pan-y`; verify via `getComputedStyle`, never the declaration text).
- **Class-name censuses anchor BOTH delimiters and span `*.ts` too:** the pattern shape is `(?<![a-zA-Z0-9_-])((([a-zA-Z-]+:)*)NAME)(?![a-zA-Z0-9_-])` - a right-anchor-only pattern matches trailing substrings inside prose and identifiers (`ordering`, `recurring`, "the focus ring" - one broken planning census counted 309 false lines). `common/formStyles.ts` and other `.ts` modules carry shared class strings a `.tsx`-only census misses. Re-run pinned censuses immediately before editing (state drifts between planning and execution) and read every hit before treating a count as an edit workload.
- **v4 pairs named text sizes with unitless line-height RATIOS that inherit as ratios:** the native pairing (sm: `calc(1.25 / .875)`) recomputes against every arbitrary-size child (`text-[10px]`), shrinking its line-height where v3's absolute pairing handed the child the used px. The `@theme` block pins the v3 absolute values via `--text-*--line-height` overrides (xs/sm/base/lg/xl). The list is census-governed, not exhaustive - introducing a new named size (`text-2xl`) without adding its override silently reverts that subtree to the ratio; the in-block comment "add a size here when a new named size enters the tree" is load-bearing because nothing lint-enforces it. Line-height regressions traced here are fixed in the theme block, never patched with per-site leading utilities.
- **`space-y-*`/`space-x-*` compile inside `:where()` - zero specificity:** a direct child's own `mb-*`/`mt-*` beats the parent's space-y margin, where v3's higher-specificity rule plus block-layout margin collapse made the same child margin inert - redundant in v3, harmful in v4. Never add margin utilities to children of a `space-y-*` container: the container's spacing silently degrades (the login forms carried three such wrappers). Parity restoration DELETES the now-load-bearing child margins; it never re-adds parent spacing.
- **Hiding stays on the CLASS, never the HTML attribute:** v4 lets the `hidden` HTML attribute beat display utilities, so an attribute-hidden element cannot be re-shown by a later `flex`/`block` utility switch - the `className="hidden"` pattern (state-preserving tab switches, conditional `'' : 'hidden'`) is the sanctioned form.

## Self-Hosted Fonts

Geist and JetBrains Mono are self-hosted - the woff2 files live in `public/fonts/`, declared by the `@font-face` block at the top of `src/index.css` (one rule per family, weight, and subset) and served same-origin from `/fonts/` (nginx caches `.woff2` `expires 1y` + `Cache-Control: public, immutable` - `frontend/nginx.conf`). Privacy is the requirement - the app must be the only origin a visitor's browser talks to for fonts - so a font-CDN `<link>` or preconnect in `index.html` (the loading mechanism this replaced) must never come back. Standing gate: `rg -i 'google.?fonts|googleapis|gstatic'` over `frontend/` sources stays at zero matches; the only surviving repo hits are historical `design/mockup.html` and `design/README.md` migration-table rows.

- **Filenames embed the fetch date as the cache version** (`geist-2026-09-12-latin.woff2`): with immutable 1y caching the URL is the only cache-buster, so a re-fetch swaps the dated filenames and every `url()` target together - never one without the other.
- **The provenance header atop `index.css` is the operational record for a re-fetch**: css2 query string, upstream revisions, pinned fetch UA, fetch date, license paths. The css2 response is UA-dependent (variable woff2 requires a modern Chrome UA), so reuse the recorded UA rather than the ambient one. The header is grep-safe by design - it records everything EXCEPT the CDN domain and never uses "Google Fonts" phrasing; a comment naming the old domain re-trips the CDN gate forever.
- **Assemble a re-fetched `@font-face` section by concatenation, never hand-pasting through an editor** (new header + url()-rewritten response + the untouched remainder of the old file): a re-typed `unicode-range` silently drops a subset - Ukrainian cyrillic, Polish latin-ext - with no error anywhere, the affected text just falls back to the next font in the stack.
- **OFL 1.1 license texts are fetched verbatim from the upstream font repos** (`public/fonts/OFL-*.txt`), never hand-authored - Geist's copyright line is "The Geist Project Authors", not "Vercel".

## Third-Party Component Theming

When theming a third-party component (e.g. `react-day-picker`) to match the design system, scope CSS overrides to a wrapper class on the variant's container only (e.g. `.rdp-inline`) so other usages keep their defaults. Never write global overrides. The container carries the scoping class in the component JSX.

Override the library's own CSS variables (`--rdp-*` in react-day-picker) to map onto the app's `var(--color-*)` tokens - the widget becomes dark-mode aware with zero `dark:` variants since the tokens invert under `.dark`. Never hardcode colors. The declaration target is version-load-bearing: react-day-picker v10's stock stylesheet declares every `--rdp-*` var ON `.rdp-root` itself, and a declaration on the element beats a value inherited from a wrapper class - so a wrapper-scoped `.my-variant { --rdp-*: ... }` block is provably inert (stock geometry and colors render; probed live: stock 42px day buttons, stock range-middle tint, no error anywhere). Overrides MUST live on a rule that MATCHES `.rdp-root`, i.e. a descendant selector like `.rdp-range-editor .rdp-root` (specificity 0,2,0 beats stock's 0,1,0 on the same element):

```css
/* Scoped to the date-range editor's calendar - other rdp usages keep their defaults */
.rdp-range-editor .rdp-root {
  --rdp-accent-color: var(--color-primary);
  --rdp-accent-background-color: var(--color-surface-hover);
  --rdp-day_button-width: 2rem;
  --rdp-day_button-border-radius: 0.25rem; /* rounded-sm - matches app buttons */
}

/* Selected day: background as text color so it inverts correctly in both themes.
   Descendant rules targeting rdp's own elements (not the root) stay valid in any version. */
.rdp-inline .rdp-selected .rdp-day_button {
  background-color: var(--color-primary);
  color: var(--color-background);
}
```

The working exemplar is the `.rdp-range-editor` block in `src/index.css` (layered on `.rdp-inline`; the plain wrapper-scoped `--rdp-*` blocks elsewhere in that file are known-inert v9 leftovers). Behavior facts pinned from the v10 probe: `resetOnSelect` has NO code default - pass it explicitly, or a third click EXTENDS the completed range instead of restarting it - and the `range_start`/`range_end` highlight classes require BOTH range bounds (a partial range shows only the middle tint).

For grid/table-based widgets (calendar grids, data tables), set `table-layout: fixed` + `width: 100%` on the grid so columns fill the container evenly.

## Theme Signal Readers Move in One Commit

The theme decision (`owlgarth_theme` in localStorage) is read in three places: `index.html`'s inline FOUC script (the earliest reader - it applies the `.dark` class before first paint), `ThemeContext` (seeds its state from the `<html>` class, owns the toggle and writes the key), and the `theme-color` metas (chrome UI color, synced on toggle). They are three views of one decision: any change to the storage key, the default, or the OS coupling must move ALL readers in the same commit. Leaving one behind diverges the views - a theme flash on reload when the script and the context disagree, or chrome color tracking the OS preference while the app stays light via a leftover media-gated meta. Hit by both the rebrand's storage-key rename and the light-default decoupling: census every reader of the theme signal before editing it.

## Responsive Breakpoints & Adaptive Components

Canonical device tiers (see `design/responsive.md`): **mobile <640px, tablet 640–1023px,
desktop ≥1024px**, snapped to Tailwind's `sm`/`lg`. In JS use `useBreakpoint()` from
`hooks/useBreakpoint.ts` — never write ad-hoc `useMediaQuery('(max-width: …)')` calls. In CSS,
mobile = `max-sm:`, desktop = `lg:`. For grid layouts `md:` remains fine as a middle step:

```tsx
<div className="grid grid-cols-1 md:grid-cols-3">
```

Input-device behavior (hover reveals, hit areas) keys on `useIsTouch()` (`pointer: coarse`),
not width. Never gate an action behind hover on touch: list rows open a `common/ActionSheet`
on tap instead, and the hover-revealed buttons are **not rendered** when `isTouch` (invisible
`opacity-0` buttons still intercept taps).

**Adaptive component pattern** (`design/patterns.md` §13): when a component needs a different
mobile presentation, branch *inside* the component on `useBreakpoint()` and keep one exported
API — zero call-site changes. State lives above the variants so a resize across the breakpoint
mid-interaction loses nothing. `Modal`, `Select`, and `DatePicker` already do this. The mobile-sheet half mounts whenever mobile - it is gated only through the sheet's own open prop, never unmounted on the transient state - so the sheet's delayed-unmount exit animation can still play after a save or cancel dismisses it (Select's mobile panel, EditableField's one-field sheet).

**Dual surfaces of one toggle are both CSS-gated, never `useBreakpoint()`-conditionally mounted.** When the same control exists as a phone affordance and a desktop control (an `sm:hidden` icon button beside a `hidden sm:block` segmented row), both stay mounted in every tree: with the toggled state in the URL and the counts in the shared query cache, nothing below the crossing holds state to lose. The same rule holds at LAYOUT scale, and `MainLayout` is the exemplar of the fix: width chrome is CSS-gated on one stable tree (`hidden sm:block` Sidebar wrapper, `sm:hidden` on BottomNav's nav, both mounted at ALL widths) instead of a JS `isMobile ? ... : ...` return branch - a JS width branch unmounts everything below it at every 640px crossing, silently destroying unsaved component state (an edit-in-place draft mid-rotation), where CSS gating changes only presentation, never identity. Its `sm:` overrides of axis-based padding bases stay axis-matched (`sm:px-6 sm:pt-6 sm:pb-6` over the mobile padding bases) - never a box padding shorthand over axis bases - so the composition never depends on shorthand-vs-longhand sheet order even where a shorthand would win today. Exemplars: Planned's Recurring-rules toggle pair; `MainLayout`/`BottomNav`.

**Behavior forks (modal vs navigate) live INSIDE the click handler; visibility forks (`max-sm:hidden`) stay on the class.** A create affordance that must open a modal at 1024+ but route to a create page below branches in the onClick (`isDesktop ? openModal : navigate('/new?...')`) so the button stays mounted on every tier - a render-tier branch would unmount and remount the header control across the 1024px crossing, churning the header for nothing. The navigate arm emits the destination's carry query from the handler. Exemplars: the header create buttons in `Transactions.tsx`/`TransfersPage.tsx`/`AccountsPage.tsx`; the BottomNav FAB is the pure-navigate twin (its carry derivation reuses the ActivityTabs pattern).

**A master-detail pair drives the detail from the ROUTE URL; the route swap remounts the page.** First open PUSHes the record URL (Back returns to the bare list), every later selection change REPLACES, and close replaces back to the list - Back never walks a click trail of selections - and the tier fork (side panel at 1024+ vs full-page record below) lives INSIDE the open handler per the rule above, so the list stays mounted on every tier. The click-time filter string rides in router `state` (`navigate(path, { state: { search } })`, read per render with a typeof guard - RR7 types state as `any`) when the record's own URL must stay clean and shareable but its header Back target must return to the exact filtered page: because the row tap was a PUSH, browser Back replays the full list URL and the remounting page re-reads its params with zero restore code. Navigating between the list and record URLs swaps the matched route ELEMENT - React Router remounts the whole page tree (proven by node identity), dropping focus to `<body>` - so focus/scroll continuity across the open is re-armed on the NEXT mount: a mount-only effect restores focus to the selected row (keyboard users would otherwise Tab back into the table after every open), and scroll memory for a non-window scroll container (`<main>`, not the document) uses a MODULE-LEVEL Map keyed by pathname (`hooks/useMainScrollRestoration.ts`) - a ref or state dies with the route component's remount, and the browser clamps the container's scrollTop against the shorter record page, so Back without the save lands at the clamped offset. An in-flow create/copy panel sharing the detail slot takes its open state from a URL param (`?new=transaction`, exact-value match so garbage reads as unset) - shareable, reload-safe, and immune to those remounts - with a precedence rule enforced at every write site (each create-open write drops the selection path; each record-open write strips `new`/`copy`), making the create panel and a selected record structurally unable to co-render with no reconciliation state. Exemplars: `Transactions.tsx`, `TransactionRecordPage.tsx`.

**Adding a tier that refines an existing one is an OVERLAP, not a sibling.** `isWide` (>=1280px, snapped to Tailwind `xl`) overlaps `isDesktop` because 1280+ is still desktop - only a layout default changes - where a sibling tier would force every existing `isDesktop` consumer to re-derive membership. Recipe: add the query const (`WIDE_QUERY`), the interface field, and the hook line; leave every structural consumer alone; snap the boundary to a Tailwind screen so the JS hook and the CSS prefixes can never disagree at a boundary pixel. A tier-dependent DEFAULT that a stored preference overrides needs a preference-null latch: read `prefIsNull` once via lazy initializer (crossing semantics mirror fresh-mount semantics ONLY while no stored preference exists), keep a self-disproving prev-tier render-adjust (`prevIsWide` seeded equal to `isWide` so mount fires nothing; `setPrevIsWide(isWide)` makes the condition false on the immediate re-render - loop-safe by construction), and disarm the latch in the SAME event handler and batched update that writes the localStorage key, never in an effect - after the first manual toggle the stored preference wins in both directions and resize stops interfering. The unguarded `localStorage` read in the initializer follows the app's client-only contract (`useMediaQuery` already reads `window.matchMedia` in one) - do not add `typeof window` branches to sibling initializers. Exemplar: MainLayout's isWide rail default (sidebar mounts collapsed through 1024-1279 until the user toggles).

Mobile rules: text-entry controls are forced to 16px on mobile globally in `index.css` (iOS
zoom prevention — don't undo per-input); amount inputs get `inputMode="decimal"`; interactive
elements meet 44px on touch — shared button/control classes get the floor via
`controlHeightClass` in `common/formStyles.ts` (`min-h-8 pointer-coarse:min-h-[44px]`, keyed
on the custom `pointer-coarse` variant so tablets above `sm` keep full touch targets); only
`SegmentedControl` uses `max-sm:min-h-[44px]` (viewport-keyed); small icon buttons use the
`.touch-hit` utility, but not on adjacent buttons whose expanded hit areas would overlap).
Ad-hoc interactive rows outside the shared classes (listbox option rows, filter chips)
interpolate the full `${controlHeightClass}` constant from `formStyles` instead of
hand-writing a `pointer-coarse:min-h-[44px]`-only half - the `min-h-8` fine-pointer base is
the other half of the contract, and the constant stays the single source of truth. A composed floor that must sit ABOVE the coarse floor on phones needs the v4 postfix important suffix: `min-h-8 pointer-coarse:min-h-[44px] max-sm:min-h-12!` - `pointer-coarse:` rules compile AFTER `max-sm:` rules in the sheet (both single-class media-gated rules at identical specificity; verified via rule offsets in `dist/assets/*.css`), so an un-suffixed phone floor silently loses to the coarse floor on every coarse-pointer phone (pinned outcome matrix: 48px phones, 44px coarse tablets, 32px fine pointers). Icon-only affordances (a back button, a trailing arrow cell) additionally need the coarse WIDTH floor - `pointer-coarse:min-w-[44px]` beside the interpolated height constant - because `controlHeightClass` sets no width and the height half alone leaves a narrow target. Exemplars: PageHeader's back button, LinkedRow's arrow cell.

`.touch-hit` sets `position: relative` in the same `utilities` cascade layer Tailwind emits
`.absolute`/`.fixed` into - equal specificity, later source order, so `.touch-hit` wins: an
element carrying both classes silently computes `position: relative`. When an element needs
true absolute positioning plus the enlarged hit area, use the v4 important-suffix form
`absolute!` - the attachment-tile delete button in `transactions/TransactionAttachments.tsx`
(`absolute! top-1 right-1 …
touch-hit`, the trash button on each receipt tile) is the canonical example; without the
`!` it computes `position: relative`, drops into flow below the image, and the tile's
`overflow-hidden` clips it out of sight (the v3 prefix spelling `!absolute` is NOT a class
under v4 and emits nothing - see Tailwind CSS 4 below). Verify cascade fixes against the
compiled CSS, not the source className. A sneakier instance of the same class: v4 emits
utilities in ALPHABETICAL order, which puts the
full-width utility AFTER every numeric width utility (digits sort before letters - same
winner as v3's width-scale order), so a
shared base class's `w-full` silently out-cascades any appended caller `w-NN` (a `Select`
trigger's base plus a caller's `w-48`) - equal specificity, later sheet order wins, and the
caller's pinned width never applies: no error, no lint, the trigger stays content-sized.
The resolution: a shared trigger/base class carries NO width utility - width is a
per-call-site decision, every caller passes exactly one width class (`className="w-full"`
for form grids, an explicit pin like `w-48 shrink-0`), and the one component reusing
the base without a caller supplies its own `' w-full'` component-side (exemplars:
`listboxTriggerBaseClass` in `common/listboxParts.tsx` + `Select`/`MultiSelect`/`PeriodPicker`).
No two width rules then target the same element, so cascade order between `.w-full` and
`.w-NN` stops mattering. Prove sizing and cascade claims against rule offsets in
`dist/assets/*.css` or a static headless-Chrome measuring harness (see
`frontend-live-stack-probing`), never the className string.

**The one-width-class rule spans components at a layout slot:** the host slot owns width ONCE (`w-[400px] shrink-0` on SplitView's panel div) and the guest component carries no width utility anywhere, filling the slot via `h-full` flex stretch - no two width rules can fight on the guest element, so cascade order stops mattering there too. Container-query containers need no registration in this setup: a plain `@container` class on the element (SplitView's list wrapper) works natively in Tailwind 4 - later container variants key on that element's inline size, not the viewport.

**A one-line flex filter row that must survive 320px wraps below `sm`, with the flexible input claiming its own full line.** When the row's FIXED members already exceed the viewport (measured: filter toggle 74-115px + labeled action button 128-147px + sort select 192px + gaps = 424-478px against 288px available at 320px), `min-w-0` on the search input cannot save it - the row itself must wrap. Recipe: `max-sm:flex-wrap` on the row; the `flex-1` search gets `min-w-0 max-sm:basis-full` - `basis-full` is the load-bearing piece, since with basis-0 the search packs onto the controls' wrap line at ~0-30px wide (the standard mobile search-on-own-line-top pattern instead gives it the full line deterministically); a pinned-width sibling uses a variant-scoped pair (`w-48 max-sm:w-24 shrink-0`). A variant pair like `w-48` + `max-sm:w-24` is NOT the one-width-class trap - that rule guards two UNPREFIXED width rules fighting in sheet order, and the `max-sm:*` half lives in its own media query that never co-applies with the base (prove it against rule offsets in the compiled sheet). Sibling header buttons go in ONE wrapping flex group (`flex flex-wrap items-center gap-3`, the gap matching the row's own so every gap is uniform) - `justify-between` treats two independent buttons as line ends and flings them apart across the viewport. Exemplars: the filter rows in `Transactions.tsx`/`Planned.tsx` and the header action group in `BudgetDetailPage.tsx`. The rule crosses the component boundary into shared slots: a slot whose own actions container does NOT wrap (PageHeader's `flex gap-2 items-center max-sm:w-full max-sm:justify-end`) makes the wrapping group the payload's duty - a caller passing multiple action clusters wraps them in ONE inner `flex flex-wrap` group, and that group is what stacks the clusters on separate full-width lines at 375px instead of overflowing the non-wrapping container (exemplar: `BudgetDetailPage`'s `actions` payload wrapping its period cluster and labeled actions in one `flex flex-wrap items-center gap-3` group).

A date-pair variant of the same recipe (two fixed `w-full` inputs in one row, overflowing a `col-span-2` cell below ~360px): `max-sm:flex-wrap` on the row plus `max-sm:hidden` on the cosmetic separator between the inputs (a dash stranded alone on a middle line is noise); the inputs' existing `w-full` IS the load-bearing basis-full that hands each wrapped input its own full line - never add flex-basis utilities on top of it, and never UNCONDITIONAL `flex-wrap` when children carry `w-full`: 100%-basis items claim their own line at every width, which breaks the desktop one-line pair. No `min-w-0` on the wrapped inputs in this shape - no wrapped line ever shrinks below its content. The envelope below `sm` is stacked BY CONSTRUCTION at every sub-sm width, never "one line if the viewport is wide enough": `w-full` resolves flex-basis auto to width 100%, so each input's hypothetical main size alone fills the wrapping line (a 480px "should fit by now" expectation is unreachable); spec or probe a one-line-below-sm pair only for shrinkable inputs (`flex-1 min-w-0`). At >=sm the nowrap row shrinks both `w-full` inputs to their automatic flex minimum (~135px in Chrome) and the pair shares one line. Exemplars: the From/To row in `components/filters/DateRangeEditor.tsx` and the min/max row in `components/filters/AmountRangeEditor.tsx` (same `${inputClass} max-sm:min-h-[44px]` inputs and a U+2013 separator span hidden below `sm`; these two spans are the whole tree's pair-separator census, pinned by a count-2 grep gate on the span's literal text). The editors render only inside a host popover or sheet, so a pair's narrow-width overflow is invisible to cold-load width matrices - only an open-popover probe measures it. Separator glyphs between look-alike rows are a design decision to make explicitly, never an incidental normalization while editing either file.

**Tables in a shrinking container: Chrome's auto table layout decides columns, floors, and input claims.** Column sets key on the table's OWN width via an `@container` wrapper (beside a 400px side panel the viewport says 1280 while the table sees ~552), built as COMPLEMENTARY `@min-[...]` pairs against a base - base = narrowest set, each upgrade (`@min-[560px]:table-cell`) adds a column and hides the narrow set's second line at the SAME boundary it appears at - never `@max-[559px]` + `@min-[560px]` twins (a fractional 559-560px width matches neither). Row height floors are `h-*` utilities, never `min-h-*`: Chrome's automatic table layout ignores `min-height` on BOTH `<tr>` and `<td>` (measured: a computed 44px min-height rendered at the 33px content height) while `height` on a row/cell is treated as a MINIMUM by CSS table sizing - taller content (a second line, an original-currency facet) still grows the row. A table-hosted input's intrinsic width claim is managed by a `w-0 min-w-full` wrapper: the definite zero width shields the content from intrinsic sizing and zeroes the claim, `min-width: 100%` restores the fill - but the wrapper also kills max-content, so a claim that must return in some bands is restored by BANDED container variants (the add-row date input: `w-0 min-w-full @min-[560px]:w-auto @min-[560px]:min-w-0 @min-[760px]:w-0 @min-[760px]:min-w-full` - collapsed in the narrowest set AND the widest, where the data columns' own floors are narrower than the input's claim). The floors being managed are real: a bare `w-full` text input directly in a td contributes ~149px min-content (NOT ~0), and a native date input keeps a ~130px intrinsic floor regardless of its width/min-width - percentage width alone never collapses either. A form hosted as a table row mirrors the visible columns by carrying the data cells' container-gate classes on its own cells (`hidden @min-[760px]:table-cell`) - zero JS width measurement, correct at every table width by construction. Exemplars: `TransactionsTable.tsx` (`ROW_FLOOR`, column sets), `TransactionAddRow.tsx` (banded wrapper, mirrored cells).

**Truncate-plus-`shrink-0` siblings sharing a constrained cell put truncation on an INNER element, never the container.** A sticky cell hosting a truncating name beside `shrink-0` chevron and `shrink-0` chip siblings carries the width cap on the cell itself (`max-w-[16rem]`) and `truncate` on an inner `min-w-0` span or Link only - container-level ellipsis (the td's own `text-ellipsis`) cannot express "this child yields, those two never do", and a chevron rendered INSIDE the truncating span can be ellipsized away with the text it trails. Exemplar: the sticky category cell in `pages/BudgetDetailPage.tsx` (Link + inner `truncate` span, chevron inside the Link but outside the span). Free text in a chip body truncates on an `inline-block` span - max-width never applies to a bare inline span - plus `align-bottom`, because an overflow-hidden inline-block's baseline becomes its bottom margin edge and would float the fragment above the label (exemplar: the remembered-search chip body in `Transactions.tsx`).

## Modal Pattern

Use `common/Modal.tsx` — it renders a centered panel on desktop and delegates to
`common/BottomSheet.tsx` on mobile (animated bottom sheet with scroll-lock, stack-aware
Escape, focus return, keyboard avoidance). Don't hand-roll fixed-overlay markup:

```tsx
const { t } = useTranslation('transactions')
// ...
<Modal open={isOpen} onClose={onClose} title={t('form.editTitle')} size="md" className="p-6">
  {/* content */}
</Modal>
```

The `title` prop is UI text and goes through `t()` like any other label.

**Titles go through the `title` prop — never a hand-rolled `<h2>`.** The prop is `string`,
not `ReactNode`: dynamic titles are template literals or string ternaries
(`title={`Set balance — ${account.name}`}`), never JSX. `Modal` renders one header flex row —
title left, labeled Close button (X icon + "Close" text) right — and the Close button carries
`shrink-0` so it can never overlap the title; a standalone `<h2>` in the panel flow
paired with a floating absolute X is the legacy overlap / accidental-closure bug — do not
reintroduce it, and never absolutely position a close button over panel content. The same
header row renders on both viewports: desktop at the top of the centered panel, and on mobile
inside the sheet body just below the drag handle (`BottomSheet` itself renders no close
button — its handle bar is a visual affordance; closing is scrim tap or Escape) — callers just
pass `title`. Modal title typography lives solely in `Modal`'s header render; don't add
per-caller title styling or title-to-content spacing (the header owns the bottom margin).

Non-modal sheets (pickers, action menus) use `BottomSheet` / `ActionSheet` directly
(`design/components.md` §21).

When a component manages multiple modals, use separate boolean state for each. Modals can chain by closing one and opening another (`onEdit={() => { setShowDetail(false); setShowEdit(true) }}`). `ActionSheet` actions close the sheet before running, so they chain safely.

**A settings bridge from an open form keeps both overlays mounted.** When the second overlay exists so the user can manage reference data mid-form (a "Manage currencies" link inside a form modal), chain-closing would destroy the typed values - the wrong move. Keep the form modal mounted, open the panel as a second overlay, and render the panel instance AFTER every other modal in the page JSX: both sit at the shared `z-modal` level so DOM order decides stacking, and `useOverlay`'s mount-order stack closes the later-mounted panel first on Escape. Gate the bridge callback at the page level (`canManageCurrencies ? openSettings : undefined`) so unauthorized roles never see a dead-end link; the prop itself stays optional so ungated call sites render no link. Exemplar: the `WorkspaceSettingsPanel` bridge in `AccountsPage`/`BudgetsPage`.

**Modal state lifecycle — two sanctioned shapes:**

- **Permanently mounted (rendered unconditionally, no `key`):** seed **all** form state in a session render-adjust - never an open-effect (`set-state-in-effect` is an error; see §State Changes in Event Handlers). A sentinel-initialized session snapshot (`{ open: false, mode: 'none', source: null }` can never match a real session, so the first open always seeds), then a two-if fall-through below the last hook (`AccountFormModal`, `TransferModal`, `TransactionFormModal`):

  ```tsx
  const seeding = open !== session.open || session.mode !== mode || session.source !== source
  if (seeding) setSession({ open, mode, source })
  if (seeding && open) {
    setName(account?.name ?? '')
    // …every field, every open
  }
  ```

  The mode discriminator (edit/repeat/create; footer Copy moves the SAME entity object from `transaction` to `copyFrom` without closing) catches mid-open source swaps that identity comparison alone would miss. NO `return null` inside the adjust: React discards the pass and re-runs the component before children render anyway, and the fall-through form keeps every hook below the adjust unconditional (the queries/mutations sitting at the old effect's slot stay in place) and keeps the seed body byte-stable as diff context. `useState(account?.x)` initializers are dead weight here - they run exactly once, before the entity prop exists, so Edit opens blank and silently submits defaults, and the stale values leak into a later New session. When a full reset plus a fresh-per-open default is all you need, prefer ONE `handleClose` wrapper on `onClose` (`BudgetsPage`'s `CreateBudgetModal`): `Modal` funnels every dismissal path (Cancel/Close/scrim/Escape) through `onClose`, and an event handler needs no render-adjust machinery at all. Exemplars of the two-if fall-through: `AccountFormModal` directly, and the form hooks `hooks/useTransactionForm.ts`/`hooks/useTransferForm.ts` behind their modals.

- **Mount-per-use:** a modal that seeds state from props in `useState` initializers drops the `open` prop entirely — the caller's conditional render (`{row && <Modal …/>}`) IS the open/close mechanism. Document the contract in the docblock (`ExtractionReviewModal`, `PeriodFormModal` - its caller's mode/id/`nonce` render `key` forces a fresh remount every open, including add-after-add). From a list page, page state is `{entity} + nonce` with a key of mode + entity id + nonce (`BudgetsPage`'s add-period modal: `add-${budget.id}-${nonce}`) - the nonce is load-bearing because entity id alone reuses the mounted instance when a close-then-open batches into one tick (the null gap never renders). A plain FORM component owns its Modal the same way: it renders `<Modal open onClose={onClose}>` with the open prop hardcoded (`CreateWorkspaceForm`), so every call site collapses to one conditional element and title/size/padding live in exactly one place. Each opening container (dropdown, sheet) closes itself BEFORE the modal mounts, so Escape always faces exactly one layer - the layering question dissolves by construction instead of by `stopPropagation` discipline. Form-level Escape handlers are deleted, not ported, when a form moves into a Modal: the overlay stack owns Escape, and a surviving form-level branch fights the topmost-layer-only close.

**A modal whose target is a LIVE-DERIVED match latches the whole session (mode + row) in the opener state at click time - render-site props branch on the latched state, never on the live derivation.** The mount-per-use shape above assumes the opened entity is fixed by the click that opened it (a row button); a create-or-edit affordance whose edit target is a client-side match over a query list is different - `BudgetDetailPage`'s bookmark button derives the matching non-archived budget bookmark from `useBookmarks()`, and a form modal that recomputes its discriminator from props on every render (`BookmarkFormModal`'s `isEdit = !!bookmark`) would let a mid-open `refetchOnWindowFocus: 'always'` refetch (the hook pins it) flip a mounted form between create and edit submit paths mid-session. The latched opener state (`{ mode: 'create' } | { mode: 'edit'; bookmark } | null`, set in the single opener button's onClick) freezes the session; the null state always renders between sessions, so close-then-reopen is a remount and no key/nonce is needed.

**A modal whose caller clears its source prop in the same tick as close renders exit-window content from a local source copy.** `BottomSheet`'s `useDelayedUnmount(open, 80)` keeps the sheet mounted through the 80ms exit animation, and a page that clears its source row state in the same tick as the close leaves the modal's source prop null while the sheet is still animating out - a modal reading the prop directly blanks its context line for that window. Seed a local `source` state copy alongside the other seeded fields in the session render-adjust and render context lines from the copy, never from the prop. Exemplar: the local `source` copy in `ExecuteAdjustedModal`.

**Escape inside a Modal:** a popup that lives inside a Modal (e.g. `DatePicker`'s desktop panel) consumes Escape at its focusable element — `preventDefault()` + `stopPropagation()` + close — gated on the popup being open, so a closed popup still lets Escape bubble to the surrounding Modal. A transient overlay with no focused element to consume Escape at (a hover/pinned hint) cannot use that shape: a document-level keydown in the CAPTURE phase + `stopPropagation()` fires before `useOverlay`'s bubble-phase listener, so the first Escape closes only the hint and the next closes the modal. Exemplar: `common/InfoHint.tsx` (component spec in `design/components.md` §4).

**An in-flow panel (not an overlay) skips every overlay mechanism and yields Escape to the overlay stack.** No scrim, focus trap, scroll lock, `useOverlay`, `role="dialog"`, or z-index of any kind - the panel is page flow, and the caller's conditional render IS the open/close mechanism (mount IS open). Its document-level keydown runs in the BUBBLE phase with `[]` deps, gated on `!hasActiveOverlay()`, reading `onClose` through a latest-callback ref so the listener never re-registers. Bubble phase is load-bearing: DatePicker's desktop popup consumes Escape at its input with `stopPropagation`, which halts propagation at the React root BEFORE a document bubble listener - a capture-phase listener would fire first and close both the popup and the panel. The pinned footer sits OUTSIDE the scroll area as `shrink-0`. An inline editor hosted in such a panel consumes its OWN Escape: the editor `preventDefault()`s the handled key at its focusable element (EditableField's base keydown arm and every override - a documented editor-bag contract), and the panel's document-level listener yields on `e.defaultPrevented` before closing. That preventDefault/defaultPrevented pair - not `stopPropagation` - is the in-repo convention for consumed Escape (the add-row hotkey and note-override sites use the same yield): React 19's synthetic `stopPropagation` DOES delegate to `nativeEvent.stopPropagation()` for bubble-phase document listeners (correcting an older planning note that claimed otherwise), but it halts propagation for every other consumer, while `defaultPrevented` leaves the native event untouched. Exemplars: `common/EditableField.tsx` + `layout/DetailPanel.tsx`.

**A standalone popover (no Modal, no overlay stack) owns its Escape and focus-return machinery through ONE document bubble listener, attached while open.** While open, a single `document.addEventListener('keydown', ...)` consumes Escape with `preventDefault()` + `stopPropagation()` so nothing beneath the row reacts to the press; teardown removes it. `stopPropagation` is load-bearing against overlay consumers that never check `defaultPrevented`: `useOverlay`'s sheet-close listener is a document-level bubble-phase keydown with no `defaultPrevented` read, so an EDITOR hosted inside such a sheet steps one level per press only by consuming Escape at its own container element (a React `onKeyDown` doing `preventDefault()` + `stopPropagation()` - preventDefault alone would still close the whole sheet). The element-level form works because focus sits inside the container by construction (the back button `autoFocus`es on mount), putting the container in the event path - the same idiom as a popup consuming Escape inside a Modal. Focus return on close keys on `document.activeElement === document.body`: that predicate alone distinguishes Escape-close (focus fell out of the removed panel to `<body>` and needs a home) from swap-close (focus already moved to the newly clicked trigger) without the component knowing anything about the host's popover state. The return focus itself is deferred (`setTimeout 0`): a focus call issued inside a mousedown listener is clobbered by the browser's default mousedown focus action, so it must land one macrotask later. The outside-click path discriminates with `target.closest('button, a, input, select, textarea, [tabindex]:not([tabindex="-1"])')` so a dismissal never steals focus from a focusable click target; dismissal listeners read the close path through a latest-ref (`closeRef` synced in an effect, the merged-setter idiom under Controlled-Open Props) so a popover swap can never run a stale trigger's refocus path; and an action row that chains into a modal calls close-without-focus-return (`closePopover(false)`) so the modal mounting next owns focus unraced. Exemplars: `components/filters/FilterChipsBar.tsx` (document listener, `deferFocus`, `closeRef`) and the editor level of `components/filters/FilterSheet.tsx` (element-level consume inside the sheet).

**A scrollable selection list inside a Modal scrolls the inner list, never the panel.** Put `overflow-y-auto` on the list element with `flex-1 min-h-0` + `overscroll-contain`, not in the panel `className` - a panel-level scroll unpins the header title on desktop and double-scrolls inside the mobile BottomSheet (whose base `max-h-[92dvh]` out-cascades a caller `max-h-[85vh]` in compiled-sheet order). Exemplar: the language list in `LanguageModal`.

**Reference-data arrival gets a separate length-keyed render-adjust.** Late-arriving accounts/currencies fill a pristine create form but never clobber typed edits: key the adjust on list LENGTHS (`accounts.length`), never array identity - a `refetchOnWindowFocus: 'always'` refetch returns an equal-length list and re-seeds nothing - and guard each seeded field with a still-at-seed check so a mid-edit refetch leaves typed values alone. Exemplar: the arrival adjust beside the session adjust in `TransferModal`.

**Migrating a hand-rolled fixed overlay to `Modal`:** pass `title` (string prop) + `className="p-6"`, and delete the manual `useOverlay` plus the hand-rolled header/`aria-labelledby`/close-X machinery — `Modal` wires stack-aware Escape/scroll-lock/focus on desktop and delegates to `BottomSheet` on mobile, preserving the behavior by construction.

**Sanctioned exception - full-bleed media lightboxes.** A viewer whose content IS the viewport (the attachment image lightbox) does not fit `Modal`'s centered panel and title header, so hand-rolling it is allowed - but it still goes through `useOverlay(active, onClose)` for stack-aware Escape, refcounted scroll lock, and focus capture/restore, and its panel carries `ref` + `role="dialog"` + `aria-modal` + `tabIndex={-1}` exactly like `Modal`'s panel. An unregistered overlay lets Escape close the modal underneath it (the bug class `useOverlay` exists to prevent). Exemplar: the lightbox in `transactions/TransactionAttachments.tsx`.

## Pointer Gestures and Drag Interactions

Three gesture surfaces exist: `hooks/useDragToDismiss.ts` (vertical sheet dismiss), `components/common/SwipeRow.tsx` (horizontal swipe-to-reveal), and `hooks/useHorizontalStepDrag.ts` (horizontal step drag). New gesture work copies their shared construction rules:

- **Gesture state lives in one ref; handlers are fresh per render; React state only at phase boundaries.** The pointer machine (slop, capture, offsets) stays in a `stateRef` with zero state and zero effects - React re-attaches handlers every commit, so each pointer event reads what the previous event wrote, and a mid-gesture refetch cannot freeze a stale callback. Imperative `style.transform` writes per frame coexist with React's `style` prop only when the two own DIFFERENT properties (React kept `maxHeight`/wrapper padding, the hook owned `transform`) - never let both own the same one.
- **Handlers read committed state, not a ref mirror.** The compiler lint (`react-hooks/refs`) traces a `close()` called from a render-adjust into any ref write and errors - dropping offset refs entirely is lint-quiet by construction because handlers re-bind every commit.
- **Dismissal continuation: the close fires at the gesture's `transitionend`, never at drag release.** The dismiss transition animates the inline transform to the terminal value (`translateY(100%)`, ~80ms) and only its `transitionend` (a timeout backstop guards a lost event) runs `setDismissed(true); setDragging(false); onCloseRef.current()` in one batch - `open=false` and the terminal flag land in a single commit, the motion derivation suppresses the exit keyframe, and the keyframe cannot restart the panel from rest mid-flight. All gesture writes live in event handlers plus ONE sanctioned render-adjust (the reopen self-heal: `if (enabled && (dismissed || dragging))`, the actual-vs-desired shape); effects do DOM-only work (listener detach, inline-style clears).
- **A one-shot completion is guarded by gesture-object identity** (`gestureRef.current === gesture`), which subsumes the finished-flag and stale-transition races in one check.
- **The trailing click after a drag is eaten by a TRANSIENT one-shot window-capture listener, never a sticky ref flag.** A drag ending off-target synthesizes a click on the nearest common ancestor of its pointerdown/up targets; the listener (`stopPropagation` + `preventDefault`, removed via `setTimeout 0`) eats exactly the release-turn click. The sticky ref alternative is a real bug the probe caught: touch pipelines synthesize NO trailing click after a drag, so a flag that only resets on the next pointerdown stays armed and silently swallows the next KEYBOARD activation (Tab + Enter on a revealed button). Three identical copies exist (one per surface above) - a FOURTH gesture surface is the extraction trigger for the shared pointer-math/swallow util (extract-at-the-third); do not unify piecemeal in a task touching only one surface.
- **`touch-action` is the scroll contract, not visual chrome.** The guaranteed touch surface carries `touch-none` (the sheet's sticky handle band); scrollable content stays `touch-pan-y`, and a vertical touch there is handed to the browser pan and dies at pointercancel BY DESIGN - so "drag by the handle or header" is honored for touch only on the handle band, while mouse/pen pointers get a wider header band that bails on interactive targets. Coarse-pointer gating lives at the CALL SITE via the hook's `enabled` (`useIsTouch()`); the hook itself never inspects `pointerType`.
- **Capture at lock (or pointerdown for step drags) does not break vertical scroll**: touch pointers get implicit capture anyway and `touch-action` governs panning - a vertical drag on a captured host still scrolls the window. Capture ON is for a LEAF target only (a stepper label button); a host wrapping cards/links keeps capture OFF - capture retargets the synthesized tap to the host and breaks the children's clicks.
- **A step-drag fires `onStep` exactly once per gesture**, at the threshold crossing.
- **Swipe-to-reveal specifics:** the collapsed tray is an `inert` SIBLING painted behind the row content via DOM order (no z tier) - `inert` keeps it out of the tab order while collapsed, and DOM-order paint means keyboard users reach the tray buttons from the PREVIOUS row's content, never from the open row's own. The row content keeps its own `tappableProps` role/tabIndex/activation byte-unchanged; tray buttons are siblings, never descendants, of the row's button role. Measure the tray by the ACTION BUTTONS' intrinsic width via an inner flex ref - an `inset-0` tray measures the full row width, not the buttons. The single-slot open-row registry is module-level (opening one row closes the other); the route-change close is a render-adjust on `useLocation()` identity (an effect body would trip `set-state-in-effect`), with a `(!eligible) && open` self-heal releasing the slot when eligibility flips mid-reveal.
- **Attach a drag handler to exactly ONE named non-scrollable element per page; horizontally scrollable regions stay siblings outside the attachment point** - a structural exclusion, not a heuristic. Exemplars: `MonthStepper.tsx`'s label button (capture ON) and `BudgetDetailPage.tsx`'s `sm:hidden` content block (capture OFF, stepping the existing `goToPeriod`).

## Deferred Destructive Actions (Undo)

Client-side deferred deletes (`hooks/useDeferredDelete.tsx`) arm a pending window and commit later, with Undo. The shape generalizes to any destructive action with a grace period:

- **The pending slot lives in a MODULE-LEVEL external store per entity family, exposed through `useSyncExternalStore`.** Module scope is load-bearing, not stylistic: the record page arms the window and navigates back immediately, and the 1024+ panel close is a route swap that REMOUNTS the page tree - a useState slot would die at either boundary and Undo could not restore the row. The `pagehide`/`visibilitychange` listeners register once at module scope and no unmount cleanup exists anywhere, so StrictMode's double mount cannot double-fire them.
- **A single pending slot, never a set.** A second delete flushes the first (its DELETE fires at the second click; one toast remains) - a set would silently stack unrecoverable requests behind one Undo affordance per row.
- **Undo clears the slot - no request was ever sent.** Every terminal path (commit timer, second delete, pagehide/visibility-hidden flush, undo) ALSO dismisses the toast: once flushed the delete is unrecoverable, so a dead Undo button must never outlive the pending item. react-hot-toast's own auto-dismiss does not cover this - the commit timer is independent of its hover-pause.
- **Flush triggers deliberately exclude route change and unmount** - an unmount flush would fire exactly in the flows where Undo must keep working (navigate-back after arming, panel close). The page-death flush is a keepalive `fetch` (axios cannot outlive the page), reading the token at flush time via `getAuthToken()`, never closed over at arm time - a stale/null captured token silently drops the teardown delete.
- **The Undo affordance is an inline button inside the toast MESSAGE ReactNode** (react-hot-toast has no `action` option). Hosts filter the pending row out and pulse totals strips off `pendingId`; empty-state gates stay on the UNFILTERED list so deleting the only row does not flash empty state. Invalidate the flushed family keys on return so a reopened tab converges with what was committed in its absence.

## Window Scroll Restoration (POP-only)

Phone-band window scrolling (`useMobileScrollRestoration` in `components/layout/MainLayout.tsx`) restores positions for Back/Forward only:

- **New navigations start at the top; only POP restores.** The restore keys pathname+search and gates on `useNavigationType() === 'POP'`. The gate is what makes the restore deferrable: restoring on every navigation forces a restore before data arrives, which the browser clamps to skeleton height.
- **The apply is deferred: a ResizeObserver on `document.documentElement` + window resize re-check, a 3s give-up, and cancel on the first user scroll input** - covering Back landing while the document is still skeleton-height. The natural content-growth trigger is reachable only after a gcTime eviction of the list cache entry (>5min dwell); invalidated-but-cached entries render rows immediately.
- **The hook owns `window.history.scrollRestoration = 'manual'` while enabled and reverts it on cleanup.** The browser's own async POP restore clamps to skeleton height and races the deferred apply; ownership is scoped to the phone band (the tablet `<main>` twin and desktop never see it).
- **Record-page back arrows are history-aware.** When the arrival was a row tap (`typeof location.state?.search === 'string' && location.key !== 'default'` - the marker is "is a string", never truthiness: an unfiltered row tap carries `search: ''`), the arrow passes `onBack={() => navigate(-1)}` so Back restores scroll; deep links keep the PUSH `backTo` target. A rider host overriding a shared component's navigation keeps ONE navigation owner per click: the component calls the override when provided, else its own navigate - never both (exemplar: `PageHeader`'s optional `onBack`).
- **REPLACE and fresh navigations land at the top by design** - the delete-success path (`navigate(backTo, { replace: true })`) opens the list at the top; nothing downstream may assume tab memory.

## Component Pattern

- Remove unused props from component interfaces — dead props create misleading API surfaces.
- **Component defaults live inside the component.** Placeholder, aria-label, and similar presentation defaults ship with the component (`PeriodPicker` owns its "Select period" trigger placeholder and "Periods" panel label); call sites pass data and handlers only. A call site re-supplying a default creates a second copy that can drift from the component's.
- When a component handles a concern internally (e.g., resend verification via API call), don't also expose a callback prop for the same concern. One mechanism is enough.
- When a child component needs more than an ID from a list item, pass the full object through callback props instead of just the ID:

```tsx
// Bad — child must fetch data again
onExecute: (id: number) => void
// Good — child has all the data it needs
onExecute: (planned: PlannedTransaction) => void
```

- **Accordion/disclosure components:** the collapsed header is a real `<button>` carrying `aria-expanded` + `aria-controls`; the expanded region is its **sibling** with a matching `id` + `role="region" aria-label` - never nested inside the button (interactive content inside `<button>` is invalid HTML and steals focus/clicks). On list pages, wire the pair from ONE `useId()` value (the toggle's `aria-controls` ↔ the region's `id`). The region hides via the `hidden` CLASS (never the HTML attribute) so `aria-controls` stays resolvable and prefilled content inside the region survives toggles; exemplar `common/Disclosure.tsx` (controlled-only collapsible section).

- **Every non-submit `<button>` carries `type="button"`.** Inside a `<form>` the browser
  default is `type="submit"`, so a bare Cancel/icon/close button silently submits the form
  on click. Only actual submit buttons omit the attribute. `common/ConfirmDialog.tsx`
  and `Modal`'s Close button show the pattern.
- **Icon-only stepper/chevron buttons carry the corrected idiom:** `type="button"` + the focus-visible outline triple (`focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-border-focus`) + `strokeWidth={1.5}` on the lucide icon + `aria-hidden="true"` on the icon when the button itself carries the accessible name. The pre-correction form (rings omitted, default `strokeWidth` 2) survived unnoticed in the period chevrons of `BudgetDetailPage` and `Pagination` because nothing about a mouse-only click ever shows the omission - it surfaces only when keyboard focus reaches the unringed button - which is why a new button copies the exemplar, never whichever icon button sits nearest (both files have since been swept to the corrected form). Exemplar: `common/MonthStepper.tsx`.

- **A registry-resolver function that RETURNS a component is consumed via member-expression indexing, never a call assigned to a capitalized identifier.** `react-hooks/static-components` (error) reads any `const Icon = resolver(key)` in a render body as "creating a component during render" - it cannot prove the call only looks up a pre-existing component - while `const Icon = REGISTRY[key] || Fallback` passes (the `TYPE_ICON[account.type]` row-lookup precedent in `AccountsPage`, `BOOKMARK_ICONS[bookmark.icon]` in the bookmark surfaces). Exporting a resolver helper is fine as a binding-name contract, but render bodies inline the member-expression lookup (with a comment saying why the helper is not called) instead of calling it.

- **A render-prop bag's callbacks escape into render - no refs inside them.** A bag handed to a render prop (`renderEditor(bag)`) is invoked during render, so any closure in the bag that touches a ref is an unlawful render-time ref access under `react-hooks/refs` (the compiler cannot prove the callee will not call it synchronously), and `useCallback` wrapping cannot fix it - the bag member still escapes. Read DOM truth instead: a detach-blur guard is `if (!e.currentTarget.isConnected) return` in the bag's `onBlur` (`FocusEvent<HTMLElement>`) - a blur fired while the editor unmounts cannot re-commit for EITHER dismissal path (cancel or a settled save; the one-shot-ref design it replaces covered only cancel), while a real blur on a live editor still commits. Exemplar: `common/EditableField.tsx`.

- **A wrapper around a multi-child editor guards blur on relatedTarget containment.** React's `onBlur` is bubbling focusout, so a wrapper hosting several focusable children (a budget Select feeding a category Select) fires "blur" on every INTERNAL focus move and would close the editor mid-edit: guard with `ref.current.contains(e.relatedTarget)` before delegating to the bag's blur. Controls that own their Enter key (Select triggers, DateQuickPick) get an `escapeOnly` bag arm - Enter belongs to the control, only Escape closes; free-text editors take the bag's full Enter/Escape. Exemplar: `FieldEditorShell` in `transactions/TransactionRecord.tsx`.

- **A one-field save hook REJECTS on failure and never toasts - the editor owns error display, and sibling editors stay closed while `isSaving`.** Every save of a full-replace-PUT entity re-sends the complete payload built from the loaded row, so a second editor committed while the first save is pending silently reverts the first field - two overlapping saves built from the same base row lose the earlier write. Fold the hook's `isSaving` into the one row-disabled derivation every row inherits (never scatter per-row checks) and gate through `EditableField.disabled`, which blocks ONLY the idle display button's `startEdit`: the button is unmounted while editing, so an in-progress editor is never force-closed by the gate. The editor catches the rejection, shows the server message, and restores the previous value. Exemplar: `rowsDisabled = !canWrite || isAuto || isSaving` in `transactions/TransactionRecord.tsx` over `hooks/useTransactionFieldSave.ts`.

- **Page-wide batch editing rides a page-owned draft map with a sequential, partial-failure save loop.** The page owns every piece of edit state (drafts, per-row errors, discard confirm); the row component renders inputs only for keys present in the map. Changed-row detection compares the canonical WIRE form - `normalizeAmountInput` plus a trailing-fraction-zero strip, so `'150'` equals `'150.00'` - because the backend serializes 2-decimal strings and a plain normalized compare fires no-op PUTs on cosmetic retypes while muddying the changed count. Saving is a `for..of` over the changed rows in rows order: saved keys leave the map (their inputs close), failed rows keep their draft plus the inline `getApiErrorMessage` text, exactly one toast per Save attempt, and the family key is invalidated once after the loop - a parallel `Promise.all` save cannot express partial failure. Draft inputs are plain `type="text" inputMode="decimal"` fields, never a debounced shared amount component whose commit timer reads stale at the Save/Cancel boundary; normalization runs only at the compare and commit seams. Type the map `Record<string, string | undefined>` - with `noUncheckedIndexedAccess` off, a `string`-typed index access cannot be compared against `undefined` (TS2367), and the widened value type makes every presence check cast-free. Exemplar: edit-plan mode in `pages/BudgetDetailPage.tsx` + `components/budgets/BudgetCategoryList.tsx`.

- **A file-upload input never carries `capture`.** With `capture="environment"` on an
  `<input type="file">`, mobile browsers skip the native source chooser (photo library /
  file / camera) and open the rear camera directly - desktop ignores the attribute
  entirely, so the bug class is mobile-only and invisible during desktop dev, and it
  applies to every file-picker entry point, not just receipt scans. The absence is
  deliberate and carries a one-line rationale comment above the picker (domain reason
  only, no PR references - see the comment rules under Naming Conventions): an absence
  cannot explain itself, and without the comment the next contributor "helpfully"
  re-adds the attribute. Exemplar: the always-mounted hidden receipt picker in
  `pages/NewTransactionPage.tsx`.

- **Inside a Link-wrapped card, per-card actions are `<button type="button">`, never a nested `<Link>`/`<a>`.** Interactive content inside an anchor is invalid HTML and double-navigates - the card's own Link still fires after the inner one. The handler starts with `e.preventDefault(); e.stopPropagation()` to suppress the card's navigation, then `navigate()` from `useNavigate()` for route changes. Exemplar: `BudgetsPage`'s per-card icon cluster.

- **Sticky rows inside a `max-h`-capped scroll panel need an opaque background and exactly one unconditional bg utility.** A pinned footer (`sticky bottom-0 z-10 bg-surface`, mirroring `PanelSearchInput`'s `sticky top-4 z-10 bg-surface` in `listboxParts.tsx`) must be opaque so rows scrolling beneath are masked, and the conditional background goes through mutually exclusive branches - the keyboard-highlight branch carries `bg-surface-hover` ALONE, never stacked on an unconditional `bg-surface` (two same-specificity plain utilities make the winner stylesheet-order luck; only pseudo-class variants like `hover:` safely out-specify the base). The mobile sheet gets plain row parity instead - its 92dvh cap is not the desktop panel's tight max-h, so pinning buys nothing.

- **A page-level sticky footer composes fixed-nav clearance with the OSK inset through CSS `max()`.** The class half reserves the clearance (`sticky bottom-0 max-sm:bottom-[calc(4.5rem+env(safe-area-inset-bottom))] z-10 bg-surface` - plain `z-10` is local stacking inside a surface), and the keyboard half applies via inline style ONLY when `hooks/useKeyboardInset.ts` (shared with BottomSheet) reports a nonzero inset: `max(${keyboardInset}px, calc(4.5rem + env(safe-area-inset-bottom)))`. The composition invariant: an OSK lift can never drop the bottom-nav clearance, and a partial keyboard never sinks below it - replacing one half with the other breaks exactly one of those. Fine-pointer desktops report inset 0 (`visualViewport.height === innerHeight`), leaving the class offset untouched. Exemplar: `layout/FormPage.tsx`.

- **Consume hook predicates where they're needed** — call `usePermissions()` inside the row/component that needs the decision; never re-derive permission math locally or thread it down as boolean props (`canManage`, `isOwner`). Derived copies drift from the hook's truth; dead props are removed from the interface in the same commit.

- **Read-level rights are implicit - ungating a read/navigation action means REMOVING the manage condition, never minting a read predicate.** Every workspace member can read; a `canViewAccounts` that always returns true is dead API surface that drifts the moment someone treats it as a real check (the hook stays mutation-only). Apply the ungate symmetrically to every surface the action lives on, one commit: desktop inline links (wrap only the mutation entries in `{canManage && (…)}`), the touch card (`tappableProps` keyed on `isTouch` alone - the spread carries the button semantics, so keyboard/screen-reader reachability widens with the gate), and the ActionSheet's conditional spread (navigation entry outside `...(canManage ? [mutations] : [])`). Exemplar: the accounts view-transactions drill-down in `AccountsPage`.

- **A clickable row - touch `tappableProps` or a fine-pointer `onClick` open handler - that contains interactive children wraps them in ONE stopPropagation seam.** The row carries unconditional `onClick`/`onKeyDown`, so a tap or Enter on a child control bubbles into the row handler and opens the row's ActionSheet (or navigates) on top of the control's own action - prior tappable rows never hit this because their hover actions were `!isTouch`-gated and touch surfaces carried no interactive children. Wrap the interactive children in a single div carrying `onClick={(e) => e.stopPropagation()}` + `onKeyDown={(e) => e.stopPropagation()}` - one seam (the clickable-row precedent in `BudgetDetailPage`) - instead of scattering stopPropagation across the individual child buttons. The fine-pointer branch is the same bug one tier over: a row opened by a plain `onClick` with hover-revealed in-row buttons (Repeat/Delete on a transfer row) double-navigates without the seam - the button's click bubbles into the row's open handler, and a keyboard-synthesized click from a focused button bubbles identically. Exemplars: the manage rows in `BookmarksPage` (touch); the transfer rows in `pages/TransfersPage.tsx` (fine-pointer onClick + hover buttons).

- **A form component that submits its own API call owns its mutation internally** — no `onSubmit`/`isLoading` props threading a parent's `useMutation` down, and never a parent reaching into the child's DOM (`getElementById` + `form.reset()`) — that coupling breaks silently when ids change and couples lifecycles across the boundary. Reset/clear fields in the mutation's `onSuccess`, never at fire-and-forget submit time (a server rejection would otherwise wipe the typed values and force a full retype).

- **ConfirmDialog is wired with `isPending={mutation.isPending}`** (both buttons disable via the shared classes). Dialog close semantics: form modals stay open on error so input can be corrected; a destructive ConfirmDialog with no correctable input (remove/delete, reset 2FA) closes in BOTH `onSuccess` and `onError` - the class is "destructive confirm with nothing to correct", not literally delete mutations.

- **In a `mutationFn`, the durable call comes first; non-durable follow-ups** (post-save description update, post-create upload) go after it, wrapped in a swallowing `catch {}` with a reason comment — a mutation retry must never re-run already-durable side effects (the append branch would duplicate saved rows). When the follow-up is user-recoverable rather than silently retryable, the catch toasts the recovery location instead of swallowing: return the durable result so the mutation still succeeds - two toasts on partial failure (follow-up error + success) is intended design, not a duplicate-toast bug. `isPending` spans the whole chain, so the submit button stays disabled until the follow-up settles. Exemplar: `BudgetsPage`'s `CreateBudgetModal` - create budget, then chain `createPeriod`; its failure toasts "you can add it from the budget page".

- **Derived-until-touched fields:** a field auto-derived from other fields (period name ← start/end dates via `formatPeriodName` in `utils/format.ts`) re-derives in the source fields' `onChange` handlers, guarded by a touched flag that flips `true` only in the derived field's own `onChange` - once the user edits it, source changes stop overwriting their text. Reset the flag only in the modal's reset path (`handleClose` for a permanently-mounted modal; the keyed remount is the reset for mount-per-use), so every fresh open re-derives. No effect is involved - the guarded setters keep `react-hooks/set-state-in-effect` at its frozen baseline. Exemplars: `CreateBudgetModal` (`BudgetsPage.tsx`) and `PeriodFormModal`, both on a `nameTouched` flag.

- **A details disclosure that auto-opens on prefilled values needs the full derived-until-touched latch `(userOpened || hasInsideValues) && !userClosed` - a derived-only latch (`!userClosed && hasInsideValues`) can NEVER open an empty disclosure.** With no inside values the derived arm has nothing to derive from, so a manual open of the empty section is unrepresentable and interactions hosted INSIDE the disclosure (an adjustment switch, a receipt picker row) become unreachable. The full shape keeps every pinned behavior at once: closed by default, auto-open on prefilled values, user-close wins, manual open representable. Exemplars: the More-details disclosures in `transactions/TransactionFormFields.tsx` and `transactions/TransferFormFields.tsx`.

- **Suggestion prefills consult a touched-guard they never write, keyed on USER-action seams only.** A prefill that overwrites a deliberate user pick destroys trust (pick the right account, tap a suggestion, watch your account vanish), so the guard flips only at host user-action seams (a Select's `onChange`) while prefill/seeding/reset writes stay unmarked - a later suggestion can still refresh its own earlier fill. The hook-owned guard takes a name DISTINCT from any same-file `touched` map with different semantics (`prefillTouched` vs the fields component's error-gating `touched`): a same-named pair invites wiring the wrong seam. A field whose suggestion value is stale history rather than current intent (an amount) is NEVER auto-filled - offer it as a one-tap hint button instead, and pin the contract with a grep gate (`applySuggestion` never calls `setAmount`). A prefill that must keep an invariant (currency follows account) routes through the same handler a user pick uses (`handleAccountChange`) - one code path per invariant. When the merged setter carries retirement semantics (every ordinary write retires the hint), only the arming path writes past the wrapper, and it arms AFTER its raw state write - the later write in the same handler wins, so the two paths cannot fight. Exemplar: `prefillTouched`/`applySuggestion` in `hooks/useTransactionForm.ts`.

- **User-interaction-armed blur latching: blur-driven `touched` latches ignore programmatic focus steals.** An autofocused field inside a focus-capturing panel (modal `autoFocus`, then `useOverlay`'s panel-focus steal at mount) blurs programmatically before the user touches anything; an unguarded blur latch records `touched` against the empty value and a pristine open greets the user with "Amount is required". Arm on the first REAL input: a one-way ref set by a document-capture `pointerdown`/`keydown` listener effect (ref-write only, no setState - lint-quiet by construction), plus a single `markTouched(key)` helper that returns early while the ref is unarmed; EVERY blur-latch site in the component routes through that helper, never `setTouched` directly - a new field wired past the seam reintroduces the bug class invisibly. The ordering argument is engine-guaranteed: every user focus change requires a pointerdown/keydown first, while mount steals fire synchronously in the mount-effect flush before paint, so the guard is count-agnostic across 0..N steals and across StrictMode's setup-cleanup-setup double run (whose cleanup refocuses the input, firing a second steal). Rejected alternatives and why they fail: a per-field one-shot "ignore the mount blur" ref breaks under StrictMode (blur #1 swallowed, the cleanup-refocus blur #2 latches); `relatedTarget` discrimination breaks on Chrome (clicking a `tabIndex={-1}` panel background FOCUSES the panel, so a user click-blur and the programmatic steal carry an identical `relatedTarget`). Exemplar: `userInteractedRef` + `markTouched` in `transactions/TransactionFormFields.tsx` - a `sessionKey` remount re-arms the ref per open; it mirrors `openedByUserRef` in the same file and Register's `failedSubmitRef`.

- **Pick the blur-steal suppression by whether YOU issue the steal.** A focus steal the page itself issues (its own effect calling `.focus()` on another field) is observable at the exact moment it fires: arm a one-shot ref in the SAME effect (`document.activeElement === amountRef.current` beside the `.focus()` call) and swallow exactly the blur the steal causes. The document-capture armed latch above exists for the complementary case - steals a component cannot observe (overlay mount machinery, whose count is unknowable) - so choose by observability, not by familiarity. Exemplar: the one-shot blur-theft guard on the amount row in `pages/NewTransactionPage.tsx`.
- **Key-handling scope:** Enter-key interception for a nested non-form action goes on the individual inputs (`onKeyDown` + `preventDefault`), never on a wrapper div — wrapper-level hijacks Enter on focused buttons inside it. Keyboard activation on non-button elements (e.g. a selectable `<tr>`) uses `tabIndex={0}` + `onKeyDown` guarded by `e.target === e.currentTarget` so nested inputs/buttons keep their native Enter/Space.
- **TS strict cannot narrow a correlated const from another variable's truthiness.** A const derived from a nullable (`const monthLabel = exactMonth ? formatMonthYear(exactMonth.from) : null`) keeps its own `string | null` type at the use site, so `exactMonth && <Stepper label={monthLabel} />` fails to compile - the label's nullness is provable only from its OWN test. Extend the render gate with the derived const's check (`exactMonth && monthLabel !== null`) rather than widening the component's prop contract to `string | null` (a wrong contract every call site inherits) or adding an unreachable `?? ''` fallback (which lies about the type).

- **Optional form fields submit `x: value || undefined`** so axios omits the key entirely when blank (backends reject `""`, not absence). To make a text input "required only when non-empty", drop `required` but KEEP `minLength` - native constraint validation ignores `minLength` on an empty, non-required input; zero conditional props needed. A full-replace PUT is the exception - blank sends the key as `null`, never omits it (see Full-replace PUT contracts under API Client Pattern).

- **Conditional ARIA attributes** (`aria-current`, `aria-sort`, `aria-controls`) use `… : undefined` for the inactive state — React then omits the attribute entirely, which is the correct ARIA shape. Prefixed ARIA props destructure as aliases: `'aria-controls': ariaControls`.

- **A takeover panel announces ONCE, statically - mutating step lists stay OUTSIDE live regions.** A panel that takes over a card mid-submit renders exactly one `sr-only` `role="status"` summary when it appears (`grep -c 'sr-only' == 1`); putting the step list inside a live region would announce every stage flip - chatty, and lagging the visuals. The panel itself takes focus via `tabIndex={-1}` + `outline-hidden`, the same panel shape `Modal` uses. Exemplar: `Register`'s setup checklist.

- **A switching control announces through a sibling live region, never by being one.** Button text changes are not reliably announced and buttons must not BE live regions, so a control whose value switches (a currency switcher) renders a visually hidden `<span className="sr-only" aria-live="polite">` beside it carrying the active value on every change. The live region MOVES with the control when it relocates - render it once beside the new home, never in both places (`grep -c 'sr-only' == 1` pins it). A `display:none` copy of the control (`max-sm:hidden`/`sm:hidden` dual embed, one copy always hidden) is outside the accessibility tree, so only the visible copy announces - the dual embed is safe for the live region. Exemplar: `BudgetDetailPage`'s currency strip.

- **`key={index}` on a reorderable list is a bug** — focus and selection jump when a `move` swaps values between stationary DOM nodes. Mint `crypto.randomUUID()` at every row-creation site (`emptyRow`, seeding maps) and render `key={row.id}`.

- **Invisible characters in source must stay visible escape sequences** — write `'\u00A0'`, never a raw NBSP byte (0xC2 0xA0) or a plain space: file writes can silently mangle the byte, reintroducing the collapsing-trigger bug (`MultiSelect`'s empty-state label) while every grep for `u00A0` still passes. Verify with `grep -P '\xc2\xa0'` when touching nbsp literals.

Standard form component shape: props interface, `isLoading` state, `handleSubmit` with `try/catch` showing `toast.error(...)` and `finally { setIsLoading(false) }`.

- **Submit-button micro-loader:** `Loader2 size={13} animate-spin` rendered BEFORE the "-ing" label ("Signing in"), with `items-center gap-1.5` added to the button's existing `flex justify-center`; keep `disabled:cursor-not-allowed`, never `cursor-wait` - every shipped Loader2 button agrees (blessed in `design/components.md` §3). Exemplar: `Login`'s "Sign in" / "Verify" buttons.

**Inline checkbox labels — raw `inline-flex`, not `labelClass`:** An inline boolean toggle inside a form (e.g. "Set as default for {currency}", "Paid in another currency?") uses a raw `<label className="inline-flex items-center gap-2 text-xs text-text-muted cursor-pointer">` wrapping its `<input type="checkbox">` — never the shared `labelClass` from `formStyles.ts`, which carries the block + margin styling meant for field labels *above* inputs. This is the established pattern wherever a checkbox sits inline with its label text.

- **An immediate-action picker pins `value={null}` and holds no selection state.** When every pick fires its action directly from `onChange` and the invalidation refetch removes the option from the derived list (an enable-currency Select whose options are catalog-minus-enabled), local selection state would only ghost an option that no longer exists - zero selection state, the placeholder is the resting state. Only valid where the option list is fully derived and shrinks with every successful action; never copy it to a form whose picked value IS the submission. Exemplar: `CurrenciesSettingsSection`'s enable Select.

- **A control that writes a persisted preference must stay mounted in every state that preference can produce.** A render gate that unmounts the control in a state its own stored value creates is a permanent dead end: the page-size Select lived inside a bar gated on `total_pages > 1`, and picking a size that collapses the list to a single page (persisted in localStorage, re-applied on every mount) unmounted the bar - the dropdown could never come back. Audit persisted-preference controls (localStorage, URL, account setting) for that self-reference. Compound bars split the concern at the component boundary: the persistent preference half renders unconditionally in-component, the situational half (page nav) is gated internally, and call sites key bar presence on "rows exist" (`total > 0`), never "multiple pages exist" - future consumers are correct by construction instead of re-learning the gate at every call site. Exemplar: `Pagination`'s in-component nav gate.

- **A render gate that hides a state-backed form section is PAIRED with a payload gate on the same discriminator, in the same commit.** Hiding the items list for adjustments (`type !== 'adjustment'` on the JSX) removes the affordance but preserves the rows in state BY DESIGN - typed work (a receipt parse before a type switch) must survive an accidental toggle - so the parked rows would silently ride the create payload unless the wire gets its own gate: `items: type === 'adjustment' ? [] : rowsToItems(rows)` matches the backend schema's empty-list default exactly, making the hidden rows' absence explicit rather than accidental.

- **A dependent boolean renders conditionally on its companion field and resets on EVERY clear path of that companion - making the backend's cross-field 400 structurally unreachable.** `materialize_all` requires an `end_date` (DB check constraint + service 400), so the Switch row renders only while an end date is set, and BOTH of the end date's clear affordances (the DatePicker's `''` wrapper value and its X button) reset the flag: a valid form cannot produce the invalid payload, which beats relaying a server error reactively. The payload always sends both keys (full-replace PUT), edit-seeding reads `recurring.materialize_all && !!recurring.end_date` so a rule whose end date was cleared does not re-submit an orphaned flag, and a companion numeric input disabled while the flag is set still submits its value - `disabled` blocks editing, not the payload. Exemplar: `RecurringFormModal`.

- **An optional FK field in a Select uses a sentinel option - never a widened shared contract.** Select's value contract is `string | number` and cannot hold `null`, and a cleared disabled control renders a deliberate state as an unfilled placeholder. Recipe: a module-level UPPER_SNAKE sentinel primitive (`NO_ACCOUNT = 0` - entity ids are positive, so it never collides), the sentinel option listed FIRST, `value={accountId ?? NO_ACCOUNT}` so the trigger shows a real selected state instead of the muted placeholder, and `onChange` mapping the sentinel back to `null`. Type-conditional option lists derive from one const (`accountSelectOptions` built from `accountOptions` plus a type gate) instead of branching the JSX - a type the backend rejects account-less (adjustments) simply drops the sentinel, and Select's absent-value-renders-placeholder contract shows the incompleteness with zero extra state. Picking a parent entity sets AND locks the dependent field (`disabled={accountId !== null}` + stock disabled styling); picking the sentinel KEEPS the dependent value - the typed amount is already in that currency, so do not snap to the primary. Exemplars: `PlannedFormModal`, `transactions/TransactionFormFields.tsx` (sentinel helpers in `utils/accountSelect.ts`). Do NOT widen a shared component's typed contract for one field.

- **A Select feeding a multi-field DRAFT keeps the sentinel until serialization - the null mapping lives in ONE seam.** The `NO_ACCOUNT` recipe maps the sentinel back to `null` in `onChange`, right for a single field; across an N-field draft that is per-field boilerplate and a facet can forget its mapping. Variant (`WorkspaceDefaultsSection`): a module-level STRING sentinel (`NO_DEFAULT = '__default'` - cannot collide with entity enums where a numeric sentinel cannot be ruled out), listed as the first REAL option, STORED in the draft, mapped to `null` only in the single `draftToPatch`-style serialization helper; type the options `SelectOption<FacetValue | typeof NO_DEFAULT>[]` so `any` stays out. A MultiSelect needs no fake "no preference" option: empty selection IS no preference (serializes to `null`) and a sentinel row inside a toggle-list would be selectable alongside real values - interpolate the page's own "all" wording into the placeholder instead, and make the dirty check normalize `null`/`[]` equal on both sides so a stored explicit-empty never reads dirty.

- **A wrapper composing a committed-value control adds synthetic slots through a wrapper-intercepted sentinel - the committed value stays real.** An extra "Other..." slot on a radiogroup composed over SegmentedControl: a module-level UPPER_SNAKE string sentinel as the option's value, intercepted in the wrapper's `handleChange` BEFORE the caller's `onChange` ever sees it (the sentinel maps to the secondary flow, e.g. opening a hidden calendar); the committed value stays a real value (an ISO date), so the composed control's `opt.value === value` selected-marking can never light the sentinel. A picked custom value takes over the slot (its own value becomes the option's value, selected-marking comes free from the composed control), reverting to the derived label when the value equals one of the fixed options. Option values that mean "today"/"yesterday" re-derive at render from `new Date()` plus local Date arithmetic and `toIsoDate` - never module scope (frozen at load, stale across a day rollover) and never `toISOString()` (UTC-shifted date near midnight). Exemplar: `common/DateQuickPick.tsx`.

- **External data seeds form fields through the canonical reference list.** A parsed or imported value (a receipt's currency code) seeds the field by matching it against the enabled-currencies list - the list's casing is canonical, never the raw parse - and an enabled parsed code seeds the own-currency field even when no account matches it (the traveling-cash case); a later account pick then locks the same code. Wire-side prefill ids resolve the same way: membership checks run against the LOADED option lists (`categories.find`, `accounts.some`), never raw id comparison - the loaded list is the only source of truth for what a Select can show, and archived or other-budget entries silently drop out of it. Exemplars: `useTransactionForm`'s receipt fill and its last-used prefill.

- **Breadcrumbs name the PARENT entity, never the page's own subject; non-navigation context is a muted line under the header, never a breadcrumb.** The breadcrumb is a navigation path one level up: the budget periods page's carries the budget name, the budget detail page's carries "Budgets". Page context that is not a navigation path (the workspace name on the members page) stays its own muted subtitle line under the header. Exemplars: `PageHeader`'s `breadcrumb`/`backTo` consumers (`BudgetDetailPage`, `BudgetPeriodsPage`) vs `WorkspaceMembersPage`'s subtitle.

- **Nav rows whose destination carries search params style active state through a no-argument NavLink `className` callback reading the live location.** NavLink's own `isActive` matches pathname only, so destructuring it on a search-param destination lights every same-pathname row together (every `/transactions?...` bookmark at once). The callback ignores NavLink's argument and closes over the live location with a helper comparing pathname AND every captured param (`bookmarkIsActive` in `utils/bookmarks.ts`); NavLink's `isActive` is destructured ONLY on plain-destination rows (the sidebar's Manage row; the More-sheet Manage row takes plain `moreRowClass`). Known accepted limitation: NavLink still auto-sets `aria-current="page"` off its own pathname matching, so same-pathname siblings can carry aria-current simultaneously while the visual state is correct. Companion rule for the surface hosting such rows: a prev-path render-adjust latch's KEY must cover every location segment same-surface navigation can change - a pathname-only latch never observes same-pathname-different-search navigation (switching filter views from the More sheet), leaving the sheet open over the re-filtered page. Track pathname+search, and rename the latch (`prevPathname` -> `prevPath`) when the tracked key widens - the old name would lie to the next reader.

**Multi-route tabs are the same idiom with a prefix list:** a tab standing for several routes (Activity covering `/transactions`, `/planned`, `/transfers`) takes an optional `activeFor?: readonly string[]` consumed through the no-argument callback - `activeFor.some((prefix) => location.pathname.startsWith(prefix))` - because NavLink matches only its own `to` and would go dark on two of the three routes; plain tabs in the same row KEEP the destructured `{ isActive }` callback so single-route prefix matching (Budgets lit on `/budgets/:id`) is unchanged. Exemplar: `Tab` in `layout/BottomNav.tsx`, reused by the sidebar's Activity item. NavLink still sets `aria-current` from its own match only - visually active WITHOUT aria-current on the covered routes is the same accepted limitation as bookmark rows; do not patch it with a manual attribute. Two boundary rules: sibling sub-rows that all share ONE destination until per-route URLs exist are plain `Link`s, never NavLink (a NavLink would set aria-current on every sibling at once on the shared route - exemplar: the sidebar's account/budget sub-rows); and a tab strip whose members each own a DISTINCT pathname is exempt from the no-argument rule - destructuring `isActive` is correct there, because pathname match is the right active signal and NavLink sets `aria-current="page"` for free (exemplar: `layout/ActivityTabs.tsx`).

## Deduplication Seams

Choose the extraction mechanism by WHAT the duplication is:

- **More than half the duplicated surface is JSX → a shared self-contained component**, not a hook (hooks can't dedup JSX). It reads ambient state - filter values from `useSearchParams()`, reference data from the `useDomain` hooks - instead of taking props, so call sites collapse to one element. `CurrencySetField` (in `components/accounts/AccountFormModal.tsx`) is the exemplar - it reads enabled currencies from the `useDomain` hooks instead of taking them as props; page-specific fields stay in the page. When a legitimate call site exists BEFORE the ambient data does (a pre-workspace form - no enabled-currencies query exists yet), add an explicit-prop override instead of forking the component: `const ambient = useEnabledCurrencies(); const currencies = currenciesProp ?? ambient` - the ambient hook still runs unconditionally above every branch (hooks-ordering corollary), the pre-workspace site passes the explicit prop, and every other site passes nothing. Exemplar: `CurrencySetField`. When the ambient query itself would be doomed at that site (an authenticated GET fired pre-auth), give the hook an optional `enabled = true` param and pass the override condition - `useEnabledCurrencies(currenciesProp === undefined)` - so the query never fires at prop-fed sites while every existing caller and the unconditional hook CALL stay untouched. When a spec pins a prop value "because the precedent uses it", verify the precedent in the code actually does - spec claims about code are code claims (a "compact mode, like workspace creation" claim hid that the precedent actually passes full mode).
- **Identical state machine with one behavioral delta → a hook with the delta injected as a callback.** `hooks/useListboxPanel.ts` + `common/listboxParts.tsx` (Select/MultiSelect): the keyboard/open/highlight machinery lives once; `onActivate` carries pick-and-closes vs toggles-and-stays. Extracted hooks keep host-surface state OUT — closing the host dropdown/sheet is the caller's `onDone` callback, run on success only, never on failure.
- **A third consumer needing different presentation is a sibling, not a fork and not a hook change.** `PeriodPicker` reuses `useListboxPanel` + `listboxTriggerBaseClass` untouched; every presentation deviation (panel width, year groups, two-line mobile rows, CURRENT chip, hover semantics) lives in the component. Changing the shared hook/parts to serve one consumer silently changes Select/MultiSelect behavior you never set out to touch.
- **A presentational extraction keeps derivations and surface gates in the PAGE.** The extracted component self-translates (`useTranslation('<ns>')` inside), so the seam passes data plus one handler and no i18n threading, while every derivation and the render gate that scopes the component to one surface stay page-side - pushing the gate into the component would need a third prop just to tell it which surface it is on. Exemplar: `common/MonthStepper.tsx` (self-translates the month-nav aria; the label derivation via `stepperRangeLabel` and the shift-wiring decision (`onShift` passed exactly when `isCalendarMonth(effective)`) live in the Activity pages).
- **Interleaved non-option rows must not break the hook's flat option indexing.** When groups carry labels/dividers between options, thread the flat index through the grouping: build groups with `periods.reduce` whose third argument IS the hook's option index (items carry `{ period, index }`), with `optionId`/highlight/`onActivate` keyed on `item.index` - never a group-local counter. aria-hidden label divs stay skipped by keyboard nav precisely because the hook counts options only.
- **Scroll-to-selected inside a popover is manual `panel.scrollTop` centering math, never `element.scrollIntoView`** - `scrollIntoView` scrolls every scrollable ancestor and drags the page under the popover.
- **A non-selectable action row inside a listbox ("View all periods") is a pseudo-option in the hook's option space.** A bare `<button>` child of the listbox sits outside `aria-activedescendant`, and End/type-ahead/Enter skip it. Recipe (`PeriodPicker`'s view-all row): append `{ value: SENTINEL, label }` LAST to the hook's options with a numeric sentinel that cannot collide with real values (`-1`, impossible for a DB primary key, keeps `ListboxOption<number>` honest); branch in `activateIndex` on the sentinel (fire the navigation callback, `closePanel`, return) - activation is not selection, so no `onChange` path; render `role="option"` + `aria-selected={false}` (an action is never the selected value), with `id={optionId(index)}` + `tabIndex={-1}` on the desktop panel (the trigger owns focus) and no `id` in the mobile sheet (row parity). The scroll-to-selected `querySelector('[aria-selected="true"]')` still finds the real selection because the pseudo-option is always `aria-selected={false}`. Any windowing around the options (a `limit` cap) is pure per-render derivation clamped so the selection always lands inside the window - never state, which would need re-sync effects; an `effectiveLimit` alias (null when the list already fits) lets TypeScript narrow inside the branches.
- **An input-anchored combobox (text-input autocomplete) is a SIBLING of `useListboxPanel`, not a consumer.** The hook's contract is a trigger button + panel pair; grafting a text input onto its trigger machinery would fork it for one consumer. Recipe (description autocomplete in `transactions/TransactionFormFields.tsx`): the panel opens on `onFocus` - "true while interacting" needs an explicit open trigger or it can never appear from false; blur closes after a ~150ms delay, because a suggestion-row click blurs the input first and a synchronous close would unmount the row before the click lands; Enter acceptance is bounds-checked (`0 <= highlighted < suggestions.length`) - a mid-flight refetch can shrink the list under a highlight set against the previous render's rows; typing resets the highlight to -1 so Enter submits the typed text (only an explicit arrow press arms acceptance); Escape is consumed (`preventDefault` + `stopPropagation`, gated on the panel being open) so the surrounding Modal/BottomSheet stays open; the plain input carries conditional `aria-controls`/`aria-activedescendant` via `: undefined`, rows are `role="option"` + `tabIndex={-1}` with useId-derived ids, and row touch floors interpolate `${controlHeightClass}`.
- **Logic- or field-identical exports → alias, keep BOTH names** (`const canResetPasswordFor = canEditMember;`): an alias makes drift structurally impossible while every existing call site stays valid. Grep all consumers first to confirm nothing depends on the copies being distinct; deleting a name is a call-site migration, not a cleanup side effect. The inverse: when a new action's backend gate is verbatim identical to an existing predicate's (reset-2fa shares reset-password's role check), reuse the existing predicate verbatim rather than minting a second alias - a new name adds drift surface and saves nothing.
- **Look-alike helpers that encode DIFFERENT thresholds stay separate, each docblock naming its surface.** Two status-color helpers on one page (a card-list fill keyed to category-level over/75% thresholds, a currency strip's burn scale at 75/95) are NOT duplication to unify: a shared severity helper silently applies one surface's thresholds to the other, and the wrong-label bug is invisible until a row lands between the two thresholds. Unify only provably identical logic (the alias rule above); scale-bearing siblings stay split with a keep-apart docblock stating which surface each belongs to, so nobody "helpfully" merges them later.
- **Copy at two consumers, extract at the third.** When a task needs a sibling component's module-private helper (a 6-line chip, a 5-line predicate), copy it byte-equivalently into the new file with keep-in-sync comments on BOTH sides instead of extracting - a premature extraction churns a component outside the task's file set (exemplar: `PeriodCard`'s local `CurrentChip`/`temporalOf` copies from `PeriodPicker`). A third consumer is the extraction trigger: promote to a shared module then, moving every copy byte-equivalently. (A task's scope fence may leave the reciprocal keep-in-sync comment off the untouched sibling - editing an out-of-fence file just to add the comment exceeds the fence; the third-consumer extraction reconciles both copies.) A shared presentation-component extraction also UNIFIES i18n keys: one byte-identical label rendered at three sites through three keys in two namespaces becomes a prop-less self-translating component (`useTranslation('common')` inside) with a single common-ns key - the label can no longer drift per-surface, and future sites render `<ArchivedBadge />` with zero t() wiring; the three legacy keys leave via the key:find/key:rm gate in the same change.
- **A resource's data logic (queries + mutations + cache-key builders) lives in a domain hooks module, not a component and not a class-based service.** When a resource will plausibly serve more than one consumer (attachments feed tiles, a lightbox, future pages), extract its full data logic at the FIRST consumer into `hooks/useAttachments.ts` - the `hooks/useDomain.ts` pattern (see Shared domain hooks) applied per resource: exported key-builder functions (`transactionAttachmentsKey`, `attachmentBlobKey`) so any hook or component can invalidate precisely, one hook per operation, each mutation owning its cache invalidation internally. Pure non-hook helpers (`isImage`, `triggerBrowserDownload`) go in `utils/attachments.ts` beside `utils/errors.ts` / `utils/format.ts`. This is the carve-out to "copy at two, extract at three" above - that rule is for presentation helpers; reusable data logic is extracted immediately because component-inline data logic cannot be reused without a rewrite. Service classes are the wrong seam in React: hooks compose with TanStack Query caching and component lifecycle, and the axios client in `api/client.ts` stays the only HTTP seam.
- When extracting, copy behavior-critical blocks **byte-equivalent**: ASSEMBLE the new file by extracting the exact line ranges from `git show HEAD:<old>` and concatenating them with authored heredoc additions - never retype moved blocks. Byte-exactness is then a property of construction, and the mechanical gate (`diff` against git HEAD) verifies rather than hopes; a hand-retyped multi-hundred-line move is a diff-noise generator, and transcription silently "fixes" pre-existing em dashes in moved comments that the byte-equivalence gate exists to catch. Never "improve" during a move; a future fix should diff against exactly what shipped. **Promoting a module-private helper to a shared module adds the `export ` keyword - the ONE sanctioned divergence** (unexported names fail the new import site's build), and byte-equivalence is verified with that prefix normalized away: strip `export ` off the moved declarations in the new file (`sed 's/^export function /function /'`) and diff the moved line ranges against `git show HEAD:<old>` - an empty diff proves docblocks and bodies unchanged. Without the recorded resolution, a future extraction either "fixes" the gate by leaving the helpers unexported (dead code, build break) or re-derives the whole argument from scratch. A whole-file rewrite of a hook module gets the same diff-against-HEAD check for accidentally DROPPED exports BEFORE probing: a rewrite that omits an export surfaces first as a runtime import error in the probe harness - the rewritten file's own lint stays green, and only a consumer build catches it - where the diff catches it in minutes.
- Shared row/shape normalization between sibling components lives in `utils/` behind a deliberately **structural param type** (`RowLike` in `utils/transactionItems.ts` — four string fields) so each component's local row type satisfies it without component-to-component type imports. URL-param readers (`intParam`/`intListParam`/`amountParam`/`createUpdateParams`) live in `utils/params.ts` — list pages import them instead of re-declaring. Object-literal API modules (`authApi`, `legalApi`) are `this`-less arrow functions — safe as bare `queryFn:` references and as stable module-level fetcher props for shared page components.

## Variant Props on Shared Components

When a shared component needs a new render variant that must NOT change existing call sites, add an opt-in boolean prop (default `false`) with an early-return render branch. Prefer this over a sibling component when the variant reuses most of the component's wiring (refs, formatters, context lookups) and differs only in presentation:

```tsx
interface Props {
  value: string
  onChange: (value: string) => void
  inline?: boolean  // opt-in, default false — existing call sites unaffected
}

export default function DatePicker({ value, onChange, inline = false }: Props) {
  const { calendarStartDay } = useUserPreferences()  // shared wiring
  const [isOpen, setIsOpen] = useState(false)
  // ...other shared hooks/helpers...

  if (inline) {
    return <DayPicker mode="single" ... />  // always-visible variant
  }
  return <input value={value} ... />  // default popup variant
}
```

**Hooks ordering corollary:** All hooks (`useState`, `useRef`, `useEffect`) and helper closures must stay ABOVE the early return — React forbids conditional hook calls. Place the early return immediately after the last `useEffect`. Hooks that are no-ops in the inactive variant are fine — do not "clean up" by moving the early return above the hooks.

## Controlled-Open Props on Popup Components

Making a component with internal open state controllable (DatePicker's additive `open?`/`onOpenChange?` pair) must stay invisible to uncontrolled callers:

```tsx
const isOpen = open !== undefined ? open : internalOpen
const setOpen = (next: boolean) => {
  if (open === undefined) setInternalOpen(next)
  onOpenChange?.(next)
}
```

- The inline ternary is load-bearing: an `isControlled` boolean const cannot narrow TypeScript at the use site.
- A document-level listener consuming the merged setter (the outside-mousedown close) reads it through a latest-ref (`const setOpenRef = useRef(setOpen); useEffect(() => { setOpenRef.current = setOpen })`, no deps array - the latest-ref idiom under Contexts): a per-render function in a `[]`-deps effect both breaks the compiler lint's stability proof (a plain function is not an exempt `useState` setter, so the empty deps stop being provably safe) and captures the mount-time closure - a controlled caller passing a fresh `onOpenChange` arrow per render would get a stale close path from the mount-time listener.
- Rename EVERY internal setter call site to the merged `setOpen` (a `setIsOpen` == 0 grep gate catches stragglers) - including dismissal funnels like the mobile sheet's `onClose`, or a sheet-dismiss stops reporting through `onOpenChange`.

Exemplar: DatePicker's controlled-open pair (consumer: DateQuickPick's hidden-trigger embed).

## Controlled-Override Seams on Form Hooks

Lifting single fields (amount, date) out of a form state machine - a page host rendering ONE shared amount/date row that feeds two form hooks - is the controlled-open idiom generalized to field values across a hook boundary. The hook stays the single source of truth per value; an optional `shared` seam per liftable field (`TransactionFormShared`) reconciles both directions, and the owning modal passes nothing so it is behaviorally unchanged by construction:

- **Internal writes report upward synchronously.** Rename ONLY the useState declaration's setter half (`setAmountState`), then define the merged const under the ORIGINAL name immediately after the state block, calling `shared?.onAmountChange(value)` after the state write - every internal call site (seeding, parse fill, resetForAnother, the returned object) resolves to the merged setter with zero further edits, and a byte-move extraction gate normalizes the rename away.
- **Explicit host values win downward via a value-compare render-adjust** on the hook's own state (skip when `shared === undefined` or the values already match) - loop-safe because each write lands on a value that disproves the guard, and StrictMode-idempotent for free.
- Carry the seam byte-identically on every hook of the family, so a future host can lift either form's rows without a second design. Exemplars: `hooks/useTransactionForm.ts` and `hooks/useTransferForm.ts` (consumer: `pages/NewTransactionPage.tsx`).
- **When a host takes over a concern, the child's duplicate machinery is gated off in the same change** - two owners of one concern double-fire with conflicting orderings. The `sharedFields` variant of the fields component keys error-display timing on the host's resettable `showAllErrors` latch and suppresses its submit-keyed focus effect (the host's focus tick owns focus). Exemplar: the `sharedFields`/`showAllErrors` props in `transactions/TransactionFormFields.tsx`.
- **When two seamed hooks session-seed during the SAME render pass, their upward reports append to ONE state queue and the LAST queued write wins - a host lifting a field re-asserts its seed BELOW every competing hook writer.** On a warm-cache mount (the external data already resolved), the page's copy seed and an always-mounted sibling hook's create-mode seeding both queue upward writes in one pass; the sibling's `setFromAmount('')` queues after the copy seed and the lifted amount lands empty. A lazy initializer alone loses the same race - the sibling's write still queues after it; the decisive piece is POSITION. The assert is a render-adjust placed below the last hook and every early return (its write is queued last and owns the queue), latched on the source OBJECT identity - the same trigger as the hook's own session re-seed - so typed edits, upward-reported parse fills, and the save-and-add-another reset are never re-applied. The latch initializes to null/sentinel, NEVER to the tracked value: initializing to the current source would suppress the mount-pass assert, which is exactly the pass the warm path needs. Exemplar: the copy-seed assert in `pages/NewTransactionPage.tsx` (`sharedAmount` lazy-seeded from `copySource`, `seededCopy` deliberately null-initialized). Needs NO assert in the contrast case: a repeat/copy seam whose seeding CLEARS the shared values (the transfer repeat zeroes the amount and re-dates) races an always-mounted sibling's create seeding that queues the SAME empty values - queue order is irrelevant because the competing writes are identical. The discriminator: assert only when the external seed writes a NON-empty value into a shared field, and state the reason in a comment at the gate so a later reader does not 'fix' the asymmetry. Exemplar pair in `pages/NewTransactionPage.tsx`: the transaction `?copy=` seam (non-empty seed, assert required) vs the `copy_transfer` repeat seam (clearing seed, none).

## Form Draft Persistence (localStorage)

Unsaved scalar form values on `/new` persist to localStorage behind `utils/formDraft.ts` - a module-closure controller, NOT a React ref or state mirror:

- **The controller is a plain module closure because the flush must serialize "latest values" from unmount cleanup.** `react-hooks/refs` (error) forbids ref writes during render and state dies with the component - the closure IS the store, updated only from user-action change handlers (debounced ~500ms writes plus an unmount-flush effect), so no effect ever reads React state to write the draft. Keys follow the app's `owlgarth_*` convention and scope per-user AND per-workspace (`owlgarth_formdraft_<userId>_<workspaceId>`): logout sweeps the user's keys before auth clears, and a workspace switch removes the old (user, workspace) draft from the switch handler's click-render closure, which holds the OLD workspace id by construction. Reads are 24h-gated with prune-on-read.
- **A generation guard closes the resurrection race.** Logout/switch remove the key directly, then `/new` unmounts and its cleanup calls `flush()` - without the guard the flush re-creates the draft the user just discarded and the next login restores it. External removal bumps a generation counter the flush checks; a `clear()`-initiated drop needs no bump (`dirty=false` already makes the flush a no-op).
- **Draft writes happen ONLY at user seams: wrap the hooks' RETURNED setters and patch the field handlers.** Internal machinery (seeding, `parse.onSuccess` fills, the prefill block, `resetForAnother`) keeps the raw setters - receipt-derived values and the post-save reset must never draft. Deliberately never drafted: the receipt File, parse state, line-item rows (absent from the draft-values type), and URL state.
- **Restore goes through SEEDING (the session render-adjust), never user-action handlers.** Restored values never mark `prefillTouched`, never draft themselves back, and land as the isDirty seed baseline - a restored-but-unedited form is correctly NOT dirty. Arrival adjusts carry explicit-choice guards: a draft carrying `accountId` (or either transfer end) made that pick EXPLICITLY, so the default re-derive must be suppressed or every cold mount re-picks over the restore; stale restored reference ids drop to null/derived, gated on the draft's presence so draft-free hosts keep today's behavior. The `draft`/`reseedNonce` hook options default to null/0 - a host passing neither gets identical behavior and byte-identical sessionKeys by construction (the nonce suffixes the session discriminator only when non-zero).
- **Sparse-draft reads test `dv?.field !== undefined`, never `??`.** Present-null is the ONLY representation of an explicit "no pick": `null ?? x` returns `x` and silently re-picks an account the user deliberately cleared.
- **Competing URL seeds win outright - the draft goes dormant under them.** Under `?copy=`/`?copy_transfer=` there is no key, no controller, no restore, no write, no delete: a copy draft would fight the copy-source seed, and query params (`type`, `account`, `copy`) always beat the draft.
- **A scoping key that resolves asynchronously must gate the seeding `open`.** `user` is guaranteed at mount (ProtectedRoute) but `workspace` resolves via query - without gating `open` on `workspace !== null`, the hooks seed on render 1 before the draft key exists and the restore can never land; with the gate, the active key, the memos, and the hooks' `open` all flip in the SAME render, so the first seeding pass holds the draft. Exemplars: `utils/formDraft.ts`, the draft block in `pages/NewTransactionPage.tsx`, the `draft`-threaded seeding in `hooks/useTransactionForm.ts`/`hooks/useTransferForm.ts`.

## Multi-Step UI Flows

Use a union-typed state machine with conditional rendering for multi-step flows (setup → verify → confirm):

```typescript
type SectionState = 'idle' | 'setup' | 'showing_codes' | 'disabling'
const [state, setState] = useState<SectionState>('idle')

if (state === 'showing_codes') return <RecoveryCodesDisplay ... />
if (state === 'setup' && setupData) return <SetupForm ... />

const mutation = useMutation({
  mutationFn: api.verifySetup,
  onSuccess: (data) => {
    setState('showing_codes')
    queryClient.invalidateQueries({ queryKey: ['status'] })
  },
})
```

**A long in-flight submit swaps the whole card body for a staged progress panel** - branch on `isSubmitting` (Register's "Setting up your workspace" checklist), never offer only a disabled button: a 2-5s synchronous request with no visible progress reads as a frozen UI. The swap never unmounts the component, so all form state stays alive and a failed submit restores the typed values for free, and the derived stage list is frozen mid-flight because the input that could change it (the sample-data checkbox feeding its conditional) is unmounted by the swap. Stages are pure client-side timers identical on every error path - backend state never leaks through stage count or timing - and the advance is capped (`Math.min(s + 1, setupStages.length - 1)`) so the terminal step stays "active" forever: it must never flip to complete while the request is still hanging. Exemplar: `pages/Register.tsx`.

## Auth Response Error Guard

Every auth function expecting an `access_token` must have an `else` branch showing an error toast when the token is missing — never silently do nothing on an unexpected response:

```typescript
if (response.access_token) {
  // ... existing success logic
} else {
  toast.error(t('errors.unexpectedResponse'))
  return
}
```

The toast message is UI text - the component has `useTranslation('auth')` in scope, and the key lives in the owning `auth` namespace.

## Stateful Component Preservation with CSS `hidden`

When a component holds important transient state (e.g., recovery codes that cannot be re-displayed), use CSS `hidden` to keep it mounted when switching tabs — conditional rendering unmounts it and loses state:

```tsx
// Good — stays mounted, preserving internal state
<div className={activeTab === 'security' ? '' : 'hidden'}>
  <TwoFactorSection />
</div>
```

Only apply this where state loss is problematic — other tabs can continue using conditional rendering.

**Focus return across a hidden-class swap needs the previous level to stay MOUNTED and the focus call to wait for the re-show commit.** A level-based surface (a sheet hub whose editor level replaces it) keeps the previous level mounted with the `hidden` CLASS while the next level is open, for two mechanical reasons: a conditional unmount clears the row refs to `null` (React drops refs on unmount, so the return-focus target is gone), and even with live refs a browser refuses `focus()` on an element inside a `display:none` subtree - calling focus from the close handler, while the hub is still hidden, is a silent no-op and focus lands on `<body>` instead. Recipe: store the target id in a pending-focus ref at close time and consume it in a DOM-only `useLayoutEffect` keyed on the visibility flip (ref read + `focus()` + ref clear, zero state writes) - the layout effect runs after the commit that re-shows the level, when focus can land. Exemplar: the hub + editor level of `components/filters/FilterSheet.tsx` (`pendingFocusRef`).

## API Error Message Extraction

Every API-error toast or handler extracts its message with
`getApiErrorMessage(error, t('uploadFailed'))` from `utils/errors.ts` - it wraps
`axios.isAxiosError` and reads `response.data.detail`, returning the fallback when either
is missing. Ninja 422 details arrive as an array of field-error objects; the helper joins
their (server-translated) msg strings into one '; '-separated line and falls back when the
array yields nothing - call sites never hand-roll array handling:

```typescript
onError: (error) => toast.error(getApiErrorMessage(error, t('uploadFailed')))
```

Never hand-roll `(error as { response?: { data?: { detail?: string } } })` casts or
`error: any` at call sites — the helper is the single seam, and it keeps the error
parameter typed as `unknown`.

**Blob responses never have a parsed body.** On `responseType: 'blob'` requests the
error response body arrives as a Blob (axios never parses it as JSON), so
`getApiErrorMessage`'s `response.data.detail` read always finds nothing. Branch on
the HTTP status first (`axios.isAxiosError(error)` + `error.response?.status`, e.g.
404 -> "no longer available", 503 -> "storage unavailable"), then fall through to
the generic helper. Exemplar: `attachmentDownloadErrorMessage` in
`utils/attachments.ts`.

**A shared blob-export helper parses the error body for a `detail` and owns every toast.**
Blob bodies can still be READ: `await error.response.data.text()` then `JSON.parse` recovers
the Ninja `{ detail: string }` shape when present, falling back to status-aware messages -
the parsing sibling of the status-first branch above. The helper shape: `runBlobExport(fetchBlob, options)`
(`utils/blobExport.ts`) takes every user-facing string PRE-TRANSLATED from the caller (utils
own no translation keys, so callers keep their own namespaces and zero i18n edits ship),
owns the optional loading toast, the success toast, and the error toast, and NEVER throws -
callers keep only their `isExporting` state with plain set-before/set-after around the call,
no try/finally. It honors `triggerBrowserDownload`'s revoke-free contract by revoking the URL
it mints itself.

## Avoid Duplicate Toasts

Before adding error toasts in a catch block, check whether the called function already shows toasts (e.g., `AuthContext.login()` shows `toast.error()` and re-throws). If so, the catch only prevents unhandled rejection; an empty catch needs a comment for ESLint's `no-empty`:

```typescript
} catch {
  // Error already displayed by AuthContext
} finally {
  setIsSubmitting(false);
}
```

When a catch block exists only to swallow the error (no inspection), use the optional catch binding `catch { ... }` rather than `catch (e)`/`catch (_e)` — no unused binding, satisfies `@typescript-eslint/no-unused-vars` without underscore noise.

**No success toast when the visual change IS the feedback.** A mutation whose effect is immediately visible on screen (an optimistic reorder re-rendering the list) skips the success toast entirely - three rapid clicks must not stack toasts. Errors still get exactly one `toast.error(getApiErrorMessage(...))`; only the success channel is conditionally silent.

## Token Storage

Access and refresh tokens are stored separately in `localStorage` (`owlgarth_token`, `owlgarth_refresh_token`). Helpers in `api/client.ts`: `setRefreshToken`, `getRefreshToken`, `clearAuthToken` (clears both tokens and the Authorization header).

All auth flows receiving token pairs (`login`, `register`, `verify2FA`) must store both tokens:

```typescript
if (response.access_token) {
  setAuthToken(response.access_token);
  if (response.refresh_token) {
    setRefreshToken(response.refresh_token);
  }
}
```

The `if (response.refresh_token)` guard matches the optional `refresh_token` field on `Token`, for endpoints that only return access tokens.

## 401 Interceptor with Token Refresh

The Axios response interceptor in `api/client.ts` uses a queue-based pattern:

1. On 401, check for a refresh token. If none, clear tokens and redirect to `/login`.
2. If a refresh is in progress (`isRefreshing`), queue the failed request in `failedQueue` and replay after refresh succeeds.
3. On refresh success, store the new token pair, replay queued requests, retry the original.
4. On refresh failure, clear both tokens, reject queued requests, redirect to `/login`.
5. Auth routes (`/login`, `/register`) are excluded from redirect to avoid loops.

`authApi.refresh` sends `{ headers: { Authorization: '' } }` to avoid sending the expired access token on the refresh request itself.

Credential endpoints (`login`, `register`, `verify2FA`, `refresh`) mark their requests `_skipAuthRefresh: true` — a wrong-credential 401 must reject immediately instead of entering the refresh path (a stale refresh token in storage would attempt a silent rotation and redirect to `/login`, swallowing the login form's own error toast). New credential-style endpoints (token exchange, magic-link consume) set the flag too.

**Post-Sign-In Return Navigation (router state):** an unauthenticated redirect from `ProtectedRoute` carries the protected location through router STATE (`state={{ from: location }}`), never a `?next=` query param - state is unbookmarkable/unshareable, so there is no open-redirect surface to guard. The sign-in page narrows it with a module-level helper (typeof-guarded, `'/'`-prefixed, rejecting protocol-relative `//` - RR7 types `location.state` as `any`) and its ALREADY-AUTHENTICATED guard performs the single post-auth navigation (`to={from ?? '/'} replace`) for both the login and 2FA success paths: a `setUser` re-render flips `isAuthenticated` and the guard fires. When a context's success path and a page's guard both navigate, delete the context's navigation in the same change - two owners of one concern double-fire with conflicting orderings (AuthContext's `navigate('/')` after `setUser` either clobbers or preempts the return navigation) - and funnel every success path through the one navigation owner. Accepted trade-off: post-sign-in navigation is `replace`, so Back no longer returns to the signed-out `/login` entry. Exemplars: `ProtectedRoute.tsx`'s redirect state, `returnToFromState` in `pages/Login.tsx`.

## Token-Based Verification Pages

```tsx
type State = 'loading' | 'success' | 'error'

export default function VerifyPage() {
  const [searchParams] = useSearchParams()
  const [state, setState] = useState<State>('loading')

  useEffect(() => {
    const verify = async () => {
      const token = searchParams.get('token')
      if (!token) {
        setState('error')
        return
      }
      try {
        await authApi.verify(token)
        setState('success')
      } catch {
        setState('error')
      }
    }
    verify()
  }, [searchParams])
}
```

- Always handle the missing-token case (`if (!token)` → error state)
- Public verification pages go outside `ProtectedRoute`; authenticated pages inside it
- Public token pages must guard any authenticated follow-up call (e.g. `getCurrentUser()` refresh) with `if (getAuthToken())` — otherwise the 401 interceptor redirects anonymous visitors to `/login`, hiding the page's own success/error state
- Success states offer a navigation link; error states offer retry/resend
- Use a named `async` function inside `useEffect` with `try/catch/await` — no `.then()` chains
- Never show the same success state in both `try` and `catch` — add a distinct error state with a recovery path

## Dashboard Widget Component Pattern

Filter-scoped widgets (e.g. account- or budget-scoped) follow this structure:

```tsx
interface Props {
  budgetId: number | null
}

export default function MyWidget({ budgetId }: Props) {
  const { data, isLoading } = useQuery({
    queryKey: ['my-data', budgetId],
    queryFn: async () => {
      if (!budgetId) return null
      return myApi.getData({ budget_id: budgetId })
    },
    enabled: !!budgetId,
  })

  if (!budgetId) return null
  const items = data?.items ?? []

  return (
    <div className="border border-border rounded-sm bg-surface p-4">
      <h3 className="text-sm font-medium text-text mb-3">Widget Title</h3>
      {isLoading ? (
        <div className="space-y-3">
          {[0, 1, 2].map((i) => (
            <div key={i} className="h-4 bg-surface-muted rounded-sm animate-pulse" />
          ))}
        </div>
      ) : items.length === 0 ? (
        <p className="text-sm text-text-muted">No data this period.</p>
      ) : (
        <div>{/* Render items */}</div>
      )}
      <Link to="/detail-page" className="inline-block mt-3 text-sm text-primary hover:text-primary-hover">
        View Details →
      </Link>
    </div>
  )
}
```

**Key conventions:** early-return `null` when `budgetId` is null (no skeleton); `enabled: !!budgetId` on `useQuery`; three rendering states (loading skeleton / empty message / data); always a `<Link>` to the detail page; skeletons use `bg-surface-muted rounded-sm animate-pulse`; container uses `border border-border rounded-sm bg-surface p-4`.

**A row cap below the page-size floor requests the FLOOR and slices client-side.** Backend list endpoints silently coerce any non-allowlisted `page_size` to 25 (`ALLOWED_PAGE_SIZES = [10, 25, 50, 100, 200]`, `core/schemas/pagination.py`), so a widget pinning `page_size: 3` actually receives a full 25-row page and renders every row it gets - no error anywhere. A widget capping at N rows where N is below the floor requests `PAGE_SIZE_OPTIONS[0]` (the synced mirror) and `.slice(0, N)` at render; never send a sub-floor page_size expecting the server to cap. (Backend-side authoring of the caps: `django-backend`'s Pagination Param Caps.)

**Enabled-chained queries gate loading on data presence, not `isLoading`.** When a query's `enabled` chains on another query's data (currentPeriod → history → summary), a disabled query reports `isLoading: false` — a bare `isLoading` gate flashes the empty-state message during the waiting window. Gate skeletons on `!!id && !data`, with a comment at the gate explaining the disabled window. Same class of race for defaults: when a fast list query and an authoritative query compete to supply a default value, gate the list fallback on the authoritative query's `isSuccess`. For switch-flash: paginated list queries get `placeholderData: keepPreviousData` (with placeholder data, `isLoading` is true only on first load, so the existing skeleton branch needs no change); non-paginated queries that should keep showing current data across id changes use `placeholderData: (prev) => prev`.

**Enabled flags gate on data PRESENCE, not optional-field inequality.** `budget?.cadence !== 'custom'` is TRUE while `budget` is still undefined - the query fires a doomed GET on every visit; write `enabled: budget != null && budget.cadence !== 'custom'`. The same gate is a data-INTEGRITY guard for write affordances, not just a doomed-request saver: a batch-Save button rendered during a summary refetch race snapshots the placeholder values (`planned: '0'` for every row mid-race), all rows read changed, and an immediate Save ZEROES real amounts - render the affordance only while the data it snapshots is loaded (`!summaryLoading`), so it is absent exactly while the surface renders skeletons. Same race class for foreign-id arguments: a derived-membership gate (`const summaryPeriodId = allPeriods.some((p) => p.id === periodId) ? periodId : undefined`, feeding the queryKey) keeps a stale previous-entity id - the pre-reset render of budget-to-budget nav - and garbage `?period=` seeds off the server, killing the transient `budgetSummary(B, A_period)` 404. The gate is a derived const (zero set-state-in-effect cost) and must sit below the memo it reads (TDZ).

**Gate at the MOUNT when the hook has no `enabled` flag to thread.** A surface that renders workspace-less (the sidebar) consuming workspace-scoped hooks whose queries take no `enabled` param (`useBudgets`, the balances query) extracts the whole region into a child component rendered only under the workspace-truthy branch (`{workspace ? <SidebarNav /> : null}`) - a workspace-less mount can only ever produce rejected requests, so the GETs never fire without a workspace. This generalizes `useBookmarks(workspace != null)` from a single hook to a subtree; a side benefit is that the subtree's queries ride the same family keys as their first consumers (`['current-balances', false]`), so existing invalidation sites refresh them with zero new wiring. Exemplar: `SidebarNav` in `layout/Sidebar.tsx`.

**"Known/loaded" gates count terminal error as known.** A boolean gate derived from a query and feeding a default-selection or reconcile branch must arm on `isSuccess || isError`, not success alone: with `retry: false`, ONE terminal request failure (backend `--reload` mid-visit, network blip) leaves a success-only gate closed for the whole mount, killing every auto-pick branch behind it while healthy list data renders behind the placeholder (this exact shape stranded budget opening with no period selected, and every naive probe passed because the defect needs a failed request). Exemplar: `BudgetDetailPage`'s `currentPeriodKnown = budget?.cadence === 'custom' || currentPeriodLoaded || currentPeriodError`. Decide a gate's error arm deliberately: a "known" gate counts error as known (no answer is coming - proceed with what is there), while a fallback-deferral gate does not fire its fallback on error (it must not preempt the authoritative answer); when touching a query's error handling, check every gate consumer for which shape it is.

**Shared domain hooks:** Widgets read workspace data through the hooks in
`hooks/useDomain.ts` (`useAccounts`, `useBudgets`, `useEnabledCurrencies`,
`useMultiCurrency`, `useExtractionConfig` (returns `{ enabled, reachable }` — extraction UI
keys polling cadence on `reachable`), `useExtractionEnabled`) rather than threading props.
Periods are per-budget, so period selection is local state on the Budget detail page — there
is no global period context.

## State Refresh After Mutations

After operations that change server-side state (email change, profile update), fetch the full updated object rather than patching local state partially:

```tsx
// Good: fetch full state from server
const updatedUser = await authApi.getCurrentUser()
updateUser(updatedUser)
```

**Workspace cache invalidation is removal-by-predicate with a keep-set — never an invalidation list.** Workspace-scoped query keys don't encode the workspace id (the API serves the *current* workspace), so on workspace switch/create/delete `WorkspaceContext` runs `queryClient.removeQueries({ predicate })` keeping only the user/deployment-scoped keys in its `userScopedQueryKeys` set. Drift asymmetry is the reasoning: a drop-list that forgets a new query ships stale cross-workspace data (that IS the bug); a keep-set that forgets a new user-scoped key costs one harmless extra refetch (the safe direction). New workspace-scoped queries need zero action; new USER-scoped query keys must be added to `userScopedQueryKeys`.

- Use `removeQueries` (query cache only), not `clear()`, inside `useMutation.onSuccess` — `clear()` also empties the mutation cache and can evict the in-flight mutation's own entry. `clear()` is reserved for auth identity changes (login/logout), where a full wipe is wanted.
- `refetch()` from `useQuery` bypasses the query's `enabled` flag — guard manual refetches on the same condition `enabled` uses whenever the queryFn dereferences possibly-null data, or it throws on null.
- react-query v5 has no query-level `onError` — query failure UX renders inline (`isError || !data` early-return), not via a toast. A manual `useEffect` + `useState` fetch should become a `useQuery` (caching, retries, dedup at zero extra code). The inline early-return is for data-carrying queries; an optional-enhancement query - one that enriches a form but does not gate it - degrades silently instead: render the defaults over `data === undefined`, no error UI, and fail fast without burning the app-wide retry budget (`retry: (failureCount) => failureCount < 1` preserves `retry: 1` for genuinely transient failures). This is the shape for pre-workspace queries against workspace-scoped auth (the currency catalog inside workspace creation 400s while no current workspace exists): an errored query is stale, so the next open refetches and the degrade self-heals once the precondition exists. Exemplar: `CreateWorkspaceForm`'s catalog query.
- **Key a derived query INSIDE the list-family prefix its mutations invalidate.** A derived query over the same rows a list shows (a totals strip, autocomplete suggestions, a fetched edit prefill) is keyed `['transactions', 'totals', ...]`, `['transactions', 'frequent-descriptions', type]`, `['transfers', 'detail', id]` - nested under the family prefix, never a sibling key like `['transaction-totals']`. The family's create/edit/delete mutations often live in other files and invalidate only the family prefix; TanStack prefix matching then refetches the derived query through those existing invalidation calls with zero out-of-scope edits, where a sibling key goes stale after every create/edit. The exception is cardinality-keyed ephemeral queries: a per-keystroke palette search (`['palette-transactions', q]`) mints a new cache entry per committed query string, so family nesting would replay one request per query string ever typed on every invalidation - keep those sibling/isolated. The partition question: does the UI re-read this data (nest under the family) or mint a new key per interaction (isolate)? Derived queries also MIRROR the list's filters: every list filter param threads into a derived query over the same rows in the same commit - the queryKey entry (e.g. `currencyFilter.join(',')`) AND the queryFn param, both mirroring the list query's expressions and ordering byte-identically. The key entry is the load-bearing half: without it, toggling the filter refetches the list but serves the strip from a stale cache entry, invisible to any backend test because both requests are individually valid. Exemplar: the planned-totals strip in `Planned.tsx`. An editable entity's DETAIL query additionally reuses the exact cache entry of an existing consumer rather than minting a sibling detail family - `useTransaction(id)` keys `['transactions', 'detail', id]`, the same entry `/new`'s copy query reads - so the family-wide invalidations refresh the record with zero new wiring and two observers of one entry stay consistent by construction. Differently-scoped entries over the same data get distinguishing key members: a date-scoped period query carries the transaction date in its key so it can never be served by (or pollute) the dateless page entry. Exemplar: `hooks/useDomain.ts`.

- **Await the refetch before clearing a selection that an effect re-derives.** When a null-picker effect re-selects from a list (`setPeriodId(periods[0].id)` whenever the selection is null), a delete mutation must `await` the list's `invalidateQueries` refetch BEFORE clearing the selected id - clearing against a stale cache lets the effect re-select the just-deleted id, and a ghost id whose lookup returns null renders a dead page. Exemplar: `BudgetDetailPage`'s `deletePeriod` awaits the `['periods', budgetId]` refetch before `setPeriodId(null)`; a fire-and-forget invalidation plus an immediate clear reintroduces the race. Invalidation ownership follows mutation ownership: the form modal's own `onSuccess` invalidates its add/edit (`PeriodFormModal`); a page-level delete mutation invalidates in the page.
- **Cross-tab staleness is a different bug class from invalidation.** Each browser tab keeps its own query cache, so a mutation's invalidation never reaches other tabs - and `refetchOnWindowFocus` defaults to stale-only while `api/queryClient.ts` sets a 5-minute `staleTime` app-wide, so focusing the observing tab refetches nothing until that expires; an entry deleted in another tab lingers in this tab's dropdown and selecting it 404s. Fix class: `refetchOnWindowFocus: 'always'` on the cheap list GETs that feed dropdowns - the `useDomain.ts` list hooks (`useAccounts`, `useBudgets`, `useEnabledCurrencies`, `useWorkspaceCategories`) and page-local lists such as `BudgetDetailPage`'s `['periods', budgetId]` query - leaving `staleTime` in force everywhere else for navigation snappiness. Probe by bug class: same-tab invalidation via SPA-link navigation (no reload), cross-tab staleness via two real tabs plus a focus event (`bringToFront()`); never `page.goto()` - a full load re-creates the query cache and masks both.

- **An optimistic reorder goes `onMutate` + `queryClient.setQueryData`, with a narrower invalidation than set-changing writes.** `onMutate` fires synchronously in the click tick, so swapping two rows in the cached array renders the move instantly with no local state and no effect - structurally lint-quiet. Capture the render-scoped previous array for `onError` rollback, and disable the move controls on `isPending` so a second move cannot interleave. Set-preserving mutations own a NARROWER invalidation internally: a reorder invalidates only `['enabled-currencies']`, never `['currency-catalog']` - the set and the catalog are unchanged, only the order moved; set-changing mutations (enable/disable/custom) keep the both-keys pattern. Exemplar: `CurrenciesSettingsSection`'s reorder.

## Reading State in Mutation Callbacks and Effects

**TDZ-safe reads in `useMutation.onSuccess`:** A mutation callback defined before a derived `const` in source order cannot reference that const — JavaScript's temporal dead zone throws `ReferenceError` at call time, and **`tsc` does NOT catch this** (TDZ is a runtime semantic, not a type error; a clean build does not prove TDZ safety). When `onSuccess` needs state that is also captured by a later-declared const, read the source state directly:

```tsx
// `account` is declared AFTER `parse` in source order — referencing it here throws at runtime
const parse = useMutation({
  onSuccess: () => {
    const current = accounts.find((a) => a.id === accountId)?.currency_code  // read source state, not `account`
    if (current !== parsed.currency) { ... }
  },
})
const account = accounts.find((a) => a.id === accountId)
```

**Date-dependent helpers are module-level functions** (`nearestPeriod` and `nextDayIso` in `pages/BudgetDetailPage.tsx`): a component-level `const todayIso = new Date().toISOString().slice(0, 10)` declared below the effect that consumes it is TDZ-poison, and hoisting it above does not help either - adding it to the effect's deps buys nothing across a day rollover. The helper takes the list as its argument and computes "today" itself.

**Stale-state-safe reads inside an effect that sets then branches:** When an effect calls `setState` and then needs to branch on the value being set, reading the state variable reflects the render that created the effect (the *previous* value), not the just-set value — React flushes state between effect runs, not mid-effect. Recompute the value locally instead of reading the state variable:

```tsx
useEffect(() => {
  const intended = accounts.length === 1 ? accounts[0].id : null
  setAccountId(intended)
  // branch on `intended`, NOT on `accountId` — accountId is still the previous open's value here
  if (intended !== parsedCurrency) { ... }
}, [accounts, ...])
```

**Guards inside closures created before an early return are NOT dead.** After `if (!x) { return }`, JSX guards on the narrowed `const` are dead (TS narrows; delete them). But the same guards inside handlers/closures declared BEFORE the return are live — the closure's `x` keeps its declared nullable type because the closure is created where `x` was still nullable, and `tsc` fails if you remove them. Check closure creation order, not just runtime reachability, before deleting "redundant" guards.

## State Changes in Event Handlers, Not Effects

The project lints `react-hooks/set-state-in-effect` at **error**: the historical 16-warning backlog was cleared (resets and prefills migrated to render-adjusts and event handlers, see below) and the temporary `'warn'` override retired by flipping to the preset's own default with a one-time end-state counts comment in `frontend/eslint.config.js` - an explicit `'error'` line documents the tripwire where a future reader looks, and deleting the override instead would lose that anchor. A new set-state-in-effect call fails the build outright. The remaining baseline was the `i18next/no-literal-string` false-positive floor, later taken to ZERO the same way (module-scope hoisting; recipe in the `i18n-tooling` skill) - it stays at zero. Lint-regression proofs count rule-fired warning lines by RULE ID (`grep -cE '^\s+[0-9]+:[0-9]+\s+warning'`), never lines containing the word `warning` - the summary line (`0 errors, 12 warnings`) also matches a substring count and skews the gate by one; when a per-rule distribution is needed, `awk '/^\/home/{file=$0} /RULE/{print file}' | sort | uniq -c` builds a warning-position map, where `grep -B` context windows smear eslint's per-file headers across neighboring files. When a spec pins a predicted count, re-measure clean HEAD instead of carrying the arithmetic forward - a stale prediction propagates a wrong gate. Build new components lint-quiet by construction: all state in a shared hook (zero `useState` in the component, e.g. `PeriodPicker`) and effects that only mutate the DOM (`scrollTop` math, no setters) - a structurally quiet component adds zero warnings whatever the baseline drifts to. For mount-time behavior (e.g. focusing a just-added row), set transient state inside the **event handler** that caused the mount, act via a plain HTML attribute (`autoFocus={condition}` - fires when the conditionally rendered content mounts), and self-clear in an `onFocus` handler - the self-clear keeps the behavior correct across unmount/remount of conditionally rendered content. Event handlers are not effects: the lint stays quiet. Don't reach for `useEffect` + `setState` or ref callbacks for this class of behavior.

The same warn-baseline discipline covers a second rule: `i18next/no-literal-string` flags JSX text and the placeholder/title/alt/aria-label props so new hardcoded English cannot land silently. Its floor is ZERO (the historical false-positive baseline was hoisted away - the suppression recipe is in the `i18n-tooling` skill); never add a warning of either rule.

**Render-adjusts - the sanctioned replacement for reset/seed effects.** When a transition fires from paths no single event handler observes (global listeners, outside-click, setters returned from a hook, router navigation), adjust state during render instead of in an effect: a `useState` latch initialized to the tracked value's initial state, then plain render code below the last hook (every hook and early return stays above it):

```tsx
const [prevOpen, setPrevOpen] = useState(open)
// …all hooks above the adjust
if (prevOpen !== open) {
  setPrevOpen(open)
  if (!open) setSearchQuery('')  // guard the companion update
}
```

- **Guard on actual-vs-desired, not on a prev-latch, whenever companion state gates rendering.** A latch can permanently drop its companion update: a parent's render-phase update (a form modal's session seeding re-rendering its subtree) can re-render the child so the latch applies while the mount update is discarded - the latch then reports "already handled" on every subsequent render and the sheet renders null forever (`prevOpen=true, mounted=false`; the live deadlock that ended the prev-latch era). The self-healing form, `if (open && !mounted) setMounted(true)`, re-evaluates its condition on every render and cannot get stuck. Exemplars: `useDelayedUnmount` in `common/BottomSheet.tsx`; the close-reset in `hooks/useListboxPanel.ts` has since grown handler-edge seeding on top of its adjust (next bullet).
- **Layer deterministic handler seeding at the open/close edges UNDER the adjust when transient panel state must not survive a close/reopen.** The adjust alone is render-CONDITIONAL: it only retries on a render that commits while open=false, so a close/reopen sequence with no committing closed-state render between them leaks the transient state into the reopened panel - the nested-sheet case: a searchable Select's BottomSheet opened inside a form modal's own mobile sheet, where a stale typed search survived a scrim-tap close and reopen. Handler seeding is render-unconditional: `openPanel` re-seeds the search and highlight at the open edge, and `closePanel` clears both in the same batched update as `setOpen(false)` at the close edge. That is safe only because the handlers run from closed state - `openPanel` is reachable solely from the closed trigger toggle (`open ? setOpen(false) : openPanel()` in every consumer) and ArrowUp/ArrowDown on a closed trigger, so it can never wipe a mid-session search, and MultiSelect's toggle-and-stay-open routes through `onActivate`, never through the handlers. The adjust stays anyway, byte-identical: `open` flips closed from paths the handlers never observe (Tab key, outside-click, the consumers' trigger toggles via the returned `setOpen`, any future direct `setOpen(false)`), so handler seeding alone would silently reintroduce the stale-state bug there; and clearing the highlight to -1 at both close layers only drops the closed dropdown's ring, because `openPanel` re-seeds it on every open. Exemplar: the three-layer split in `hooks/useListboxPanel.ts` - its comment block above the adjust is the authoritative narrative.
- **Loop-safety is structural, and stated in a comment.** Every branch's setState lands on a value that disproves its own guard on the immediate re-render (an auto-pick lands on a list member, a clear lands on null), so the adjust terminates by construction; the recommended-latest preset permits exactly this guarded form. StrictMode is idempotent for free: the second pass sees `prev === current` and sets nothing. The comment stating the argument stops a future editor "fixing" it back into an effect.
- **Per-session display state resets ride the SNAPSHOT adjust, not the session adjust - which render pass each fires on is load-bearing.** A form hook's session adjust runs on the boundary pass itself, where the session state variable still reads the OLD value; the seed-snapshot adjust (identity-latched, `snapshottedFor`) runs on the pass AFTER, when the seeded values are committed. Zeroing a per-session counter (`setSubmitCount(0)`) beside the snapshot re-baseline lands the reset and the fresh `isDirty` baseline in ONE commit, so a fields component keyed on the session (`key={form.sessionKey}`) mounts with the reset already in scope - no error flash and no focus steal on the first painted frame after a reopen. Loop-safe by construction: the companion write does not participate in the adjust's latch condition, so the adjust still disproves its own guard on the immediate re-render; within a session it never fires, so a failed submit keeps its errors until the user edits or the session changes. Exemplar: the snapshot adjust in `hooks/useTransactionForm.ts` (the reset also fires on every `resetForAnother` bump - hosts may rely on a fresh session starting with clean display state, and must not cache the counter outside the hook).
- **A mid-component fall-through adjust is safe for derived query keys - the discarded-pass argument.** On the transition render where the consume fires, derivations already resolve from the source that changed (`raw ?? latchDefault` resolves to the param for present bounds), so every derived query key is identical on both passes; the only divergent render (a partial-bound transition momentarily filling the missing bound from the default) is a pass React discards before commit, and effects and fetches never run from a discarded pass. The argument removes the "might fetch with default-filled bounds" fear that pushes authors back into banned effect writes.
- **Fold the mount case into the lazy initializer when the tracked value is accurate on first render.** `useBreakpoint` is (its `useMediaQuery` initializer reads `matchMedia` lazily), so a plain prev-latch would skip the mount transition the old mount-run effect handled: seed via `useState(() => (isTablet ? true : storedPreference))` and keep the adjust transition-only (crossing INTO tablet collapses; tablet-to-desktop leaves a manual un-collapse alone). Exemplar: `MainLayout`.
- **Async-data default selections are derived-until-touched, not latched.** `selectedId` + `touched` state with `id = touched && touchedInList ? selectedId : derived` - zero setState during render, and a touched pick that leaves the list falls back to the derived default deterministically. When the target file already hosts the idiom, a sibling selection mirrors it rather than importing a second selection idiom. Exemplar: `BudgetInsights`' budget/currency selections.
- **Query-lifecycle state uses a result-identity latch.** `doneResult !== seenResult` hands the review payload to state once per result OBJECT - dismissal cannot re-latch, a re-extraction's fresh result object can; a ref-based latch is illegal anyway (`react-hooks/refs` errors on ref writes during render). Exemplar: `hooks/useExtractionPolling.ts`.
- **An open-request seam into a component that owns a render-phase latch is a context-held monotonic tick plus a consumer-side render-adjust - never shared open state.** The consumer's close-on-navigation latch calls setState during its own render, legal only in the component that owns the state; a provider-owned open boolean would turn that latch into a render-phase update of parent state, which React forbids. Recipe (`AccountMenuContext`/`AccountMenuSheet`): the context exposes `open()` bumping a `useState` counter (`openTick`); the sheet keeps its open state locally and latches the tick with a self-disproving adjust (`const [seenOpenTick, setSeenOpenTick] = useState(openTick)`; `if (seenOpenTick !== openTick) { setSeenOpenTick(openTick); setMoreOpen(true) }` - exactly one open per request, zero effects in the consumer); any surface calls `open()` with no knowledge of the latch. Mount the provider ABOVE any breakpoint-branching layout split so the context identity survives the 640px crossing remount.
- **Consumer-side DOM that mounts a commit AFTER the state flip is observed with an identity-stable callback ref.** An effect keyed on the state cannot see the second event when the component's DOM appears a commit later (a delayed-unmount gate returning null until its timer): an `useCallback(..., [])` ref callback stores the node and runs the DOM sync on fresh attach, reading the state through a latest-ref mirror (an unstable callback detaches/reattaches every render and re-fires the sync on every keystroke). Keep the original state-keyed effect alongside when an exit window keeps the node attached on fast reopen - both paths call one idempotent helper. Exemplar: `sheetListRef` in `hooks/useListboxPanel.ts`.

**Grep/lint done-criteria gates - classify the failure before touching code.** Gates that grep the working tree count comment text and exact-cased identifiers only: keep gated literals out of the comments/docblocks of gated files (the phrase "Zero useEffect by construction" tripped a `grep -c 'useEffect' == 0` gate; comment mentions of `scrollIntoView` tripped a banned-call gate - both fixed by rewording the comment, zero code change), and a lowercase grep pattern cannot see a PascalCase setter (`grep 'periodModalNonce'` finds 2 lines, not 3 - `setPeriodModalNonce` hides its capital P; count exact-cased occurrences only). When a lint count disagrees with the spec, prove "pre-existing" mechanically instead of fixing a non-regression: `git show main:<path> | npx eslint --stdin --stdin-filename <path>` lints main's copy without touching the working tree, and findings compare by IDENTIFIER, not line number - earlier tasks' import lines shift rows without adding warnings. The same content-not-position comparison anchors token-REMOVAL gates: when the token being removed also appears in legitimate prose (`capture` also sits in "focus capture/restore" comments), enumerate the known prose hits (file:line) in the done criteria BEFORE editing and require `rg -n <token>` to list exactly that content after the edit - the gate then catches both a missed occurrence and collateral comment edits while staying mechanically checkable; lines below a deletion shift mechanically, so compare the listed content, never raw line numbers. The binding invariant is zero NEW warnings against the frozen baseline; a spec's per-file count that disagrees is a spec arithmetic error, and "improving" a pre-existing warning mid-pass is an out-of-scope refactor of working code. Deletion gates over shared symbol names are scoped to the task's file set from the start: sibling files own pre-existing locals with the same name (a repo-wide `\bsetAmount\b` count of 26 with every hit on `main` proves nothing about your deletion), so gate on the task files' content compared against `main`, never on repo-wide emptiness. Diff-level special-char gates (no added em/en dashes) constrain which LINES you may touch, not just what you write: a line carrying a pre-existing gated character (a U+2014 placeholder in a fallback render) re-emits it in any edit's `+` twin, so ANY edit to that line fails the gate. When a pinned edit collides with one, restructure the change so the line stays byte-identical - name the derived const what the consumers already read (rename the raw picked state instead) so every consumer line goes untouched - never re-type the character and never relax the gate. A formatter can force the collision anyway (ruff format re-indenting a docstring re-emits a pre-existing dash as an added line); repair via byte-anchored whitespace surgery - replace only the leading-whitespace prefix of the line, never retyping the character - and prove preservation from BOTH directions: zero dashed lines added AND zero dashed lines removed, which together show the pre-existing dashes as unchanged context. When the edit must genuinely rewrite the line's content (byte-identity is impossible), write the replacement with an ASCII hyphen where the dash stood - an added dash is the gate failure, and the hyphen rewrite lowers the count instead of re-typing the byte; quoted literal content that must stay byte-accurate (a msgid, a template's rule line) is the exception and is described in words rather than re-typed. Run the byte gate itself as `LC_ALL=C grep -P '\xe2\x80\x94'` (and `\xe2\x80\x93` for en dashes) - each spelling works in exactly one locale: a UTF-8 locale makes the byte pattern silently match nothing (every gate passes vacuously), and the C locale rejects the codepoint spelling outright (`\x{2014}` -> "character code point value in \x{} or \o{} is too large") - an errored grep piped through `wc -l` also prints 0, so check the exit code, not just the count.

- **A spec's pinned "frozen" comment text is NOT exempt from the spec's own gates.** A pinned docblock can carry the very literals the same spec's zero-count grep gates ban (a frozen comment containing `role="status"` against a `grep -c` gate of zero), so run every gate against the INTENDED file content - pinned snippet and comments included - before landing, and reword the comment semantically rather than weakening the gate. Counted-line corollary: an explicit type annotation naming a gated identifier (`useState<ReturnType<typeof monthRange>>`) adds a counted line - plain inference both satisfies the gate and tracks the helper's return shape.

- **A verification gate can itself be wrong in ways a correct implementation exposes - correct the gate's expected text, never the code.** Gate-script bug shapes seen in one extraction task: an end anchor truncated so it can never match the real line (`= s` vs `= useState(false)` - use the partition map's full anchor), an expected heredoc missing its inclusive end-anchor line, a heredoc listing diff lines in interleaved order where `diff -u` emits all `-` then all `+`, and `grep -cF 'a\|b'` (with `-F`, `\|` is literal and the count is always 0; alternation needs `-E`). When the implementation matches the spec's pinned intent but the gate script disagrees, re-derive the gate's expected text from that intent, report the correction, and never bend correct code to a broken gate.

- **A parallel-written spec reconciles against the LANDED code by adapting member names, never redesigning.** The landed API's name wins over the spec's planned name; missing members are added additively at the return-object/props seam; only members the spec explicitly deletes get deleted, and only after a consumer grep proves zero live consumers (a member whose backing state was deleted can still have callers). A pinned snippet can also be internally inconsistent with its own checklist - when a pinned latch cannot express a checklist-required interaction, extend the latch (add the missing arm) rather than forking the derivation; a props contract too narrow to reproduce shipped markup byte-equivalently is extended additively and flagged, never resolved by forking the markup.

When a `setState` in an effect is genuinely unavoidable, the rule reports **once per effect** (at the first violating call) — work within that granularity:

- **State seeded by an effect is declared ABOVE that effect.** `react-hooks/immutability` errors (not warns - "Cannot access variable before it is declared... prevents the earlier access from updating") on an effect referencing a setter declared later in the component body, even though a plain JS/TS closure would legally allow the later declaration. Declaration order is doubly load-bearing here: the seeded `useState` sits above the effect that writes it, while derived consts sit below the memo they read and above whatever consumes them.
- **Per-entity resets extend an already-flagged effect.** Resetting state on id change (stale period leaking across budget→budget navigation in an unkeyed route) goes INTO the existing `[entityId]` effect as more setters — zero new warnings. A new same-shaped effect would add one.
- **Adopting server truth is derivation, not effect-setState.** `const activePendingId = pendingId ?? serverPendingId` — a derived const is lint-quiet where copying the server value into state would add a warning, and the derived value drives the poll that eventually clears it.
- **Loaders stay effect-local.** A hoisted `useCallback` loader called from a mount `useEffect` is traced by the compiler lint across the `await` and produces a NEW warning even when every setter sits after the await — declare the named `async` loader inside the effect. Retry comes from an event-handler-bumped tick in the deps (`const [retryTick, setRetryTick] = useState(0)`; the Try-again button does `setRetryTick(t => t + 1)` — always lint-quiet).
- **Timed or staged progress setState lives ONLY inside the timer callback.** `useEffect(() => { const timer = setInterval(() => setStage((s) => Math.min(s + 1, last)), 1200); return () => clearInterval(timer) }, [isSubmitting, setupStages.length])` adds zero `set-state-in-effect` warnings - the rule flags synchronous setter calls in the effect body, and the timer callback runs on a later tick; a synchronous `setStage` seed in the same body would be flagged. Deps stay in the list-LENGTH member-expression form (see the length-keyed arrival adjust under Modal Pattern). Exemplar: `Register`'s setup-progress effect.
- **Event-to-effect signaling uses a one-shot ref flag, never state.** When an event handler must trigger behavior in an effect that runs after the re-commit (focus restore after a failed submit), the handler's `catch` sets `failedSubmitRef.current = true` and an `[isSubmitting]`-deps effect consumes it: `if (!isSubmitting && failedSubmitRef.current) { failedSubmitRef.current = false; submitButtonRef.current?.focus() }`. Ref reads/writes in effects are invisible to `react-hooks/set-state-in-effect`, where a boolean useState flag would add a warning and a pointless re-render. Exemplar: `Register`'s `failedSubmitRef`. The same flag discriminates event ORIGIN for a focus-only effect: a swap-style disclosure's textarea-focus effect runs only when the flag was set in the toggle's `onClick`, so an effect-driven pre-expansion (a hook's seeding pass flipping the disclosure open for a note-carrying source) leaves the amount field's `autoFocus` in charge. Exemplar: the note focus effect in `transactions/TransactionFormFields.tsx`.
- **React-Compiler lint mechanics around custom-hook tuples and memo deps:** a setter returned through a custom hook's tuple (`useDebouncedField`'s `setQuery`) loses its stable-setter recognition - `exhaustive-deps` then demands it in the consuming effect's deps (safe: it wraps a `useState` setter, stable at runtime), and `set-state-in-effect` stops flagging its calls, relocating that effect's single report to the next traceable setter (net zero against the frozen baseline). And a plain const holding a fresh array (`const rows = data?.items ?? []`) used as a `useMemo` dep trips "dependencies change on every render" - move the derivation inside the memo and depend on the stable `data` reference instead.

## URL Search-Param State Sync

Pages that mirror a selection into a URL param (`/budgets/:id?period=X`) follow a read-once / write-from-handlers contract (`BudgetDetailPage` is the exemplar):

- **Seed read via latest-ref:** `const periodParamRef = useRef(intParam(searchParams, 'period'))` plus a ref-sync effect whose body contains ONLY the ref write - no `setState`, so zero set-state-in-effect cost (render-time `ref.current` writes are illegal under `react-hooks/refs`). This extends the latest-ref rule under Contexts from callbacks to derived values: effects read the seed from the ref instead of the page subscribing to `searchParams` changes. The idiom generalizes to ANY opaque external-store seed, not just URL params: `react-hooks/set-state-in-effect` flags a setState whose ARGUMENT is an opaque external call (a `localStorage` read the compiler cannot analyze) even inside an otherwise-clean effect, while a `ref.current` read passes - so `const storedRef = useRef(readStoredValue(id))` as the initializer, a ref-write-only sync effect, and the consuming effect seeds from `storedRef.current`. The ref-sync effect must be declared BEFORE the consumer (effects run in declaration order, so the reset reads THIS entity's value). Exemplar: `BudgetDetailPage`'s `storedViewRef` per-budget view-currency seed. The ref-read bailout is per-argument and does NOT extend across `??` coalescing: a setState argument like `refA.current ?? refB.current` is flagged even though each ref read alone passes - seed a local const first (`const seeded = refA.current ?? refB.current; setX(seeded)`), which restores the bailout with byte-identical semantics (the `?currency=` seed in `BudgetDetailPage`). Probe a novel bailout boundary with a throwaway file before restructuring - guessing the fix blind risks weakening either the behavior or the gate.
- **A render-consumed stored seed is a lazy `useState` initializer, never a ref read.** `react-hooks/refs` errors on READING `ref.current` during render ("Cannot access ref value during render"), not just on writing - the ref seed above is effect-consumed only. A stored value the render itself consumes (a remembered search term) is seeded as `useState(() => urlHasParam ? '' : readStored())`: the lazy initializer runs exactly once, and the change handler clears it so a removed URL param can never re-apply the old term.
- **A localStorage-remembered list facet joins the filter registry as an EDITORLESS def (`editor: 'search'`).** Hosts offering editor surfaces skip it (the sheet hub and the Add-filter menu guard `d.editor !== 'search'` - an INACTIVE editorless def in the Add-filter menu would render an empty editor popover), the applied chip's body routes through a per-chip `onBodyClick` that focuses the always-visible search input (the chip-level flag also suppresses that chip's `aria-haspopup`/`aria-expanded` - focusing an input is not opening a dialog), and EVERY clear path (chip X, Clear all) kills all three storage sites - URL param + stored value + restored-hint state - in the SAME handler: on the next render `search = param ?? restoredSearch` resurrects the remembered term if only the param was cleared (with the single three-site call removed, the chip X visibly does nothing - storage re-applies the term). The recipe: registry entry (chip/badge/Clear-all coverage) + the editor kind + the page-owned three-site clear, with an exhaustive `case 'search': return null` left in `renderFilterEditor` so future editor hosts stay type-safe. Exemplar: the search facet in `Transactions.tsx`/`Planned.tsx` (`forgetStoredSearch`).
- **Effects NEVER write the URL - only event handlers and mutation callbacks do.** Sanctioned write sites: the selection setter invoked from the picker's `onChange`, adjacent/materialize navigation branches, and a delete mutation's `onSuccess` when it removed the selected id. An effect-side router write is both a fresh lint risk and URL churn - an auto-pick running in an effect would rewrite every entry URL.
- **Param-only navigation never re-runs `useState` initializers - the routes carry no `key`.** Navigating same-pathname-different-search (tapping a bookmark while already on the page) keeps the component mounted, so a mount-time initializer (e.g. `useState(() => paramCount > 0)`) is the ONLY pathway that class of navigation can bypass by construction - audit "state derived from URL" bugs against that fact before adding param-change machinery that can never fire.
- **A cross-route tab or link emits the DESTINATION's query string from a typed carry matrix, never a copy of the source query.** A tab switch is a scope change: every param the destination cannot render must drop, and a param whose TYPE differs per destination carries per-destination rules - `account` parses as a comma list on Transactions/Planned but a single id on Transfers, so the list carries between the two list pages and reaches the single-id destination only at list-length-1; `from`/`to` always travel verbatim. Enumerate each destination's param types, read each carried param once through the shared reader (both CSV and single-id shapes parse via `intListParam`, so only the emit differs per destination), and build `to + carrySearch(...)` in the click-time render - copying the whole query string leaks list-specific facets onto sibling lists that render them wrong. A create NAVIGATION into a page host is a plain push (never `replace`) - Back must return to the list the user came from, where `replace` is reserved for in-page selection writes (below). Exemplars: `carrySearch` in `layout/ActivityTabs.tsx`; the create-carry twin is the FAB in `layout/BottomNav.tsx` (a list-valued `account` param travels only when it resolves to exactly ONE id - the destination's single-id reader cannot render a CSV).
- **Sanctioned exception - a response-proves-staleness page reconcile.** A paginated list page reconciles a provably stale `?page=` through `useStalePageReset` (`utils/params.ts`): the trigger reads `page > Math.max(data.total_pages, 1)` of the MOUNTED response, never the response's returned `page` - under `placeholderData: keepPreviousData` the placeholder's returned page sits below the requested one on every forward navigation, so a `data.page` comparison yanks every "next" click back to page 1 - and the write goes through the page's own `createUpdateParams` updater, making the reset byte-identical to a page-1 chip click for reload and history. Response arrival is not an event (v5 removed `useQuery onSuccess`), so a guarded effect is the only possible seam; the trigger fires at most once per stale occurrence (`1 > max(total_pages, 1)` is false for every count).
- **Sanctioned exception - a client-side filter mirror closes a record the list no longer contains.** When list filters change under an open detail panel whose keep/close decision must track the server's list query, mirror the filters as a conservative predicate instead of refetching: exact BigInt cents only (never `parseFloat` - backend amounts are exact 2-decimal strings), and a bound with 3+ decimals must never round in the keep-open direction because the server compares the RAW decimal bound - ceil lower bounds toward +infinity, floor upper bounds toward -infinity (`tx >= ceil(bound)` proves `tx >= bound`). Facets the payload cannot evaluate (budget/category filters OR-match transaction items server-side, and item categories are absent from the list payload) read as no-match - a panel showing a record the list no longer contains is the worse failure mode. The reconcile effect navigates (never `setState`), holds while `recordLoading`, closes on `recordError`, and reads CURRENT filter values with a composed `filterKey` string as the change signal (sanctioned partial deps + disable comment). Exemplar: `recordStillMatches` + `amountBoundCents` in `Transactions.tsx`.
- **Sanctioned exception - a session-scoped default materialized once into the URL.** A page default whose absence must stay distinguishable from the user's explicit "everything" choice (with an implicit read-time default, absent params mean BOTH, and the escape affordance is unrepresentable) writes itself into the URL on first entry, composing three sanctioned shapes: (1) a lazy latch `useState(() => bothParamsAbsent ? defaultRange : null)` - a mount WITH any param never defaults (the `restoredSearch` idiom); (2) a fall-through consume adjust `if (latch && anyParamPresent) setLatch(null)` - no early return, hooks below unconditional - so clearing params later ("All time", "Clear filters") can never re-default within the session, while a fresh mount re-initializes; (3) the one-shot URL write in an effect guarded on the still-live latch, through the closure-wrapped `createUpdateParams` updater (`useStalePageReset`'s seam - `react-hooks/set-state-in-effect` cannot trace through the closure, and a render-adjust must never write router state). The latch is STATE, not a ref: suppressing the default after a user clear requires reading it during render, and `react-hooks/refs` errors on render-time `ref.current` reads. Reads (query keys, totals, export scope, chip labels) consume EFFECTIVE values derived in the page - explicit params win, both-absent falls back to the default, partial ranges pass through unfilled - while a shared self-contained filter component keeps reading RAW params: no visible mismatch exists (the panel is closed before materialization, and raw == effective after), and threading effective values as props would couple every consumer of the shared component. Exemplar: Planned.tsx's default month.
- **Stored per-user page defaults generalize the session-default latch behind an ARRIVAL GATE.** Server-side defaults must resolve before first render - a cold-cache mount that runs the latch against `settings === undefined` materializes the page BUILT-INS into the URL, then flips every control when the real blob lands a beat later; correcting after mount is racy, so gate arrival instead. Split the page: a thin wrapper owns the shell (h1 + header stay mounted for route-change focus), gates the content on the settings/preferences queries resolving (an errored query opens the gate with `undefined` - built-ins apply - per the known-gate rule), pulses a skeleton only after a 300ms timer (setter inside the timer callback only), and mounts the content once; the latch's settings-undefined branch is defense-in-depth for a total function, never the primary path. Materialization is TWO-CONDITION per facet: write iff (a) its URL params are absent (any deep link wins outright, present-but-garbage included) AND (b) the resolved default (null facet -> page built-in) differs from what absent params already express - a saved built-in leaves the URL byte-identical to the pre-feature page, and only named presets are default-able (an edited absolute range reverse-resolves to nothing by exact-equality against the current period). With N facets, per-facet consume adjusts MUST use functional updaters - an object-spread of the closure's stale latch lets the last write resurrect facets an earlier one killed when several consumes fire on the same pass - and the one-shot write emits ALL live facets atomically, never gated on an EFFECTIVE (derived) facet value: the latch fallback flips the effective view before `?view=` is written, so gating on it deadlocks that write permanently. A LIST-valued facet presence-branches outright (`rawType !== null ? parse : (latch.type ?? [])`) - a CSV cannot half-match, so it has no enum-facet "valid but non-default single value" middle state; do not unify the two disciplines. Cross-boundary intent (header New -> content-owned modals) travels as an incrementing counter nonce consumed by a render-adjust initialized to the CURRENT counter (a zero init re-opens the modal on every gate-reopen after a workspace switch that follows an earlier click), and the wrapper's export handler reads the URL at click time instead of threading effective derivations across the boundary - the URL is the source of truth once defaults materialize into it. Exemplars: the gate-wrapper + content splits in `Planned.tsx` / `Transactions.tsx` / `TransfersPage.tsx`, with the pure latch/capture core in `utils/pageDefaults.ts` (`buildDefaultsLatch` / `capturePageDefaults`).
- **Writes use functional `setSearchParams` with `{ replace: true }`.** The functional form preserves unrelated params (same shape as `createUpdateParams` in `utils/params.ts`); `replace` keeps selections out of history so Back leaves the page in one press.
- **Effect declaration order is load-bearing.** Ref-sync effect BEFORE the `[entityId]` reset effect (the reset seeds from the ref, so the ref must already hold the NEW URL's value on mount and entity-to-entity nav); the reconcile effect also before the reset effect (its seed must land last, beating a cached `currentPeriod` auto-pick mid-race) but AFTER any memo its deps reference - a deps array naming a later-declared const is a TDZ `ReferenceError`.
- **Two effects writing the same state in one flush can coalesce the first write away - guard the LATER write functionally.** With a warm query cache, an auto-pick effect (declared first) can queue `setPeriodId(currentPeriod.id)` and the `[entityId]` reset effect then call `setPeriodId(null)` in the SAME effects flush: the updates coalesce to null, no dependency ever changes, and the pick never re-fires - works on cold mount, dead on warm remount, no error anywhere (the deps array cannot see it: the loser's re-trigger condition is "the value changed", and it reads null to null). Fix the later effect with a functional, membership-guarded write: an explicit `?period=` seed wins outright, a same-entity pick queued in the same flush survives (`prev` still belongs to this entity), foreign ids still clear immediately for entity-to-entity navigation. Feed the updater's membership data through a latest-ref synced by a ref-write-only effect - ref reads INSIDE a setState updater closure are exempt from `react-hooks/exhaustive-deps`, while putting the list in the effect deps would re-run the whole reset effect (and every seed it owns) on each refetch. The guarded write is StrictMode-idempotent, unlike a skip-first-run latch. Exemplar: `BudgetDetailPage`'s `allPeriodsRef` + functional `setPeriodId` reset; the ref-sync effect stays between the memo it mirrors and the reset effect that reads it.
- **Garbage or foreign seeds reconcile by clearing state only** - never an effect-side URL rewrite; the URL keeps the bad param and self-heals on reload. Gate the clear on the data being authoritative (`periodsLoaded && currentPeriodKnown`): a valid seed may equal a lazily-materialized current period that is not in the periods list mid-race, and clearing it early flashes the wrong selection.

## API Client Pattern

```typescript
// Categories are nested under a budget (see budgetsApi in client.ts):
export const budgetsApi = {
  listCategories: (budgetId: number, includeArchived = false): Promise<Category[]> =>
    api.get<Category[]>(`/budgets/${budgetId}/categories`, { params: { include_archived: includeArchived } }).then(r => r.data),
  createCategory: (budgetId: number, data: { name: string }): Promise<Category> =>
    api.post<Category>(`/budgets/${budgetId}/categories`, data).then(r => r.data),
  // …update / archive / delete follow the same nested shape
}
```

**Export type aliases for repeated literal unions:** When a literal union (e.g., ordering options) is used in more than one place, export it as a `type` alias at the top of `client.ts` and import it at call sites — don't inline the same union in multiple files:

```typescript
// client.ts
export type TransactionOrdering =
  | '-date' | 'date' | '-description' | 'description'
  | '-amount' | 'amount' | '-type' | 'type'
  | '-category__name' | 'category__name'
  | '-account__name' | 'account__name' | '-account__currency__code' | 'account__currency__code';
```

**Per-request headers via an optional `opts` bag:** `create(data, opts?: { idempotencyKey?: string })` injects the header with a conditional spread on the axios config — `...(opts?.idempotencyKey ? { headers: { 'Idempotency-Key': opts.idempotencyKey } } : {})` — so call sites without the option are untouched. Never push per-request headers onto `api.defaults.headers`; that leaks across requests.

**One base-URL seam for out-of-band requests:** `getApiBaseUrl()` is exported from `api/client.ts` and the axios `baseURL` routes through it - any request that bypasses the axios instance (a keepalive `fetch` that must outlive the page, a worker) calls the helper instead of re-deriving the `getRuntimeApiUrl() || VITE_API_URL || localhost` chain, so the two can never drift.

**Write payloads declare a dedicated `XInput` interface, never `Partial<Entity>`** (`TransactionInput`, `BudgetInput` in `client.ts`): the interface lists exactly the fields the frontend actually sends, so adding a payload field is a documented decision. `Partial<Budget>` keeps silently accepting `id`/`workspace_id`/`created_at`, and the next payload field becomes an accident of the response type instead of a declared contract. Response and payload interfaces mirror the backend wire format (snake_case fields like `category_id`); camelCase lives only on editing-row shapes (`Row.categoryId`), and exactly one seam module (`utils/transactionItems.ts`) maps between the two.

**Additive backend enrichment fields are OPTIONAL on the wire type and read `!= null`.** A nullable field an older backend omits entirely is typed `x?: T | null` so absence is representable in the type itself, and every read treats `undefined` (key absent) and `null` (explicit empty) identically (`x != null`, `?? null` on derived values) - no version flag, no feature gate. The frontend tolerating absence by design is what lets the backend field land additively. Exemplar: the `last_*` fields on `FrequentDescriptionItem` in `types/index.ts`.

**Full-replace PUT contracts make EVERY update call site echo the derived fields.** When a backend update becomes full-replace (the whole resource is rewritten from the payload), every caller that updates in place - including best-effort follow-ups like a post-parse description update - must echo the fields the server now requires (`currency_code: p.currency_code`), or account-less rows 400 and a swallowing `catch {}` silently drops the side effect. When the payload contract gains a required-when-X field, grep the sibling `xxxApi.update` call sites across pages and modals - the sites that break are the ones that never looked like update flows (a cancel action, an extraction review). For an OPTIONAL field under a full-replace PUT this inverts the optional-fields rule: every create and update payload sends the key, with `null` as the cleared value (`note: note.trim() || null`) - direct field assignment server-side makes the schema default the stored value, so an omitted key silently wipes stored data; pin the contract in a doc comment on the `XInput` field so the next payload editor sees it. Close the sweep with a two-way grep: the API method's call sites PLUS the raw `api.put('/<endpoint>'...)` path - only the second grep proves no untyped bypass exists. Payload fields echoed from a stored object pass through verbatim (`note: transaction.note`); `trim() || null` normalization belongs only to fields sourced from user input. A one-field editor over such a PUT concentrates the rule in a save hook: `mutationFn` assembles the COMPLETE payload from the loaded row (verbatim echo of every stored field, the null-capable keys always sent even as null, the patch spread on top), making a one-field edit structurally unable to clear another field; editors normalize values before calling and the hook forwards patch values verbatim. Exemplar: `hooks/useTransactionFieldSave.ts`.

**A DELTA field on a full-replace list omits on `undefined` - the inverse of the always-send-null rule.** When the backend reads a field only when sent (`Optional[...] = None`, acting only `if ... is not None`, so an omitted key keeps the stored value), the client method takes `x?: T | null` and the body conditionally spreads the key only when defined: `undefined` is the omission signal, never null - the day a backend distinguishes null from omitted, an always-sent null silently flips from "leave unchanged" to "user cleared it". When the backend instead treats null and omitted IDENTICALLY (no clear path exists), a string field with a reset affordance uses `''` as the explicit reset value (honored and stripped server-side): send user-input-sourced values unconditionally trimmed, never `|| null` - against such a backend, `|| null` silently KEEPS the stored value instead of reverting to the default. The remainder controls on `replaceItems` are the exemplar.

**A list response that embeds a server-owned system row is filtered at EVERY mapping-to-payload site.** GET/PUT items responses include the remainder row (`is_remainder: true`); the write payload cannot express the flag and the backend schema ignores unknown keys, so an unfiltered echo is silently stored as a USER row, double-representing the derived amount with no 400 anywhere. Filter `!i.is_remainder` in every consumer (the items editor and the extraction review both do), read the system row via a find-helper, and write it only through the dedicated replace params.

**Internal per-request flags go through axios module augmentation, never `as any`:**

```typescript
// api/client.ts
declare module 'axios' {
  interface AxiosRequestConfig { _skipAuthRefresh?: boolean }
}
```

Augmenting `AxiosRequestConfig` also types `error.config` (`InternalAxiosRequestConfig` extends it), so producer and consumer sites stay fully typed with zero casts.

**Idempotency keys on create mutations:** `crypto.randomUUID()` per modal session - stable within one open, fresh across opens. A modal that seeds in a session render-adjust mints the key in the adjust's create branch (`null` in the edit branch); a permanently-mounted modal reset via `close()` → `reset()` uses a lazy `useState(() => crypto.randomUUID())` initializer and regenerates inside `reset()`.

**Backend-mirrored constants:** `PAGE_SIZE_OPTIONS` in `utils/pageSize.ts` duplicates the backend's `ALLOWED_PAGE_SIZES` — the user's choice is persisted to localStorage and sent as `page_size` on every list request, so the two lists must change together (the 422 trap is documented under Pagination Param Caps in the `django-backend` skill). Put an inline sync comment at the constant itself in the one-line `/** Synced with backend <file> <CONSTANT>. */` format (see `TotalsLabel`) — the coupling knowledge belongs where the next editor actually looks, not only in this skill. Mirrored reference DATA pulls from the backend's data module, never its seed command - `PRE_AUTH_CURRENCIES` in `utils/currencies.ts` mirrors `currencies/data.py`'s ISO 4217 rows byte-for-byte under a source-naming sync comment. Ordering type unions in `client.ts` are the same mirror for the backend's `ORDERING_PATTERN` allowlists - they widen in lockstep with the backend change that widens the pattern. The same discipline applies to format strings: `formatPeriodName` (`utils/format.ts`) mirrors the backend's period-naming format (dd MMM + en dash) and is persisted as period names, while the adjacent display-only `formatPeriodRange` ("Apr 1 - Apr 30", regular hyphen) is deliberately different - harmonizing the look-alikes would corrupt the mirror, and the separator difference is invisible in review surfaces. The docblock adjacency warning between them is the guard; do not remove it.

## Blob Downloads and Object-URL Ownership

Files behind authenticated endpoints are fetched as blobs through the axios
client (`responseType: 'blob'`, e.g. `transactionsApi.downloadAttachment`) -
browsers cannot send the JWT header on navigations, so `<img src>`/`<a href>`
pointing at the API never works; `URL.createObjectURL` bridges blob -> URL. The
load-bearing contract is that exactly one site creates a URL per lifecycle, and
`URL.revokeObjectURL` ownership is explicit at each call site (exemplar:
`hooks/useAttachments.ts` + `utils/attachments.ts`):

- **The query cache mints and pins display URLs.** The blob query's `queryFn`
  returns `URL.createObjectURL(blob)` with BOTH `staleTime: Infinity` AND
  `gcTime: Infinity` - the bytes are immutable, and the default 5-min gc drops
  the cache entry, leaks its object URL, and mints a duplicate URL for the same
  bytes on remount.
- **A download-to-disk mutation creates and revokes its own short-lived URL**
  around the programmatic anchor click (`useAttachmentDownload`).
- **A reuse path NEVER revokes a cached URL.** The lightbox reuses the URL
  passed in from the tile's cached data - revoking it after close would poison
  the thumbnail that still references it. Shared download helpers stay
  deliberately revoke-free (`triggerBrowserDownload`); never "simplify" the two
  paths into one helper that always revokes.
- **Per-item blob queries live in a child component** (`AttachmentMedia`) -
  hooks cannot be called inside a list `.map()` callback; the parent's map keeps
  the stateless chrome (border, delete button, extraction overlay).
- **Delete mutations drop the deleted item's blob cache entry**
  (`queryClient.removeQueries({ queryKey: attachmentBlobKey(...) })`); the
  object URL itself is reclaimed at document unload, bounded by the
  per-transaction attachment caps. A new blob consumer reuses the same client
  call and key builders instead of minting a second query family for the same
  bytes.

## Money Arithmetic (Exact Strings)

Backend Decimal amounts cross the API as strings; any arithmetic whose result is **persisted or sent back** must be exact string/BigInt math via the helpers in `utils/format.ts` (`subtractAmounts` — BigInt cents, 3rd-digit round-half-up, never returns `'-0.00'`). Never `parseFloat` a backend Decimal that will be persisted: a 17-digit Decimal through `parseFloat` loses the last cent, and the wrong delta gets recorded as a real adjustment transaction. Floats are for validation/display only. The exact arm also covers categorical CLAIMS, not only persisted values: an over/not-over boundary that decides chip text, link-side grouping, or sort position is a `subtractAmounts` sign check (exact cents), because a float compare can flip a row at exact equality by a fraction of a cent - a wrongly-labeled OVER chip is a false alarm, not a rounding artifact - while the percentage itself stays float math for display and pct-ordering.

**A total displayed beside a table is an exact BigInt sum over the rows that table renders - never an API summary total whose scope differs from the visible table.** The budget summary endpoint includes archived categories' money while the ledger table filters them out, so an API-sourced total disagrees with the very column it sits under and reads as a wrong sum; summing the rendered rows is the only total that matches what the user sees. This is the display-side arm of the exact-math rule above: a total that must match its visible column exactly is exact math too - 17-integer-digit Decimals lose their last cent through `parseFloat`, and a visibly-off total is the same failure as a wrong persisted delta. Exemplar: `BudgetDetailPage`'s `totalPlanned`/`totalActual`/`totalRemaining` consts (`sumAmounts(rows.map((r) => r.planned))` etc.) feeding the desktop `<tfoot>` row and the mobile totals card.

**Adding an exact-money helper: mirror the shared output idiom verbatim, and treat the docblock's worked examples as the review contract.** A new helper lives beside the others in `utils/format.ts` (`sumAmounts` beside `subtractAmounts`), reduces over module-private `toCents` with a `0n` seed, and reuses the shared output idiom (`.toString().padStart(3, '0')` + slice, never `'-0.00'`) - a second formatting path drifts. `toCents` stays module-private by design, so negativity of a formatted money string is the string-sign check `startsWith('-')` at the call site - sound only because the helpers never emit `'-0.00'`. The frontend has no test runner, so the docblock's worked examples ARE the helper's contract: execute them against the real module (a throwaway `node` import) before landing instead of trusting the author's arithmetic, and keep them in sync if the behavior ever changes.

Number-input values are arbitrary strings — `'1e5'`, `''`, `'.5'`, `'5.'` — so validate with a regex (`/^-?(\d+(\.\d*)?|\.\d+)$/`, which also rejects e-notation) before the BigInt math. BigInt itself accepts leading zeros; only the regex gate keeps scientific notation out.

**User-typed amounts normalize at the commit boundary, never per keystroke.** Money inputs are `type="text" inputMode="decimal"` and their state holds the raw draft string; `normalizeAmountInput` / `parseAmountNumber` (`utils/amountInput.ts`, style-aware via live `getNumberStyle()` reads) run only when the value is committed. A submit seam threads the normalized value as the `mutation.mutate(arg)` argument into `mutationFn` (no new state, no effects, lint-quiet); a filter input wraps its debounced commit inside the shared component (`onCommit(normalizeAmountInput(next) ?? next)`). Never reformat the field on keystroke or blur. `parseFloat` on user input is forbidden - it silently truncates at the decimal comma ('1,5' parses as 1); display-only seams use `parseAmountNumber` with a tolerance (`?? 0`, `?? 1`) and never toast-and-abort (a collapsed-card preview must not error mid-edit). Submit seams toast the shared `common`-ns `validation.amountInvalid` key only for unparseable NON-EMPTY input - the empty case belongs to the form's per-namespace required-key rules and keeps its existing payload behavior.

## UI Text and i18n

Every user-visible string goes through `t()` from `useTranslation('<namespace>')`. The UI ships in English, Ukrainian, and Polish; a new UI string is THREE files' worth of work: the `t()` call plus the key in the owning namespace's `en`, `uk`, and `pl` JSONs under `src/i18n/locales/` - `npm run i18n:check` fails a key that exists in one language and not the others. Namespaces map to owning surfaces (auth, nav, accounts, transfers, budgets, transactions, planned, bookmarks, dashboard, members, settings, common, numbers - canonical order is `NAMESPACES` in `src/i18n/index.ts`, and the table lives in `docs/i18n.md`); a component adds keys only to its own namespace.

- **`aria-label`, `placeholder`, `title`, and `alt` are UI text.** They go through `t()` like JSX text. The ESLint `i18next/no-literal-string` rule (warn) flags new literals in those positions and in JSX children - see the baseline note in §State Changes in Event Handlers, Not Effects.
- **An aliased `t` is flagged in EVERY JSX position - attribute values, JSX children, and expression containers alike; hoist it to a const wherever it renders.** `const { t: tBookmarks } = useTranslation('bookmarks')` reads fine, but the rule recognizes only the unaliased `t` callee, so `title={tBookmarks('add')}` warns while `title={label}` from a body-level `const label = tBookmarks('add')` is invisible to it. There is no JSX position where the alias itself is safe - hoist every aliased-t call that renders, attributes and children alike (an early session note claiming children were exempt was disproven against the linter: a rule-boundary note is a claim about code - re-prove it before relying on it).
- **Module-level label arrays hold keys, not text.** The nav-item arrays (`Sidebar`, `BottomNav`) store key strings (`as const`, so `labelKey` stays a literal union) and resolve them in the component body via `t(item.labelKey)` - the same trap shape as any module-level constant: English text at module scope has no hook in scope and silently ships untranslated. Under typed i18n resources `TFunction` is NOT assignable to `(key: string) => string`, so a shared label-lookup helper cannot take the translator as a parameter - it RETURNS the `as const` labelKey and each caller translates it with its own namespaced `t()` (the pages' `statusLabel` shape, generalized as `labelKeyFor` in `WorkspaceDefaultsSection`).
- **A genuinely dynamic i18n key resolves ONLY through the defaultValue overload.** Under typed i18n resources (i18next `CustomTypeOptions`), `t(d.labelKey)` with a wide `string` key does not compile - and neither does the cast `t(d.labelKey as Parameters<typeof t>[0])` (`Parameters` picks the last overload, which resolves to `never`). The one compiling form is a helper: `const filterLabel = (key: string) => t(key, { defaultValue: key })` - behavior-identical for every landed key, and a missing key renders itself (visible, never a silent blank). The static side of the same coin: a literal-union key from an `as const` array (the nav-item `labelKey`s above, `DATE_PRESETS` presets) compiles fine through plain `t(key)` - the trap exists only for wide `string` keys, where the helper is the page-resolved seam every host reuses. A registry of cross-namespace labelKeys uses the qualified `'ns:key'` form, which resolves through ANY namespace's `t()` at runtime (a page's own-namespace `t()` resolves both its plain keys and the qualified ones), so one helper serves mixed-origin keys. Verification trap: a typecheck probe must use the build's own invocation - `tsc -p tsconfig.json` against the root project (`files: []` + references) checks NOTHING and false-passes; only `tsc -b` (or `-p tsconfig.app.json`) type-checks sources. Exemplar: `filterLabel` in the Activity pages (`pages/Transactions.tsx`), threaded into `FilterChipsBar`/`FilterSheet`.
- **A variant entry on an `as const` module-level array needs NO type annotation - the inferred element union is the discriminator.** A range-less preset beside keyed entries (`{ labelKey: 'listFilters.presetAllTime', allTime: true }` among the `{ labelKey, range }` rows of `DATE_PRESETS`) narrows via `'allTime' in preset ? null : preset.range()`; an explicit annotation flattens the union to its common shape and silently breaks the `in`-narrowing. An absence-variant's ACTIVE condition mirrors its click payload by construction: a click that clears both params (`{ from: null, to: null }` - a ParamPatch deletes the keys) pairs with an active test that both raw params are unset.
- **Registry/catalog display data is DATA, not UI text.** A language's `nativeName`/`englishName` from `backend/common/languages.json`, currency codes, and other reference values that are already human-readable render verbatim - never `t()`-wrapped (there is no key for them), never uppercased or letter-spaced (Slavic and non-Latin self-names break). Only chrome around the data translates. Static data in public assets outside the i18n runtime (`manifest.webmanifest` shortcut names) is English-only by the same rule - the runtime never loads there.
- **Registry derivations live at module scope.** Consume a shared registry once per file: `Object.fromEntries(registry.fonts.map((f) => [f.code, f.cssStack]))` for a code->value map (with an explicit `Record<string, string>` annotation) and a plain `.map` for option lists (`{ value: f.code, label: f.label }`); seed state defaults from `registry.default*`, never a bare literal repeated per site. A code added or renamed in the JSON then appears everywhere with no second edit. Exemplars: `UserPreferencesContext` (`FONT_STACKS`), `PreferencesForm` (`FONT_OPTIONS`).
- **Operator semantics are load-bearing when substituting registry defaults for literals.** Keep `??` where the operand is non-optional on a nullable object (`preferences?.font_family ?? registry.defaultFont` - fires only logged-out/pre-fetch) and keep `MAP[value] || MAP[registry.defaultFont]` fallback chains verbatim: dropping the `||` arm lets a stale stored code assign `undefined` to `document.body.style.fontFamily`, reverting the whole UI to the browser default serif. Do not "upgrade" `??` to `||` or flatten the chain.
- **A registry-driven Select clamps stale stored codes in its seeding effect.** Select renders a blank trigger (`placeholder ?? '\u00A0'`) when the value matches no option, so an unknown stored code displays as empty. A membership test in the seeding effect (`registry.fonts.some((f) => f.code === stored) ? stored : registry.defaultFont`) subsumes the old `|| default` falsy arm (an empty string matches no code), and a later Save persists the default, participating in backend self-heal. Clamp ONLY the registry-backed field - neighbors whose `|| registry.default*` shape is already correct keep it. Exemplar: `PreferencesForm`.
- **A deleted component's catalog keys are removed in the same change, and its dead CODE name reaches zero repo-wide** (`rg <Name> frontend/src` empty): file, imports, usages, and every comment/docblock mention reworded in the same commit - a name surviving in a comment resurrects the convention for the next reader. Dead keys left behind fail nothing at runtime but rot the catalogs; `npm run key:find` must run clean after the deletion and `key:rm` is never `--force`d (tooling rules, incl. the escape-restore cure after a `key:rm` run, in the `i18n-tooling` skill).
- **Plurals use i18next `count`:** `t('multiSelect.selectedCount', { count: n })` (exemplar: `MultiSelect`) with `selectedCount_one`/`selectedCount_other` in English and the full `_one`/`_few`/`_many`/`_other` set in Ukrainian and Polish - both Slavic languages need all four forms, and `i18n:check` validates the category set per language via `Intl.PluralRules`. A label that renders its numeral separately (a font-mono count beside the noun) still pluralizes through `count` but carries no `{{count}}` interpolation - `count` selects the plural form even when nothing interpolates (exemplar: the filter surfaces' `sheetNoun` keys). Interpolation is `{{name}}`; never concatenate translated fragments with `+`. `values` is a plain safe interpolation name, not a reserved i18next option key - `t(key, { values })` fills `{{values}}` (verified live against the installed i18next).
- **`formatPeriodName` never localizes** - it mirrors the backend's period-naming format and its output is persisted as period names (the full warning and the do-not-unify rule against `formatPeriodRange` are in Backend-mirrored constants under API Client Pattern). Do not route it through `t()`; do not "fix" its en dash.
- **Month and date names come from the date-fns locale, never from i18n catalogs.** A locale-formatted date phrase goes through the `utils/format.ts` formatters' locale wiring (`formatMonthYear(isoDate)` = `format(parseISO(isoDate), 'MMMM y', { locale: formattingConfig.dateLocale })`, beside `formatPeriodRange`), and a catalog message that would interpolate a month name carries NO interpolation - compose the message around the formatted label instead. The locale owns grammatical case: Polish renders a month-year date phrase in the genitive ("października 2026" for 'MMMM y') because that is correct Polish for a date phrase - derive expectations from the locale library's output, never "fix" the case toward a spec's illustrative nominative.
- **Backend errors arrive already translated** - the API client sends `Accept-Language` (`setApiLanguage`), so `getApiErrorMessage(error, ...)` receives a localized `detail`. The FALLBACK argument is frontend UI text and goes through `t()` like any other string.

## Contexts

```typescript
const { user, isAuthenticated } = useAuth()
const { workspace, workspaces, switchWorkspace, createWorkspace, deleteWorkspace, userRole } = useWorkspace()
// No global account/period context — use hooks/useDomain.ts and page-local period state.
```

**Stable context values:** wrap every context function in `useCallback` and the value object in `useMemo`. When a callback reads mutable state, prefer a functional `setState` update (`setUser(prev => prev ? {...prev, ...patch} : prev)`, empty deps) over listing the state in deps — stable identity beats freshness for context functions. Every render of an unmemoized provider recreates its function values, so any consumer effect keyed on them replays — the verification-pages double-POST class of bug.

**Latest-ref for context callbacks consumed in effects:** `const fnRef = useRef(fn)`; `useEffect(() => { fnRef.current = fn }, [fn])` — effect deps then stay `[realDeps]` while the effect always calls the current callback. Sync the ref inside an effect; render-time `ref.current = fn` writes are an ERROR under the `react-hooks/refs` rule — do not "simplify" back to them.

**Singletons shared between `main.tsx` and contexts live in their own module** (`api/queryClient.ts`), never exported from `main.tsx` — importing app code from the entry file creates a circular import the moment that module imports anything from the app.

## Runtime Config and Build-Arg Env Values

Deploy-time values (API URL, demo mode) are runtime config, not build args: the ui container's entrypoint writes `/config.js` (`window.__APP_CONFIG__ = {"apiUrl":...,"demoMode":...}`) from its `API_URL`/`DEMO_MODE` env at startup, `index.html` loads it before the bundle, and every consumer reads it through the helpers in `src/runtimeConfig.ts` - never `window.__APP_CONFIG__` ad hoc. Precedence at each read: `window.__APP_CONFIG__` -> `import.meta.env.VITE_*` -> hard-coded default (`http://localhost:8000/api` / `false`). The Vite arm is dev-server only (the root `.env`'s `VITE_API_URL`/`VITE_DEMO_MODE` reach the Vite process env: `dev.sh` sources the file on the host, the `node` service takes it via `env_file`) - `/config.js` 404s on the Vite dev server, which is expected, and the chain falls through; the `vite-ignore` attribute on its `index.html` tag keeps the build from warning about an unbundleable classic script. Demo mode is case-insensitive end to end, matching the backend's `DEMO_MODE.lower() == 'true'`: the container hook normalizes the value to lowercase (so a shared `prod/.env` `DEMO_MODE=True` cannot crash-loop the ui while the backend accepts it) and the Vite arm lowercases before comparing. `VITE_APP_VERSION` is the one remaining baked build arg (release.yml passes exactly it): module-scope read with an inline `||` fallback (`import.meta.env.VITE_APP_VERSION || 'dev'`, `ProfilePage.tsx`) - local dev and dev compose builds pass no build args, and without the fallback a non-release build renders `undefined`.

## Naming Conventions

- **Components**: PascalCase (`TransactionsTable`, `SplitView`)
- **Functions**: camelCase (`handleSubmit`, `fetchData`)
- **Constants**: camelCase for objects and module-scope DERIVED values, UPPER_SNAKE for authored literal sentinels - `savedToken`/`savedLanguage` (client.ts) and `appVersion` (ProfilePage) are camelCase derivations even though primitive, while `TOKEN_KEY`/`NO_ACCOUNT` are UPPER_SNAKE: the UPPER name is the grep target for an authored literal, and a derived value has no literal to find.
- **Types/Interfaces**: PascalCase (`User`, `Transaction`, `Props`)
- **Event handlers**: `handle` prefix (`handleSubmit`, `handleClick`)
- **Comments**: plain-language rationale only - never planning artifacts ("(R1)", "patterns.md SS3", task ids, "(plan decision N)", "(SKILL §section)"). Review-round and spec references are meaningless outside the session that wrote them, and the citation forms rot mechanically: "(plan decision N)" points into `.plans/`, which is pruned post-merge, and "(SKILL §...)" section numbering reshapes on every skill promotion - both targets disappear while the code stays. A comment must state the WHY so a reader with no access to the plan can act on it. The check applies to handed-down spec snippets too: a pinned snippet whose docblock carries planning artifacts (goal/requirement/phase ids, ruling attributions) is reworded to plain-language rationale at landing time - the substantive statement stays, the designator dies.
